## AI Code Review — NFL Draft Simulator v20 (Excerpt)

### Overall Verdict

This is an unusually deep piece of work — a full draft sim, unit-based game
engine, personnel/game-plan search, procedural recaps, awards, and a 100-season
audit, all in one portable file. The quantitative design (soft-capped point
channels, Hungarian-algorithm lineup optimization, Monte-Carlo draft-priority
forecasting, procedural recap variety) and the explanatory copy are genuinely
excellent. The problems are concentrated in three areas: one crash bug, a
malformed document header, and the costs of a 6,400-line monolith with no
persistence.

### Bugs to Fix First

**1. `rWeights` is never defined — the 100-season report crashes.**
At `NFL Draft Simulator v20 Claude.html:6018` the report template interpolates
`${rWeights.toFixed(2)}`, but a grep shows that identifier appears exactly once in
the file and is never assigned. When `runLeague100` finishes the progress bar and
calls `render100()`, evaluating the giant template literal throws
`ReferenceError`, so the user watches "Season 100 of 100…" and then nothing
happens. Either compute the number (e.g., Spearman correlation between the rankings
implied by `weights`/`modelWeights()` and the simulated `avgW`) or delete that
sentence. This is the one fix I'd make immediately.

**2. The document has two merged HTML documents.**
Line 1 is a complete mini-document (`<!doctype html><html><head><meta charset=utf8>…</head><body>`),
then lines 2–4 open a second `<!DOCTYPE html><html lang="en"><head>`. The parser
ignores a second `<html>` start tag in `in body` mode, which means the real document
root ends up with no `lang` attribute (an accessibility and SEO miss), plus you get
duplicated charset/viewport metas and a nested `<head>` that browsers salvage
inconsistently. Merge the safe-area/`[hidden]` bootstrap styles from line 1 into the
single real `<head>` and delete the duplicate doctype/html/head/body wrapper.

**3. Pick-critique prose contradicts its own math.**
The intro paragraph says wins are measured "against a 75-rated player" (`:5548`)
but `valueAt` subtracts `slotWins(s, WINS_BASE)` with `WINS_BASE = 70` (`:5522`),
and the table header says 70. Change the sentence to 70.

**4. Dead code in `initGroupRankings`** (`:849`–`:854`): the first loop appends
empty optgroups that are immediately wiped by `sel.innerHTML = ''`. Delete the
loop.

**5. Trivia:** `sp` is unused (`:5968`); `renderDraftBoard2` reads `draftPosFilter2.value`
three times under three names (`:1629`–`:1631`); `.needslabel` is defined twice in the CSS
(`:195`, `:212`).

### Architecture & Maintainability

- **Everything is global.** ~100 top-level functions and a dozen mutable globals
  (`draftSim`, `seasonState`, `weights`, `draftUI`, `league100`, …) in one script
  with no `'use strict'` and no IIFE/module boundaries. This is why a typo like
  `rWeights` survives — nothing catches it until the code path runs. Minimum viable
  fix: wrap the whole script in one IIFE and lint it (`npx eslint` with
  `no-undef` would have caught bug #1 for free). Better: split into ES modules
  (data / engine / narrative / UI) with a bundler, keeping a single-file build
  output if portability matters.

- **Positional arrays with magic indices.** `p[0]`, `p[3]`, `p[4]`… appear at dozens
  of call sites. Player tuples `[name,pos,team,ovr,spd,str,agi,cod,inj,awr,xf]` are
  fine for size, but convert once at load into `{name, pos, ovr, spd…}` (1,200
  objects is nothing) or at least define `const NAME=0, POS=1, OVR=3…`. It would
  eliminate a whole class of silent index bugs.

- **Data redundancy.** `TEAM_DATA` duplicates name+OVR pairs that already exist in
  `PLAYERS`. I verified they're currently 100% consistent (0 mismatches — nice), and
  that all 1,200 names are unique (so the name-keyed Maps — `_warCache`, `sim.fm`,
  `draftUI.slotPick`, `taken` in `pickCritique` — are safe today). But any manual
  data edit can silently drift. Either derive `TEAM_DATA` from `PLAYERS` at build
  time or add a cheap load-time assertion.

- **Caching is scattered** (`_wTable`, `_wpoCache`, `_replStatic`, `_warCache`,
  `planCache`, `_decompCache`, `draftUI.sim`, `S._emKey`, `_ratingsReady`,
  `_guideHtml`…). Each has hand-rolled invalidation. A tiny `memo(key, fn)` helper
  would make stale-cache bugs visible.

- **Inline styles everywhere** (~100 `style="…"` in generated HTML). This is what
  forces the brittle mobile overrides `[style*="grid-template-columns"]{…!important}`
  (`:309`) and the 7-ID selector at `:249`. Replacing the repeated
  `style="grid-template-columns:1fr 1fr"` with a `.grid-2` class (and a `.primary-btn`)
  would let you delete both hacks and shrink the CSS.

### Performance

- **The draft table rebuilds ~1,200 rows × 10 cells via `innerHTML` on every
  keystroke** (`draftSearch2` input → `renderDraftBoard2`) and on every pick, after
  which the mstack MutationObserver re-processes it. On desktop that's fine; on a
  phone it will feel heavy. Debounce the input ~150ms, and consider rendering the top
  ~200 rows with a "show more" (users can't scan 1,200 rows anyway).

- **Two document-wide MutationObservers** (the blue "your team" highlighter at 120ms
  and the mobile table stacker at 150ms) wake on every DOM change, and season views
  re-render wholesale per week. Scope both observers to the containers that actually
  change, and mark machine-generated regions with `data-nohighlight` so the
  highlighter skips big table rebuilds.

- The 100-season sim is properly chunked (120ms time slices) — no change needed
  there. `simRecs`' 12 Monte-Carlo replays per user turn is well judged.

### Product / UX

- **No persistence is the biggest product risk.** One accidental refresh destroys a
  26-round draft plus a 17-game season with awards and recaps. `draftSim` + `seasonState`
  are plain JSON-able data — snapshot them to `localStorage` (or IndexedDB if the
  summaries push past ~5MB) after each pick/week, and offer "Resume draft/season" on
  load.

- **Slow-draft pacing:** 832 picks × 750ms ≈ 10 minutes of wall time at the default
  speed. Instant/Sim-to-End exist, but consider a "fast (0.25s)" option or making
  Instant the default for CPU runs between user picks.

- **Accessibility:** clickable `tr.teamrow`/`tr.sgrow` rows and sortable `th` have no
  keyboard equivalent (no tabindex/role/button); `confirmDialog` has no focus trap and
  doesn't close on Escape; `th` cells lack `scope`. The toggle switches, by contrast,
  are properly done.

- `html{font-size:21px}` with a hard cut to 16px under 760px is a big jump at the
  breakpoint; `clamp()` would smooth it.

### Data & Content Notes

- Dataset integrity is clean: 32 teams, 1,200 players, no duplicate names,
  `TEAM_DATA` fully consistent, and the 58 empty starter slots (e.g., most teams'
  SAM) are handled gracefully as 70-OVR placeholders by design.

- The roster is a **projected/fictional 2026 world** (Aaron Donald active on the
  Rams at 95, Boye Mafe a Bengal, an invented 2026 coaching carousel), while the meta
  description says ratings are "real Madden ratings… set after the 2025 season" and
  the realism section asserts the model was validated against real 2025 results. If
  the fiction is intentional, soften the marketing copy so it doesn't read as a
  factual claim that can be falsified in ten seconds.

- The quoted NFL records in the realism audit (5,477 / 2,105 / 1,964 / 22.5) are
  correct.

### Smaller Polish

- Missing `og:image`, Twitter card, and favicon; the `keywords` meta is dead weight.
- `🏃🏿` is the only emoji with a skin-tone modifier (next to tone-free
  `🛡️`/`🚫`) — pick a neutral variant.
- `buildFullSchedule` throws a raw `Error` after 3,000 failed attempts with nothing
  user-visible; catch it and show a "try again" toast.
- The strengths/weaknesses threshold comments, plan-search design (decisions scored
  against _scouted_ expectations, not the opponent's actual choice), and record caps
  are all well documented in comments — genuinely good practice worth preserving
  through any refactor.

### Suggested Order of Attack

1. Fix `rWeights` (crash), the double-document head (+ `lang="en"`), and the 75-vs-70 copy bug.
2. Add persistence (localStorage snapshot per pick/week).
3. Wrap in an IIFE + run ESLint `no-undef`; delete the dead code.
4. Debounce/virtualize the draft board; scope the observers.
5. Longer term: modules + a build step, and derive `TEAM_DATA` from `PLAYERS`.

## Additional Architectural Recommendations (from Same Review)

1. **Centralize State with a Proxy-Based Store**
   - Replace scattered global objects (`draftSim`, `seasonState`, `weights`, `synergy`)
   - with a Proxy-based store that automatically triggers targeted UI re-renders
   - or local storage persistence on state changes.

2. **Offload Heavy Computation to Web Workers**
   - Move Hungarian assignment, Monte Carlo draft projections, and season schedule
     generation into a dedicated `draftWorker.js`.
   - Communication via `postMessage()` keeps the UI fluid during animations or
     user scrolling.

3. **Modularize Data and View Layers**
   - Externalize `PLAYERS` and `TEAM_DATA` into separate `.json` files loaded
     via `fetch()` on startup.
   - Split the script into logical modules: `ratings.js`, `draftEngine.js`,
     `seasonSim.js`, `ui-renderer.js`.
   - Keep a single-file build output if portability matters.

4. **Enhance Error Handling and User Feedback**
   - Add `try-catch` blocks around complex initialization routines and schedule
     generators with fallback UI states rather than failing silently.
