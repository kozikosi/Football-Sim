REVIEW-OF: 20261026-2354-uk-P-152-work.md
VERDICT: rejected

The visual intent needs a new, source-anchored implementation sketch before it can be integrated. I checked the proposal against the pinned `Football-Sim-PreColors.html`; no changes were made to the product.

- **Defect (shown):** the proposed helper does not parse as written: `renderPlayerCard(r, g, mx, sim, roster, draftUI)` declares `mx` as a parameter and then redeclares `const mx` in the same function scope. It also reads `entries` inside that helper without receiving or defining it.
- **Defect (shown):** the second proposed card snippet refers to `team`, `ovr`, `name`, `gp`, and `grey` without defining them in the shown `renderDraftBoard2()` loop. The generated card markup opens `.pcard` and `.pcard-body` but closes only one `div`, leaving the outer card unclosed.
- **Defect (shown):** the requested 85+ three-color dots are not implemented. The helper emits one OVR-number bubble; the alternate markup also emits one bubble. The drawing labels three circles as OVR values, not the team's three brand colors, and neither version centers the logo over three dots below the OVR.
- **Defect (shown):** `getTeamColor()` and `getTeamLogo()` have no definitions in Pre-Colors (`grep -n -E 'function getTeamColor|function getTeamLogo|function zpbTeamLogo' Football-Sim-PreColors.html` returned no matches). These are dependencies on the not-yet-built team-theme work, not helpers available for a standalone proposal.
- **Defect (shown):** the board rows do not carry the pick-history fields used by the proposal. `boardEntries()`/`mkEntry()` returns `{p,w,slot,g,flex,pen,v,later,pri,gone,score}`. `round`, `pickInRound`, and `overall` are recorded in `draftSim.log` by `executePick()` only after a selection; an available player row cannot truthfully display `R1.31` from `r.round`/`r.pickInRound`.
- **Defect (shown):** the sort-arrow removal rule targets `.th.sortable::after`, while the product uses `th.sortable`. The source search found the clickable header listeners and hover styling, but no existing sort-arrow pseudo-element to remove.
- **Risk:** the card's solid/gradient team colors and repeated `#FFFFFF` text do not show a legibility strategy and conflict with the task's “no white text” constraint. The raw color arrays shown in the proposal are not tied to an in-scope authoritative dataset; do not make those hard-coded values the source of UI colors.
- **Not run:** requested 1280px screenshots for the Ravens, Dolphins, and Saints; no screenshots or runnable mock-up are included. I also did not run the product linter because this proposal has not supplied an applicable patch to lint.
- **Weakest point:** the proposed render code is not connected to the actual draft-board data model, so several of the most visible elements (team colors, logo, pick label) are either undefined or unavailable for these rows.

**Colors v1 implication:** keep the distinction between immutable team identity (three sourced brand colors and logo) and readable interface tokens. A future shared theme should expose derived text, surface, accent, border, and focus colors for light/dark modes; draft-player identity can then use its real team while the app chrome uses the selected franchise, in line with the Owner's requests. The current Pre-Colors build contains no `getTeamColor()`/`getTeamLogo()` implementation, so this is a dependency and architectural recommendation, not an accepted implementation.
