## A1 — Should v1 ship with full account deletion?

The data model has user-owned `saves`, `save_history`, `runs`, and `shares`, while the Better Auth user/session/account rows are a separate ownership boundary. A slot-delete route is not account deletion. A manual contact is a weaker and less verifiable promise, especially for a free, owner-operated service that may not have a staffed support process. This is a product-trust baseline, not a feature-polish item.

A dated commitment alone would not: it changes the schedule, not the user need. If A is selected, the route must have an integration test proving that all user-owned data is gone, another user's data remains untouched, and repeated deletion is safe. The GitHub grant/revocation question (A3) and the deletion semantics (A2) must be resolved before implementation is considered complete.

## B1 — How far should the CSRF fix go?

1. **How I would decide:** **C — move the existing Origin guard above the `/api/auth/*` dispatch**, retaining the current exemption for GET and HEAD. The existing guard already rejects non-GET/HEAD requests whose Origin does not exactly match `BASE_URL`; it is simply placed after the auth early return.
2. **Why:** I inspected `server/src/worker.ts` on `architect/engine-and-seats` (source SHA to be recorded by the Architect at implementation): the auth branch returns before the Origin guard. Therefore the two state-changing auth POSTs are not protected by this Worker-level check. The proposed move does **not** break the OAuth callback described in the filing: the allowlisted GitHub/Google callbacks are GET requests, and GET remains exempt. The current code's comment says the guard applies to every state-changing request, but its control flow does not.
3. **What would change my mind:** A reproducible test showing that moving the guard blocks the legitimate OAuth callback, or a verified Better Auth flow requiring a cross-origin state-changing POST to this same endpoint, would change the placement/design. Better Auth's own CSRF/origin behavior should also be inspected, but it is not a reason to leave an obvious gap in our additional defense without evidence. Required tests: foreign-Origin `POST /api/auth/sign-in/social` → 403; foreign-Origin `POST /api/auth/sign-out` → 403; same-origin versions reach Better Auth; the GET OAuth callback remains reachable and the existing full sign-in round trip stays green.
4. **Who owns the call:** **Architect** owns this ordinary technical/security decision and its test. MUSE should update wording only after the behavior is verified.
5. **What is blocked meanwhile:** Treat the current Worker-level CSRF claim as incomplete. Do not describe the Origin guard as covering all state-changing `/api/*` requests, and do not treat the auth spike as security-rehearsal complete until the two POST cases and callback regression are tested.

## D2 — Should `kind:'save'` shares expose a whole envelope?

1. **How I would decide:** **Restrict v1 shares to `kind:'run'` only. Do not create `kind:'save'` shares.** A public brag link should expose a compact completed-run result, not a resumable or replayable save envelope.
2. **Why:** The filing quotes the Owner's 1 Nov direction as: “no to the hidden full save”, “it's a brag share”, “No downloads”, and that the challenge should not carry a save or be a seed challenge. The current `postShare()` implementation in `server/src/api.ts` does exactly the risky thing: for `kind:'save'`, it copies `row.envelope` into the public snapshot. The `run` branch already constructs a compact result object from the ledger, without exposing the envelope or seed. That is the closer match to the Owner's described product.
3. **What would change my mind:** A new, explicit Owner ruling that a public share is intended to expose the complete save envelope, including its seed and replayable state, would change my recommendation. A desire for a challenge link or richer brag card would not; those can be represented as a narrow, purpose-built snapshot without exposing the full save. Before release, tests should prove that save-share creation is rejected, run-share output contains only the approved result fields, and no seed, save envelope, user id, or email appears in the public response. If any save-share rows already exist in a deployed database, the Owner must decide their revocation/migration; do not silently leave their public exposure in place.
4. **Who owns the call:** **Owner** owns the meaning of “no hidden full save” and the public-share product boundary. Architect owns the route/schema change and tests. My reading is that the existing `kind:'save'` path conflicts with the quoted Owner direction; the Owner should confirm or correct that reading.
5. **What is blocked meanwhile:** Do not expose `kind:'save'` shares in a rehearsal that uses real or publicly reachable data, and do not call the public-share feature release-ready until the Owner's intent is recorded and the endpoint is constrained accordingly.
