## What I did

P-331 asked for two `next` gaps (found while working the queue as a council member, 2026-11-10): (1) `next` prints the P-item ID and the file to read, but NOT the brief — the reviewer has to grep the 132 KB PRIORITIES.md; (2) `next` surfaces old P0 reviews before current P1 work — the council prompt's highlights are the real priority, but the tool does not reflect them. I implemented both, and found two further bugs while testing. This is council.mjs v10.

### Change 1 — REVIEW items and fallback rows print the brief

- REVIEW entries in `next` now print `BRIEF: <first 200 chars of the P-item brief>  [full brief: node tools/council.mjs show <ID>]`. WORK entries already printed the full brief; REVIEW entries printed only the file to read. (The brief is truncated to 200 chars because some briefs run to ~2000 chars; `show <ID>` prints it in full.)
- The `next` fallback (top open PRIORITIES rows, printed when the derived list is empty) now prints the brief too (truncated to 120 chars).

### Change 2 — current-prompt highlights are boosted above old P0 reviews

- `loadState` now reads the latest council-prompt file (`_agents/muse/deliveries/**/council-prompt-*.md`, dated YYYY-MM-DD in the filename) from origin/council/muse and extracts the P-IDs in its **"Work to take" section** only. Those IDs are stored as `state.highlights`.
- `nextFor` sorts highlighted items first (before tier), marked `★` in the output. ASK entries (the Architect's questions) keep highlight 0 so they stay at the top.
- Only the "Work to take" section counts. My first implementation extracted P-IDs from the whole prompt, which boosted old P0 reviews named in the "Recent council work" section (P-116, P-167, P-193) — the opposite of the intent. Fixed to the Work section only.

### Change 3 (found while testing) — `readFrom` read the Architect's stale PRIORITIES.md, not the live queue

`readFrom` read PRIORITIES.md from the Architect's branch first, then council/base — never from origin/council/muse, even though the live queue is on council/muse (MUSE is custodian, Owner 2026-11-09). A council seat running `next`/`board` therefore read the Architect's (stale) PRIORITIES.md: newly filed items (P-330, P-331) never appeared, and the board showed 164 live / 6 retired instead of the live queue. Fixed: `readFrom` now tries `origin/council/muse` first, then the Architect's branch, then council/base, then the local file. Files council/muse lacks (BUILD.txt, STALE-EPOCH.txt) fall through to the Architect's branch as before. After the fix the board shows **176 live / 3 retired** and P-328/P-329/P-330/P-331 appear (BLOCKED, but visible).

### Change 4 (found while testing) — newly added P2/P3 rows were instantly auto-retired STALE

`derive` auto-retires P2/P3 items with no activity for ≥21 days. `touched` for a table row with no files/ops is `max(epoch, added || 0)`. When the epoch is 0 (STALE-EPOCH.txt missing/empty — it does not exist on council/muse), `touched` is 0 and the age is ~20,000 days, so a P2/P3 row filed today was retired STALE on the next `board`/`next` run. P-330 and P-331 were both retired this way the day they were filed. Fixed: the STALE auto-retire (and the warn window) now requires `touched > 0` — a stale item needs evidence of inactivity, not the absence of a timestamp. (With the real epoch, 2026-11-02 from the Architect's STALE-EPOCH.txt, P-330/P-331 have age 8 days and are live either way; the fix covers the epoch-missing case.)
