# Part 6 — two short answers, deliberately light

**N for paired comparisons — 12,000 stays the iteration default; 120,000 becomes the headline bar.** The 12k-vs-120k lesson cut both ways and it should be written down as a rule, not an anecdote: at 12,000 keys the sacks shift read −1.72% (z −3.0); at 120,000 it read −1.07% — the direction, the sign, the ranking, and every *verdict-relevant* claim survived (the 4th-down artifact reproduced to within 0.2 pp of the 12k figures at 10× keys; the downs counts matched event-for-event; the counterfactual moved 7.069→7.065-ish). So 12k is good for iteration and shape, and at least one seat should run 120k before any *number enters a build gate or a default decision* — call it "every number quoted in the report comes from ≥120,000 keys, or says it doesn't". The converse rule matters just as much: do not let 120k become a ritual where seats re-run the suite to "confirm" it — Beam and Ernie and I each confirmed the same artifact at 12k and only one seat ran 120k, and that sufficed. Standard: 12k for exploration and early filings; 120k (or a stated reason otherwise) for any figure the Architect or the Owner will act on.

**The tools door — same door, stricter check, no second registry.** The council now produces measurement tools (bucket-bar, the merge-gate candidate, pin-watch) and the failure modes are instructive: two of the three conform as-filed from a clean tip on Node 24 and 26 (ernie's, glyph's — I ran both), one is broken-as-filed (beam's — drops the score-state axis entirely, carries dead placeholder code, and his own note concedes it; a reviewer running it five minutes re-discovers the failure). That spread is exactly what the filing rule already handles: a tool is a proposal with an executable HOW TO CHECK, and the review that matters is not "did the author run it" but "does the reviewer run it from a clean extract at both node majors with the falsifier on". So no new door is needed — but the filing rules should get one line: **a tools/ proposal must be runnable from a `git archive` extract with zero repo-state beyond the committed packs, or it is not filed yet** (Beam's proposal declared nothing about the score axis and a five-minute review run shows the question the whole round is about, minus the axis it needs). Tools land through the Architect like everything else (FILE the tool, don't edit the engine), get one verifier like any other build change, and the council's tools directory stays `colors/tools/` (tracked, reviewable, versioned) — never a lane file, never inline-only. Knowledge it buys: the pin-watch idea gets a fair yes/no on its merits, the bucket-bar is on its way to a versioned home, and the next broken-as-filed tool gets caught by the review, not by luck.
