## Draft ADR set

These are proposals, not accepted architecture decisions. The four choices expressly reserved for the Owner remain **OPEN**. Section 13 labels its consensus and technical claims REPORTED / unchecked by the Architect; this document does not upgrade them to VERIFIED.

### ADR-01 — Framework-independent engine and seeded randomness

**Status:** PROPOSED

**Decision:** Keep football logic in a framework-independent TypeScript module. Pass configuration and an injected seeded RNG explicitly; do not call `Math.random()` inside the engine. Validate external data with Zod at data-load boundaries. Return simulation results as data.

**Rejected:** Framework-coupled game logic and ambient randomness. They make it harder to run identical logic in a browser worker and tests, and prevent reliable replay of a reported result.

**Why:** The engine can be exercised independently, seeded runs can be compared against golden fixtures, and the same football logic can run in a Web Worker or Vitest. Before changing the model, compare seeded output against the archived legacy HTML reference.

**Revisit when:** A demonstrated engine requirement cannot be met with this boundary. Any change to randomness must retain repeatable seeded runs and update golden fixtures with an explained model change.

### ADR-02 — Simulation compute location

**Status:** PROPOSED

**Decision:** Run simulations in browser Web Workers; keep rendering and user interaction on the main thread. Do not send game simulation to a server in v1.

**Rejected:** Server-side simulation, a hosted queue, WebSockets, and Durable Objects as initial requirements. Section 13 gives no measured workload requiring them; the engine boundary keeps a later server runner possible without coupling football logic to it.

**Why:** A worker isolates CPU work from the UI while leaving the simulation under the user's control. Use progress reporting, cancellation, and transfer-efficient messages only as justified by a measured prototype.

**Revisit when:** A recorded benchmark shows the browser worker cannot meet performance or memory targets that the Owner has approved. No numeric target is supplied here; agree one before benchmarking.

**Free-tier note:** The cited Cloudflare Workers CPU limit of 10 ms is **UNKNOWN** for this decision: §13 gives no dated source. Do not rely on it as verified evidence.

### ADR-03 — Application framework

**Status:** **OPEN — OWNER DECISION**

**Decision:** None. Choose between SvelteKit and Next.js only after the Owner selects the intended target audience and priorities.

**Options:** SvelteKit was favored by the friend and Grok; Next.js or a role-dependent choice was favored by GPT, Z.ai, DeepSeek, and Grok's comparison. Keep the engine independent of either framework.

**Why open:** Section 13 explicitly reserves this choice for the Owner and says the engine boundary makes either option reversible. Do not treat the number of job listings or an agent majority as approval.

**Revisit when:** The Owner states the target roles, audience, or hosting constraint that should decide the tradeoff.

### ADR-04 — Linter and formatter

**Status:** **OPEN — OWNER DECISION**

**Decision:** None. The Owner chooses Biome or ESLint + Prettier.

**Options:** The friend preferred ESLint + Prettier; GPT, DeepSeek, and Grok preferred keeping Biome unless a concrete need appears. Neither option is rejected by this proposal.

**Why open:** Section 13 marks the linter as an Owner decision. Do not change the existing toolchain as a side effect of this draft.

**Revisit when:** The Owner selects one option, or a demonstrated rule, plugin, or compatibility gap requires bringing the choice back.

### ADR-05 — Database in v1

**Status:** **OPEN — OWNER DECISION**

**Decision:** None. The Owner decides whether v1 has a database.

**Options:** A full-stack database from the start, or no database until a user-facing feature requires persistence; if a database is later needed, D1 + Drizzle is the option recorded in §13. No database provider or schema is selected here.

**Why open:** The proposals disagree, and §13 explicitly reserves the choice for the Owner. The reported Supabase idle-pause claim is not verified here and is not used as evidence.

**Revisit when:** A specified v1 feature requires durable account, cross-device, or shared data. Until that requirement exists, avoid treating a database as an implementation prerequisite.

### ADR-06 — Authentication in v1

**Status:** **OPEN — OWNER DECISION**

**Decision:** None. The Owner decides whether v1 has authentication.

**Options:** No auth in v1, then consider GitHub OAuth, Better Auth, or Auth.js if a feature requires identity; the friend also proposed Auth.js with email/password. No authentication flow is selected or authorized by this draft.

**Why open:** Section 13 explicitly reserves the choice. Never implement hand-rolled password hashing; if identity is later approved, compare maintained libraries and supported providers.

**Revisit when:** An approved feature needs user identity or account-owned persistence.

### ADR-07 — Free-tier and demo-path guardrails

**Status:** PROPOSED

**Decision:** Apply the four guardrails recorded in §13: do not require a payment card for the demo path; do not let an idle free tier make the demo sleep; fail closed at quotas rather than silently incurring charges or returning fabricated success; assume any free tier can be revoked.

**Rejected:** Treating free-tier availability or quotas as a permanent product guarantee, or making the demo depend on a service that can sleep when idle.

**Why:** These are operational constraints, not evidence that a specific provider or plan is available. Keep the demo path understandable and surface quota/service failure explicitly.

**Revisit when:** A provider changes its plan, quota, sleep policy, or availability, or a feature requires paid capacity. Re-check the service terms and document the dated source before relying on any numeric limit.
