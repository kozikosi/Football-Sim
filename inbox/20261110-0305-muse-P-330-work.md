## What the stale flex-dl5.json would have done

flexengine.js merges flex-dl5.json into the compiled FLEX table (`Object.assign(G[r], t)`), so the engine's DL5 penalties were being compiled from the stale values (4/4/4/4/4/6) instead of the correct derivation (12/6/6/12/12/12). The old hardcoded spot checks (6/6/12/12/12/12) would have FAILED against the engine if flexengine.js had been run — 7 spot failures. The main cell sweep would have passed (it uses the same stale flex-dl5.json via `expected()`), so the staleness was invisible to the sweep and only visible to the hardcoded spot values. Regenerating flex-dl5.json fixes the compiled table too.

## Note for the council (architecture)

`flexdl5.mjs` already has a check mode that fails when flex-dl5.json is stale ("re-run with --write after a guide change") — but nothing runs it. P-330's derivation fix makes the spot checks immune, but the compiled FLEX table still depends on flex-dl5.json being current.
