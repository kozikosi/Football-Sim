## B1 · The CSRF gap — I would decide **C, done as a hoist** (and the test is the real deliverable)

**The bytes (V).** `server/src/worker.ts` is 20 lines at `5d10336`. The auth branch returns at line 13-15; the origin check is line 17:

```ts
13:    if (url.pathname.startsWith('/api/auth/') || url.pathname === '/api/auth') {
14:      return authPathAllowed(req.method, url.pathname) ? auth.handler(req) : json(404, { error: 'not-found', message: 'unknown route' });
15:    }
16:    // CSRF defence in depth on top of SameSite=Lax: every state-changing request must come from our own origin.
17:    if (req.method !== 'GET' && req.method !== 'HEAD' && req.headers.get('origin') !== new URL(env.BASE_URL).origin) return json(403, { error: 'bad-origin', message: 'cross-origin request refused' });
```

`AUTH_ALLOW` (`server/src/auth.ts`) contains exactly two state-changing routes: `POST /api/auth/sign-in/social` and `POST /api/auth/sign-out`. Both reach `auth.handler` before line 17. The comment on line 16 therefore describes a property the code does not have for those two routes — **V**.

**Why I would pick C and not A.** The ask says C is ruled out "because it breaks the callback". That is not what the code does: the guard on line 17 already excludes `GET` and `HEAD`, and the callback is `GET /api/auth/callback/(github|google)`. **Hoisting line 17 above line 13 cannot touch the callback** — the method guard is the same guard, just earlier. So C is available, and it is strictly better than A: one check instead of two, and no second place for the origin rule to drift.

Smallest form (proposal, not an edit):

- WHERE: `server/src/worker.ts:11-17`.
- old: the auth branch at 13-15, then the origin check at 17.
- new: the origin check first (after `const url`), then the auth branch, then `handle(...)`.
- WHY: every state-changing request is refused before any handler, including `auth.handler`; the GET callback is untouched.
- SAFE ALONE? Yes. Two observable differences, both acceptable: (a) a foreign-origin POST to an **unknown** auth route now gets `403` instead of `404` (the allowlist no longer runs first — the route list is not a secret; if you want 404 preserved for unknown paths, keep the allowlist above the check and accept that the two known POSTs are then checked by A's narrow block); (b) `makeAuth(env)` need not be constructed for a rejected request if the check goes above it.
- HOW TO CHECK: the e2e case below, plus the existing suite unchanged.

**The test gap is the part I would not defer (V).** `server/test/e2e.test.ts:81-83` is the only foreign-origin assertion in the file, and it targets `/api/saves/nfl/A`:

```ts
81:  for (const origin of ['https://evil.example', null])
82:    assert.equal((await send('/api/saves/nfl/A', { method: 'PUT', ... origin ... })).status, 403);
```

There is **no** foreign-origin case on the two allowlisted auth POSTs — I grepped every `server/test/*` file for `origin` and the only hits are the e2e helper (`:13,:22,:38-43`) and that loop. So the property is asserted for one route and assumed for the other two.

**What I would decide:** hoist the check (C), and add one loop:

```ts
for (const path of ['/api/auth/sign-out', '/api/auth/sign-in/social'])
  for (const origin of ['https://evil.example', null])
    assert.equal((await send(path, { method: 'POST', origin, body: '{}' })).status, 403);
```

**Why.** The council's own standard is that a security property is a property when a test fails without the fix. Today no test fails if the auth branch moves the check away again — which is how the comment and the code came apart in the first place.

**What would change my mind.** (a) If a foreign-origin `POST /api/auth/sign-out` returns **403 before any change**, then Better Auth's own origin check covers it and B is right — I did **not** read the library (`better-auth ^1.7.27`, `authOptions` sets no `trustedOrigins`; **U** whether the default rejects). That is a ten-minute read and it should come before the code change, because if the library covers it the change is optional and the *test* is the whole deliverable. (b) If `sign-in/social` is ever called cross-origin by design (it is not today — the client posts from our page, **I**), hoisting would break it.

**Who owns it.** Architect — ordinary technical decision. **Blocked meanwhile:** nothing. Do not block the spike on it, but do not call the spike CSRF-complete while the two state-changing auth routes are unchecked and untested.
