REVIEW-OF: 20261025-1060-beam-P-153-work.md
VERDICT: rejected

The inventory is useful, but the stated Priority root cause is not present in the pinned `Football-Sim-PreColors.html`, and several “already works”/exact-change claims do not match this build.

- **Defect (shown):** the Priority diagnosis is false. I ran `grep -n -E 'function prioOf|const prioOf|PRIO_MULT|function mkEntry|score:|function newDraftUI|WV_GROUPS|DEPTH_CHART_GROUPS|draftTable2|draftBody2|draftingAsBanner|zpb-teamcol|data-ztf|data-filter' Football-Sim-PreColors.html`. `prioOf(g)` reads `draftUI.prio[g]` and defaults to `1`; the draft-chip click handler cycles values `1 → 2 → 0 → 1`; `mkEntry()` applies `PRIO_MULT[prioOf(e.g)]` to `score`. The stars and multiplier are live, not removed/dead, so removing them would break the existing preference control.
- **Calibration question:** there is a real display/sort distinction worth resolving before calling Priority broken. The table cell displays raw `r.pri`, while `keyOf()` sorts the “priority” column by weighted `r.score`; a user's star choice can therefore change sort order without changing the displayed number. The tooltip defines Priority as value minus what remains available, which is `r.pri`; decide whether that column should remain raw and the sort should use raw, or whether the weighted score should be visible under a different label. I did not run a seeded draft or establish the original reported symptom.
- **Defect (shown):** the claimed team-logo filter does not exist in Pre-Colors. The proposal's anchor `zpb-teamcol`/`data-ztf` is from the separate Z-post-blue artifact, not this pinned build; searching Pre-Colors for those selectors/attributes found no matches. The current row contains a team abbreviation, and the click handler on `draftBody2` handles only pick buttons and slot changes.
- **Defect (shown):** position sorting is not the stated roster order. `keyOf()` sorts position by `POS_DISPLAY[r.p[1]] || r.p[1]` (text ordering), while `WV_GROUPS` is `QB, EDGE, OT, CB, WR, DT, OG, C, LB, SS, FS, TE, RB, K`. The sequence written in the proposal (`QB, RB, WR, TE, OL, DL, LB, DB`) is not a constant in this build. Use an explicit order derived from `DEPTH_CHART_GROUPS`/`ROSTER_SLOTS` if this requirement is pursued.
- **Defect (shown):** the exact seven sort words are not implemented. Current HTML has eight sort choices including `value="value"` / “Sort: value here”; P-005 separately requires “Value here” removed from every visual, including sort. The proposal asks to retain seven keys but does not remove that eighth choice or provide replacement markup.
- **Defect (shown):** the view control is still a native select with “One table” and “Position cards”; the proposal says it needs no change, although the request is a visible “Table / Cards” toggle with both options clickable. A select does not provide both visible toggle buttons.
- **Defect (shown):** the proposed sort-arrow fix targets `.th.sortable::after`; the actual headers are `th.sortable`, and the source has no arrow pseudo-element to remove. The grep found sortable headers/listeners and hover styling only.
- **Risk:** changing `#draftTable2` overflow on mobile alone does not establish “no horizontal scrollbar on desktop”: `.tablewrap` has `overflow:auto` at all sizes. No computed 390px/desktop widths or browser evidence accompany the proposal.
- **Defect (shown):** the search alignment and all/none graphic have no exact layout/markup change. The existing `.filters` is wrapping flex; the proposal's `margin-left:auto` is not shown in a tested layout. The Undo button already reads “↶ Undo my last pick” and is dynamically shown only when undo is available; the proposed shorter label and Guide copy are not verified against a complete Guide change.
- **Scope overlap:** removing “Drafting as” is already a separate P-044 item. The P-153 submission does not provide an exact implementation for it.
- **Not run:** a seeded draft, product lint, screenshot, or viewport overflow test. The requested Priority reproduction is unresolved; no unseeded outcome is reported.
- **Weakest point:** the central diagnosis assumes the user-priority stars were removed, but they are present and active in the actual build; proposed deletion would remove functioning behavior rather than fix a demonstrated numerical bug.

**Colors v1 takeaway:** keep the derived raw value (`pri`, “value now minus expected value later”) separate from the user-weighted ranking score (`score`) in engine/view-model contracts. The current board intentionally uses weighted score for recommendations/order but prints raw priority; that can look broken unless the UI distinguishes the two. A typed selector such as `{ rawPriority, userWeightedScore }` would make the semantics explicit in a future UI without changing the protected win math. This is a source-backed architecture suggestion, not a proposed engine-value change.
