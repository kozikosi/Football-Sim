### 2. Tone-lift algorithm uses OKLCH, Z.ai uses HSL
uk proposes a `toneLift()` function using OKLCH color space. The actual Z.ai `zpbPackFor` uses HSL (`zpbHsl`, `zpbFromHsl`, `zpbReadable`). The Owner's COLORS-V1-DESIGN.md says "the algorithm is a port of w33's zpbPackFor". So the reference algorithm is HSL-based, not OKLCH. The results would differ. Recommend: port the actual HSL-based `zpbPackFor` rather than inventing an OKLCH variant.

### 3. `zpbPackFor` is much more complex than uk's simplified version
uk's `toneLift()` is ~15 lines. Z.ai's `zpbPackFor` is ~60 lines and generates 40+ CSS variables per team (accL, accD, acc2L, acc2D, txL, txd, hairL, hairD, bgL, bgD, g1-g6, b1-b6, o1-o4, d1-d2, and their dark variants). uk's simplified version doesn't capture the full palette generation. The Architect needs the full `zpbPackFor` port, not a simplified tone-lift.

### 5. `--team-primary` CSS variable doesn't exist in Pre-Colors
uk's CSS uses `--team-primary`, `--team-secondary`, `--team-accent`, `--team-primary-text`, etc. These don't exist in Pre-Colors (0 occurrences). The Architect would need to define them. This is fine for a proposal, but should be noted as a dependency.

### 6. Dark logo filter — reasonable but untested
The CSS `filter: brightness(1.4) contrast(1.1)` approach is pragmatic and zero-asset. But:
- `brightness(1.4)` on a dark logo (e.g., Patriots navy) might wash out details.
- The filter applies to ALL dark logos, but some (like Raiders black) might need different treatment.
- No `prefers-reduced-motion` concern (filters aren't motion). Good.
- The per-team overrides are specific and reasonable.

### 9. PICK ORDER/DEPTH CHART readability — CSS is reasonable
The `.pick-order-label`, `.depth-chart-label`, `.slot-label` CSS uses `var(--team-primary)` with a text-shadow halo. This is a reasonable approach. But the "text-shadow: 0 0 2px var(--card)" halo might look odd on some backgrounds. Recommend testing.

### 10. The `onPrimary` text color logic has a bug
uk's `getTeamPalette()` uses `base.primary.L > 0.5 ? '#000000' : '#FFFFFF'` to determine text color. But `base.primary.L` is a 0-100 value (from the table: L* = CIE Lightness 0-100), not 0-1. So `> 0.5` would always be true (since all L* values are > 0.5). The comparison should be `> 50`. This is a code bug in the proposal.

### 11. The table's "Contrast on White" values — some are questionable
- KC: 4.5:1 for #E31837 on white. Let me verify: E31837 is dark red. WCAG contrast for #E31837 on #FFFFFF... The luminance of #E31837 is ~0.13, white is 1.0. Contrast = (1.0+0.05)/(0.13+0.05) = 1.05/0.18 = 5.8:1. uk says 4.5:1. Slight discrepancy.
- SF: 5.2:1 for #AA0000 on white. Luminance of #AA0000 ~0.11. Contrast = 1.05/0.16 = 6.6:1. uk says 5.2:1. Discrepancy.
These are approximate but should be verified with a proper tool.
