# Findings

1. **No actual table provided.** The work item claims "One proposed table: Owner's weights plus the agreed K .45, WR2 .63, …" but delivers only a framework and says Owner input is required for the full 33-slot table. The arithmetic checks (col2 = 20×col1, sums, quantisation) cannot be verified against a table that does not exist. As submitted, this is a process document, not a reviewable proposal. Recommend: either the Architect runs `slotWinsPerOvr()` to produce the data-driven column 1 and attaches the full 33-row table, or the Owner supplies the manual table. Until then, P-013 is not reviewable for arithmetic and should be marked "needs Owner input" rather than "needs review".

2. **The "20×" rescaling is not a code path.** `modelWeights()` (l.459) scales `slotWinsPerOvr()` so that the max becomes 700 directly (mx = max, out = w/mx*700 rounded to nearest 5, floor 5). There is no "col1 → ×20 → ÷max×700" step in code. The proposed three-column workflow (Owner's weights, 20×, quantised) is a manual authoring aid, not the implementation. That is fine as documentation, but the work item should state explicitly that the implementation is either (a) `DEFAULT_WEIGHTS` set equal to `modelWeights()` output (data-driven), or (b) `DEFAULT_WEIGHTS` set to the Owner's manual values with no quantisation. Mixing the two (manual values then quantised) would create a second, divergent default. Clarify which.

3. **Protected-constant scope check.** `DEFAULT_WEIGHTS` is protected (AGENTS.md §3). `modelWeights()`/`slotWinsPerOvr()` are the monotone-quantisation contract (700 scale, nearest 5, floor 5, error ≤2.5 per slot, no rank inversions beyond rounding ties). Recalibrating `DEFAULT_WEIGHTS` does NOT touch that contract as long as `DEFAULT_WEIGHTS` remains the fallback/personal default (which it is: line 6410 sets `personalWeights = {...DEFAULT_WEIGHTS}` and `weights = modelWeights()`). So changing `DEFAULT_WEIGHTS` changes the "My Weights" fallback only. If the intent is instead to change the *model* default, that requires changing `modelWeights()`/`slotWinsPerOvr()` inputs, which is a different (and heavier) change requiring re-pin of the hash. The work item should state which.

4. **Quantisation floor.** The proposed "floor 5" matches `Math.max(5, …)`. Good. But note the work item says "TE1 within 0.5 of WR1" and "TE2 within 0.5 of WR3" — these are constraints on the *wins* (col1) or on the *quantised* values? If on quantised (nearest 5 on 700 scale), "within 0.5" is impossible (granularity 5). Must be "within 5" on the 700 scale, or "within 0.5" on col1. Clarify. Similarly "QB/WR run shares" is unspecified.

5. **Agreed adjustments are Owner-supplied values (AGENTS.md §7).** K .45, WR2 .63, RB1 .58, CB2 .95, DE1 1.38 are Owner-supplied (fine, cite the Owner's 21 Oct message). But the work item should quote the source message and confirm these are the *wins* values (col1) not the 700-scale weights. Ambiguous as written.

6. **Monotone-quantisation verification.** If `DEFAULT_WEIGHTS` is set to `modelWeights()` output, the contract (error ≤2.5 per slot, no rank inversions beyond rounding ties) holds by construction. If set to manual values, the contract does not apply to `DEFAULT_WEIGHTS` (it applies to `modelWeights()`). The work item should not test `DEFAULT_WEIGHTS` against the monotone contract unless it is meant to equal `modelWeights()`. Recommend: keep `DEFAULT_WEIGHTS` as the Owner's fallback and do not subject it to the monotone test; test `modelWeights()` separately (already covered by existing tooling).

7. **Re-pin requirement.** Changing `DEFAULT_WEIGHTS` (protected) requires: Owner approval (quoted), re-pin of the protected-constant hash in `MERGE-MANIFEST.md` in the same commit, and a Verifier's gate result. The work item notes this. Good. But it should also note that `personalWeights` initial value (l.6410) changes too, affecting "My Weights" fallback — a behaviour change worth a before/after note.
