## 1 · Definition 1 — what "done" means for a slice

### 1.1 The sentence

> **A slice is done when it renders correctly at 390 px and from `file://` with zero blocked requests and zero console errors; its battery passes on the shipped tree with every SKIP and DEFER justified in writing; its engine is byte-identical to the pin; its manifest verifies from git, not from the author's working tree; and the Owner has used it and said it is right.**

**The last clause is not a formality.** "Done" for a product is a product state, not a technical one. A slice that passes every check and that the Owner will not use is not done.

### 1.2 Necessary vs nice

**Necessary — without it, not done:**

| Condition | Check |
|---|---|
| 390 px, no horizontal scroll | the 390 px probe on the heaviest view |
| `file://`, 0 blocked, 0 console errors | the boot probe — **in vanilla mode** |
| Battery passes, every SKIP/DEFER justified | the battery output + the reasons |
| Engine byte-identical to the pin | `diff -rq` against `git archive <pin>` |
| Manifest verifies **from git** | extract the archive, then `sha256sum -c` |
| Owner has used it | the Owner's word |
| Keyboard reachable, sane tab order | the tab-order probe |

**Nice, not necessary — real, but they do not gate:**

- Every turnover named · no banned phrasings — **content** rules, checkable by grep, gating a *view that shows a game*, not a slice.
- A screenshot matching a committed shot — **the seed mints per boot**, so this can never be a gate. Evidence, not a condition.

### 1.3 What my own list was missing

I listed eight candidates in the prompt. Three of them are not conditions at all, and two real ones are missing:

1. **"The battery passes" is not enough — the 10 loud SKIPs and 3 DEFERs must each carry a reason.** A slice with ten unexplained skips is not done; it is a slice with ten holes. Z.ai's harness prints reasons, which is right, but nothing requires them to be *read*.
2. **The two-check sweep** — files present **and** citations resolve. This has caught three of this wave's defects and belongs in the definition, not only in the packaging rules.
3. **No unexplained numeric change.** If the slice moves a number, the before/after belongs in the receipt. This is the condition most often skipped.

## 1.4 Who decides, and what happens when they disagree

**The Architect builds, a reviewer who wrote none of it verifies, the Owner accepts.**

- Architect vs reviewer: the reviewer's receipt wins on **facts**; the Architect wins on **design**.
- Owner vs either: **the Owner's use is the tiebreak**, because "done" is a product state and the Owner is the only seat who can say whether the product is usable.

### 1.5 The falsifiability test — what this un-calls

**Slice 3, as shipped, is not done by this definition.** It does not boot from `file://` in vanilla mode — the dist's `crossorigin` tags CORS-block it, and it only mounts with `--allow-file-access-from-files`. Z.ai filed that as a finding for the Architect; INKLING called it *"a vite-level finding, filed for the Architect, identical for both arms."*

**A finding nobody owns is not a closed finding.** Slice 3 is rev2-landed and described as done in three separate filings; by this definition it is **done except for offline**, and offline is a hard requirement.

**One command un-calls it.** That is the test working.

### 1.6 Does "done" differ between a slice (S1–S5) and a system (S6–S7)?

**Yes, and the difference is the receipt.** A slice is gated by its battery and its probe. A system (a season, a playoff bracket) is gated by **a full run to completion**: season to the Super Bowl, standings correct, no crash, no console error across the whole run. **A system cannot be "done" on a battery alone, because a battery exercises a slice and a season is a thousand of them.**

## 2 · Definition 2 — what makes a w89 view "improvable"

### 2.1 The sentence

> **A w89 view is improvable in a framework if that framework can do at least one of three things w89 cannot — preserve state across a transition w89 loses, express a transition w89 cannot (animate, interpolate, morph), or reach a 390 px fidelity w89 cannot — and the difference is visible to a user without being told.**

**The last clause is the whole definition.** If you have to explain the improvement, it is not a UX improvement; it is a feature list.

### 2.2 The three tests, each checkable

| Test | How to check it |
|---|---|
| **State survives a transition w89 loses** | set a filter on the board → navigate to lineup → return → is the filter still set? w89: no. |
| **A transition w89 cannot express** | does a row position *animate* when the board re-ranks, or snap? w89 rebuilds, so it snaps. |
| **390 px fidelity w89 cannot reach** | the heaviest view at 390 px — overflow, reflow, touch targets. |

**I am not counting "more beautiful" as a test**, because it is not checkable. Beauty is the *reason* the three tests matter, not a measurement.

### 2.3 The falsifiability test — where this fails

**The GUIDE is not improvable in either framework.** It is static reference text. Neither Vue nor Svelte makes a glossary more dynamic without inventing content the engine does not have, and inventing content is a data-integrity violation.

**So "improvable" must be reported as `no` for the Guide in both arms — and that is a result, not a failure of either framework.** A seat that reports "improvable: yes" for the Guide without naming a specific mechanism has failed this definition.

## 3 · The design review — I am attacking my own design

**I designed the cross-agent authoring measurement. I now think it is the weaker of the two available designs, and I am saying so before it runs.**

### 3.1 Cross-agent is the wrong primary design

**Agent skill variance is larger than framework variance.** Two models differ more than Vue and Svelte do. So a cross-agent comparison measures the *pair*, not the framework — and if the two agents disagree, the disagreement is attributed to the framework when it is probably the models.

**It also cannot be replicated.** A third agent building a third arm produces a third number, and none of the three generalises to "which framework is easier for an agent," because each is one agent.

### 3.2 The confound I did not name

**Training-data mix.** If I have seen more Vue than Svelte in training — or the reverse — my "easier" is a prior, not a measurement. **It is not separable from skill, and it is not separable from the framework.** It sits inside every number I would produce.

**That is the confound that breaks cross-agent**, and I did not name it in the prompt. A seat reading my design should have caught it.

### 3.3 What I would do instead

**Primary: within-agent, more slices, order randomised *per slice*.**

- Z.ai builds both arms across N slices.
- **The order is randomised per slice, not per sitting** — so if slice 1 is Svelte-first, slice 2 is Vue-first.
- That measures **the framework for Z.ai**, which is the actual question the Owner asked: *"is it easier for Z.ai and other agents to code in..."*

**Secondary: cross-agent, reported alongside, never averaged.**

- My arm is worth having — but as **"a second agent found X"**, not as a number in a mean.
- If we disagree, the disagreement is the finding.

**And one more thing the primary design needs:** **the same fixture and the same fidelity, pinned numerically.** "Same view, same chrome" is not enough — the fidelity has to be a number (the same DOM node count, the same rows, the same states), or the two arms are not comparable.

### 3.4 My answer to my own questions

| Question | Answer |
|---|---|
| Is cross-agent right? | **No — it is the weaker design. Within-agent with per-slice randomisation is stronger.** |
| The confound I did not name? | **Training-data mix.** |
| Minimum scope for comparability? | **Same view, same fixture, same fidelity as a number (DOM nodes, rows, states), same chrome bytes.** |
| If I were running it? | **I would drop cross-agent as the primary and keep it as a secondary check.** |

## 4 · The structural assertion for the two de-gated tests

**I recommend rewrite, not delete — and here is the structure. The Architect adapts the exact API names; the intent is what matters.**

### 4.1 `lineup.test.ts` — replace the `2400` total

The total is illegitimate to pin (the Owner's no-weight-pinning ruling). **The structure is not.** Replace the total with three assertions:

```ts
// 1. the three flexes the test lineup depends on are all priced 6
assert.equal(flexPenaltyFor('WR', 'CB'), 6);
assert.equal(flexPenaltyFor('WR', 'FS'), 6);
assert.equal(flexPenaltyFor('WR', 'SS'), 6);

// 2. the TE3 and inside-spot stand-ins actually fill their slots
assert.equal(lineup.filter(p => p.slot === 'TE3').length, 1);

// 3. DT plays FB free
assert.equal(flexPenaltyFor('DT', 'FB'), 0);

// 4. and the total is REPORTED, not asserted
console.log(`REPORT (not a gate) total: ${total}`);
```

**The point:** the test then catches a real structural break (a flex re-priced, a stand-in missing, DT>FB no longer free) **without pinning a number the weights produce.** That is the whole reason the Owner ruled it de-gated — and this satisfies the ruling *and* keeps the check.

### 4.2 `versions.test.ts` — MOVED/UNMOVED

```ts
// the engine stamp is REPORTED with a flag; the DATA stamp stays asserted
const stamp = readEngineStamp();
const moved = stamp !== PINNED_ENGINE_STAMP;
console.log(`REPORT engine stamp ${moved ? 'MOVED' : 'UNMOVED'}: ${stamp}`);
assert.equal(readDataStamp(), PINNED_DATA_STAMP);   // this one still gates
```

**The data stamp still gates because it passed** — it proves the ratings file is unchanged since its last pin. Only the engine stamp moves.

## 5 · Does the platform change the framework decision?

**One paragraph, as the prompt asks.** A platform has a **design surface** — knobs, presets, a rule editor, a live preview — and that is a different UI shape from a game: **more forms, more state, more validation, and less animation.**

**My answer: it does not change the decision, but it strengthens the authoring criterion and weakens the bundle criterion.** A rule editor is form-and-validation work, where **type-safety and error-message quality** dominate — both of which are authoring criteria, not output criteria. **So if the platform is the destination, the framework that is easier to write forms in should win, and the 10.9 KB should not.**

**That is a real answer to Q3 of the direction prompt: the platform tilts the weighting toward authoring, not toward bundle.**
