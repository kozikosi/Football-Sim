**Short answer: in every build on record, the player-of-the-game is either (a) silently absent because the PoG is only ever attached at `playGame` time and never rebuilt, or (b) deliberately null in v1's feed seam. The Owner's "some reviews have no player of the game" is not an exception path — it is the design.**

1. **Pre-Colors (reference): `g.detail` is set exactly once — at `playGame` (line 3483), via `buildGameDetail(g, hs, as)` — and never rebuilt, never re-hydrated, never serialized.** Every renderer that can show the game ball reads `g.detail.mvp` — e.g. `generateGameSummary` (3188: `const mvp = d.mvp;`), `renderGameResultHTML` (3730–3743: `const mvp = g.detail.mvp;` + `Key Players (⭐ game ball)`). Any game object that reaches those renderers without a freshly-built `detail` takes one of two paths: (i) the guarded early return at **2876** (`const r = g.result, d = g.detail; if(!r || !d) return '';`) — **the whole paragraph renders empty**, silently; or (ii) an unguarded `d.mvp` at 3188 — an exception that kills the review component for that game. The Owner's "some reviews" is (i) for any reload/restore/replay path that re-renders a played game from stored state where `detail` is gone or was never built (e.g. after a reload mid-week — the exact class the cakepanz boot path normalizes differently).
2. **The MVP itself can never be absent from a fresh `playGame`** (`buildGameDetail` always returns a non-null `mvp`: `pool = winTeam ? (team∩all + perfGrade≥90 losers) : all; if(!pool.length) pool = all; mvp = pool.reduce(max by ballScore)` — never null; the `TIE` case takes `winTeam=null → pool=all`). So "missing PoG" is never a selection failure — it is **always a missing/stale/elided `detail`**, i.e. a render-path or persistence gap, full stop. In the reference there is also no `autosave:week` surface at all (`grep -ni autosave` → 0) — hydration differs by build, which is why the symptom is intermittent rather than universal.
