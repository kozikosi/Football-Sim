## Attack points (new, not covered by OR or UK)

### 1. Stage 1 (seeded RNG) is coupled to V23 with no escape hatch
The doc says Stage 1 is "small, inside V23". But V23 is a UI-heavy build carrying the Owner's 30+ visual requests (P-001 through P-125). If V23 slips (likely, given the scope), the RNG slips with it. The seeded RNG (P-031) is the enabler for reproducible before/after numbers, which is the single most interview-valuable thing the project has. It should be a standalone stage that ships independently of V23 UI work, even if that means a small V23-adjacent patch. **Propose: split Stage 1 into Stage 1a (RNG, ships as its own small PR) and keep V23 UI work separate.**

### 2. "Remove a feature without losing the whole" has no stage
§4 asks "could I remove a feature without losing the whole?" and answers with "Stage 2 modules plus feature flags; and a CI job that deletes each feature module in turn." But the staged path (§3) has no stage for feature flags or the deletion CI job. The answer lives in §4 while the work lives nowhere. **Propose: add a Stage 2.5 "feature flags + module deletion CI job" before Stage 3, or fold it into Stage 2's exit criteria.**

### 3. Two git histories reconciliation is absent
AGENTS.md §2 documents two unrelated git histories (council/base from 474eb52, origin/main from 268fd56). The Architect plans "one deliberate unrelated-histories merge when Colors v1 ships." This is a real engineering problem (merge conflicts, asset reconciliation, Z.ai's package in z-core/) that an interviewer would probe. The architecture doc says nothing about how the two histories merge, what gets kept, or how assets (logos, CSV) are reconciled. **Propose: add a Stage 0.5 or a §2.5 note documenting the merge strategy, since it blocks everything in origin/main (logos, all-logos-sdv.csv, CLAUDE-START-HERE.md) from entering the council build.**

### 4. The "no build step for the user" constraint is unresolved and blocks Stages 2-4
§2 recommends reading "no build step for the user, one file" as describing only the delivered artifact. But §6 question 1 is "Does 'no build step for the user, one file' describe only the delivered file?" with default yes. If the Owner says no, Stages 2-4 are blocked. The doc correctly flags this but does not provide a fallback plan. **Propose: add a fallback — if the Owner says no, Stage 2 becomes "extract to a second HTML file that is concatenated at build time" (still one file delivered, but no modules in source). This is worse but unblocks progress.**

### 5. Stage 7 (second sport) references an unread branch as a prerequisite
The doc says "GPT's `gpt/multisport-strategy-proposal` branch exists (UNREAD by me; review it at this stage)." If this branch contains a fundamentally different abstraction (e.g., a plugin system vs. a data table), Stage 7's effort estimate and approach change. Reading it should be a Stage 0 or Stage 1 task, not a Stage 7 afterthought. **Propose: move "review GPT multisport branch" to Stage 0, or at least Stage 1, so the abstraction shape is known before module extraction (Stage 2) locks in the interface.**

### 6. Stage 0 "done pending approvals" understates the blocker
Stage 0 says "done pending approvals" but ENGINE-MATH-SPEC.md §9 confirms DL5=140 and flex rules still wait for Owner approval. AGENTS.md §3 lists 7 protected constants. The doc does not enumerate which are approved vs. pending. An interviewer asking "what is the approval gate?" would get a vague answer. **Propose: Stage 0 should list each protected constant with its approval status (approved/pending/needs-repin) and the exact Owner note that approved it.**

### 7. No mention of the preservation/commit workflow in CI
AGENTS.md §4 mandates commit+push after every task, preservation gate checks, no force-push. The CI stage (Stage 3) should enforce these same rules (e.g., a CI job that checks no uncommitted work, no force-push to protected branches). This is part of "how is it deployed and who sees a failing build?" which §1 lists as an interview question. **Propose: add a CI rule "no force-push to main/council/base" and a preservation check to the Stage 3 exit criteria.**

### 8. Stage 5 (persistence) and Stage 6 (accounts) ordering
The doc puts persistence before accounts. But if the data is per-user (seasons, drafts), persistence without accounts means anonymous data that cannot be recovered across devices — which is the main reason to have a database. Either accounts come first (so data is owned), or the doc should explain why anonymous persistence is valuable (sharing links, public leaderboards). **Propose: clarify the ordering rationale or swap 5 and 6.**

Beyond what OR and UK flagged (testing, security, performance, data integrity, rollback), I add:

- **Git workflow / branching strategy**: the project has a complex multi-worktree setup (AGENTS.md §4) that is itself an interview talking point. The doc doesn't mention it.
- **Error handling / graceful degradation**: no mention of what happens when the lab fit fails, when a roster is missing players, when localStorage is full. An interviewer would probe "what happens on bad input?"
- **Accessibility**: no mention of keyboard navigation, screen readers, color contrast (Owner requests rose/gold/white — contrast audit Q-V23-2 is open). An interviewer at a modern company would ask.
- **Internationalization**: the product is English-only (AGENTS.md §7 rule 7). Fine for now, but an interviewer might ask about i18n strategy.
- **Monitoring/observability**: no mention of error tracking (Sentry), analytics, or performance monitoring. "How do you know it's broken in production?" has no answer.
