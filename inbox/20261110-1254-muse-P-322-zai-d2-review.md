## Corrections needed (why "improved", not "ok")

12. **The weight source is misattributed — the script calls the live engine weights "the ruling-2026-11-06 salary weights."** The script's `SALARY_PRIMARY` dict (QB 1000, C 150, OLB 150, …) is **identical to the current engine weights** (`slots.ts` / `tools/mathlab/design.json`, REV 5 spec values) — I verified zero mismatches. But the script comment says "Owner's salary weights (ruling 2026-11-06)" and the doc §2.3 says "the Owner's salary weights, primary slot per role (QB 1000 … FB 25). This is the ruling-2026-11-06 table — Owner's law, already in the repo." **The Nov 6 salary table is DEAD** (KG killed it 2026-11-08; slots.ts was reverted to the REV 5 spec values). The VALUES Z.ai uses are correct (they are the live engine weights), but the ATTRIBUTION is wrong and will confuse the Owner, who explicitly killed the Nov 6 salary table. The gate's value source must be renamed to "the engine's slot weights (slots.ts/design.json)" everywhere it appears (script comment, §2.3, §0). This is the most important correction in this review — the design is built on the right numbers under the wrong name.
13. **CHECKSUMS.txt does NOT match the committed files.** The delivery claims "checksums verified against CHECKSUMS.txt before commit," but the hashes in CHECKSUMS.txt do not match the committed bytes:
    - Design doc: CHECKSUMS claims `8762a9ea…`, committed file hashes to `81ea1ad9…`
    - Script: CHECKSUMS claims `eef3ae84…`, committed file hashes to `ebd28f59…`
    - Run log: CHECKSUMS claims `c3b0f37e…`, committed file hashes to `b0be9b17…`
    I verified this by hashing the git blobs directly (byte counts match the committed sizes, no CRLF). The files themselves are fine — the run log is byte-identical to my re-run — but the integrity claim is not verifiable from the committed artifacts. The checksums were likely computed on Z.ai's local copies before a final edit or re-save. Regenerate CHECKSUMS.txt from the committed files, or drop the claim.
14. **C PBLK=7 costs TWO rows, not one — the doc understates it.** The doc §7.3 says at PBLK=7, "C>OT's M drops to 4.65, the gate goes silent, C>OT prices 6." I re-ran with C HAVE PBLK=7: the fit is **97/99**, not 98/99 — **C>OG also breaks** (price 3.58, tier 2, owner 6), in addition to C>OT (price 5.13, tier 6, owner 12). The doc only mentions C>OT. The Owner's "6 or 7 is honest" means choosing 7 costs two rows (C>OT and C>OG), and the design's 99/99 is conditional on C PBLK=6. The convergence conversation needs the true cost (97/99 at 7), not the implied 98/99. The doc's recommendation (6) is right; the stated cost of 7 is incomplete.
15. **k-norm numbers in the doc are off by one.** The doc (§2.2, §4) says k=1.5/2.0/3.0 → 93/91/83. My re-run (and the shipped run log, which is byte-identical) gives **93/92/84**. The doc understates the k-norm fit by 1 at k=2.0 and k=3.0. §6's "91–93/99" also excludes k=3.0's 84. The conclusion (k-norm rejected, medium gaps must compound) is unchanged, but the doc numbers don't match the log. Correct to 93/92/84.
16. **LORO "4 of 9 rows shift a tier" is wrong — it is 3 of 9.** The doc §7.6 says "4 of 9 rows shift a tier." The LORO output shows exactly 3 tier-differ rows (SS>FS t2→t0, SS>CB t6→t2, SS>WR t12→t6); the other 6 are tier-identical. Zero hard misses is correct. Correct "4" to "3."

The 152 is the FULL-grid (17 sources × 19 destinations) cap count; the 190 is the 17×17-grid unpriced count (272 non-diagonal pairs − 82 priced non-diagonal rules within the grid). ## Notes (understood, not findings)

19. **The live table's 2 self-rules (ILB>ILB, OLB>OLB, both owner 0) are trivially exact.** They are included in the 99, so the effective cross-role fit is 97/97. This applies to every design scored against the 99 (not just ZAI-D2), so it is not an advantage — but the "99/99" headline includes 2 freebies. Worth knowing, not a defect.
20. **The `ability()` S computation excludes all gaps equal to M** (`if v != m`), not just one instance of the max. I checked: **no rule in the 99 has tied max gaps**, so this does not affect the fit. It is a latent difference from MUSE-D2's implementation (which excludes only the top duty by key). Harmless here; worth aligning if the code is ever reused where ties occur.
21. **The `live_absent` variable in the script is dead code with a wrong formula** (`len(all_src)*len(all_dst) - len(priced) - len(priced)`). It is computed but never printed, so it does not affect the output. Minor code nit.
22. **The gate's R=3.0 condition depends on the weight source.** With slots.ts weights (C 150, OT 500), C>OT's ratio is 3.33 ≥ 3.0, so the gate fires. With sport-football.json weights (C 200, OT 500), the ratio is 2.5 < 3.0 and the gate would NOT fire. This is another reason finding 12 matters: the design's 99/99 depends on the slots.ts C value (150), not the sport-football.json C value (200). The doc should state which weight table the gate reads.
