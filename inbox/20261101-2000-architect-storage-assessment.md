# Architect assessment of the storage brief (1 Nov 2026) - for Z.ai and the Owner
Source brief: `_agents/owner-notes/2026-11-01-storage-brief-verbatim.txt`. Labels: VERIFIED = run or read in `colors/` at `cfe97fa`; INFERRED = reasoning, not tested.
No implementation code here. Numbers come from `colors/test/fixture.ts` (real Madden file, 1,953 players, seed 777) and a season at seed 5.

## A. Answers to the engine questions (§6)
**Q1 Seeds - VERIFIED.** Exists today. `rng.ts` = mulberry32 over ONE uint32; `fork(label)` derives an independent stream from (seed, label). A season is a pure function of (rosters, seed, year, prevRank); same inputs give the same champion/record (`season.test.ts`). Shape: **seed only is enough** - there is no serialisable mid-stream state because nothing ever pauses mid-stream (every game is its own fork `w<week>:<home>` / `po:<round>:<home>`). Storage reads/writes the seed as a plain integer. Do not persist PRNG state. Fork labels are part of the ruleset version: renaming one changes every result.
**Q2 Re-entry at a week's preview - VERIFIED yes, with one gap.** `simulateGame` is atomic and pure; it returns the whole `GameResult` (drives, events). There is no pause-mid-drive state in the engine. The 2nd-quarter view is UI playback of a finished result, so a refresh loses only UI position: nothing is unaccounted for **in the engine today**. Two gaps: (1) `simulateSeason` runs all 285 games in one call (88 ms), so there is no week-stepping API; (2) the user's per-week plan choices are not ported yet (step 9 gap). When they are, a week's result depends on a choice made AT the preview, so the season must be stepped, and the preview save must contain the user's plan state. Both are mine (E3 below).
**Q3 Player IDs - VERIFIED, and the news is mixed.** IDs exist but are the composite string `name|pos|team`, not stable: a rename, a position change (HB to FB) or a trade changes the id, i.e. exactly the cases the Owner described. Free agents and the 3 repeated names are already disambiguated by pos/team. Cost of stable ids: a crosswalk file `data/player-ids.csv` (key to pid, minted once, never reused; new players get new pids; a changed player keeps his pid by an explicit crosswalk row) plus a `pid` column or lookup in `buildPool`. About half a day, but it **changes tie-break order in the draft** (`byOvr` ties on id string), so seeded results and golden files move once. Freezing: feasible, see §C. The crosswalk needs a human-checked first pass: nothing can infer "same player after a rename".
**Q4 Interface** - see §D. **Q5 §5** - see §B.

## B. Where I disagree or read differently (the Owner asked me to challenge)
1. **A seed+picks save breaks on any engine or data update.** `app/store.ts` today saves `{seed, userTeam, picks}` and REPLAYS the CPU draft. That is fine in one session and wrong for persistence: change `draft.ts`, a CPU trait, or the CSV, and the same save rebuilds a different league. It also cannot keep "old OVR/names". So persisted saves must be **materialised results with frozen player values**, not recipes. This matches the council's "materialised snapshots", but for a better reason than "RNG is unseeded": my RNG is seeded, the recipe is not durable. (The w58 shell's RNG is unseeded; that only strengthens the rule.)
2. **Refresh mid-game must replay the SAME outcome, not re-roll.** The rule says a refresh returns to the preview and the user replays "against the same opponent". If the result is rolled after the preview, refresh = free re-roll of a loss, which also makes "went 17-0" cheap to farm. Fix: when the preview is committed, store that game's seed (derived from the slot seed and the week) so replay is identical. **Owner call**: same result after refresh (my recommendation) or re-roll.
3. **Compression is not needed.** Numbers (JSON chars; gzip in brackets):
   | payload | chars |
   |---|---|
   | thin draft record (current store) | 2.0 K (0.7 K) |
   | user roster frozen, 32 players, full fields | 3.8 K (1.2 K) |
   | whole pool frozen, 1,953 players, full fields | 233 K (45 K) |
   | whole pool as [id,ovr,spd,str] tuples | 93 K (28 K) |
   | all 32 rosters frozen, 1,024 players | 122 K (25 K) |
   | season scores only (285 games) | 14 K (2.7 K); 4 K with team indices |
   | final table | 1.9 K |
   | **full GameResult, 1 game** | 4.3 K |
   | **full GameResults, whole season** | **1,123 K (109 K)** |
   Worst design, 3 slots each holding a frozen full pool (mid-draft) = 0.7 M chars; 3 slots with all-league frozen rosters = 0.37 M. localStorage is about 5 MB per origin (browsers differ); counting 2 bytes/char gives 2.5 M chars, so the worst design uses 15 to 28%. The one thing that does not fit is full game logs: 3 x 1.1 M = 3.4 M. That is already the Owner's rule ("prune all season logs"), now with a number. **3 slots are fine.** Compression adds async work, harder corruption debugging and no headroom we need; drop it from v1. The async facade stays, so IndexedDB remains a clean swap.
4. **The save's storage origin is a risk nobody named.** localStorage and IndexedDB belong to the origin the page is served from. Moving the game to another host or domain loses every save; opened from `file://` the behaviour differs per browser; Safari may evict script-written storage after about 7 days without a visit (INFERRED, from memory, not checked). Z.ai: state the deployed URL and check these. The "never imply recovery" rule in §5(b) is right; add that a move of host is also a loss.
5. **"Prune oldest expendable first" vs "completed slots stay until overwritten".** Define expendable explicitly: the one-deep backups, then a slot's preview, never a completed slot or a stats record. If only those remain and a write still fails, tell the user and refuse the write rather than evict a run.
6. **"Run it back with the same players, ideally a different schedule" is under-specified, and the engine does not do it for free.** I checked (VERIFIED): seeds 5 and 6 on the same year give 272 of 272 identical home/away matchups; the seed only reorders weeks and byes. Opponents come from the year and last season's division ranks. §8 says "same pool (same IDs)", so I read run-it-back as a **new draft from the same pool**, which is fine. If the Owner means "same drafted roster again", say so, because that needs a different year/prevRank input to change opponents, and removed players must be handled. Owner call, one line.
7. **Corrections of fact in §5(b) and §8 I agree with:** the backup does not survive a data clear; the app must not suggest otherwise.

## C. What a save must hold (my side of the contract)
Common envelope, plain JSON only (no engine objects, no Maps): `{kind: 'draft'|'week'|'season', schemaVersion, engineVersion, dataVersion, slot, savedAt, payload}`.
- **draft (mid-draft):** seed, userTeam, picks made so far (overall, team, pid, slot) and a frozen copy of the pool as compact tuples plus names (about 233 K). Needed because §8 freezes the board at draft start. After the draft ends the pool is dropped.
- **week (game preview, rolling, one per slot):** seed, year, 32 team `Ratings` and lineups needed to simulate (small; INFERRED about 10 to 15 K, I have not measured it), the user's 32 frozen players, the schedule, scores so far, the next week and its game seed, the user's plan state once ported.
- **season (completed):** final table, the user's schedule results, playoff results, champion, the user's 32 frozen players. No logs, no drives (about 25 K). Global stats are updated from this, once, atomically with the slot write.
Global store (separate keys): profile, settings, stats by overall and by franchise, achievements. Keyed by franchise, never by slot.

## D. Interface, boundaries, merge safety
- **Storage consumes only the envelope** and returns it. It must not import from `colors/src/engine/**`. The engine/store side must not import storage. The only shared artefact is the envelope TypeScript/JSDoc type that I publish.
- **Facade:** async `list() -> SlotMeta[]`, `load(slot)`, `save(slot, envelope)`, `delete(slot)` (soft), `migrate()`, plus `stats.read/update`, `settings`, `profile`. `load` returns a typed result (`ok | empty | corrupt | newer-version | unavailable`) so the UI can say the honest thing in each case.
- **Z.ai must not touch:** `colors/src/engine/**`, `colors/src/app/store.ts`, the 39-function seam and its 10 laws, `build/build.mjs`, fork labels, and the team packs (`zpbPackFor`). Z.ai owns: the storage module, the stats module, UI for Continue/slots/profile/settings/brag, their tests.
- **Merge conflicts in the single-file shell:** storage lives in its own payload block (own marker comments), the same pattern as the `w51-js` / `w53-js` blocks, so the file diff is one contiguous region. Screen call sites are wired in a separate commit, not mixed with the module. Branch rule stays: Z.ai pushes `council/zai`, I push `architect/engine-and-seats`.
