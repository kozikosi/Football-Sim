## ADR-001: Browser compute (Web Workers), not server-side simulation

**Decision:** Simulations run in the browser via Web Workers, not on a server.

**Context:** The friend proposed server-side simulation. The council (GPT, Z.ai, DeepSeek, Grok) reversed this: free Cloudflare Workers allow 10 ms CPU per invocation (REPORTED, not verified by the Architect), so server-side simulation is infeasible on free tiers. Browser compute is free and unlimited (user's machine).

**Rejected options:** Server-side simulation (Cloudflare Workers, Lambda) — infeasible at free tier; server costs money and adds latency.

**Consequences:** Simulation must be fast enough for the browser (7.8 ms/game measured, §4). Web Worker prevents UI blocking. No server infrastructure needed for the core loop.

**Trigger to revisit:** If a single game exceeds 100 ms or a 1000-season Monte Carlo exceeds 10 minutes; or if the Owner wants shared/public simulations.

**Free-tier source:** Cloudflare Workers 10 ms CPU limit — REPORTED by the council, not verified by the Architect (§13: "REPORTED: nothing in this section was checked by the Architect").

## ADR-002: Engine = framework-independent TypeScript with injected seeded RNG

**Decision:** The simulation engine is pure TypeScript with no DOM dependency and no `Math.random`. All randomness goes through an injected `rng()` function. Zod validates data only at load boundaries.

**Context:** The current engine is 439 functions in one inline script with 56-58 `Math.random()` sites and no seed (§1, VERIFIED). No run can be repeated. The spec requires reproducible runs for before/after comparisons (AGENTS.md §3, "Moving a number").

**Rejected options:** Keep `Math.random` (no reproducibility); server-side RNG (adds server dependency); WASM (premature, no measurement demands it).

**Consequences:** Golden fixtures from seeded runs become possible. Property tests (fast-check) can verify invariants. Engine can be tested in Node without a browser. Extraction to modules (Stage 2) is unblocked.

**Trigger to revisit:** If browser compute proves insufficient (see ADR-001); if a native-language engine is needed for performance.

## ADR-003: No database in v1

**Decision:** No database in v1. State is in-memory with localStorage as a convenience cache. A database is added only when a feature needs one (Stage 5).

**Context:** The friend proposed full-stack with a database. GPT, DeepSeek, Grok argued: not until a feature needs one. Supabase's free tier pauses on idle, failing the "nothing on the demo path sleeps" rule. Cloudflare D1 (SQLite) is the candidate when needed.

**Rejected options:** Supabase (free tier pauses on idle — fails rule 2); hosted Postgres (costs money or requires paid tier); D1 in v1 (premature, no feature needs it yet).

**Consequences:** No multi-device sync, no history, no sharing in v1. Simpler stack, faster to ship. localStorage kept as convenience cache.

**Trigger to revisit:** When a feature requires cross-device sync, history, or sharing (Stage 5). Candidate: Cloudflare D1 + Drizzle.

**Free-tier source:** Supabase pauses on idle — REPORTED by the council. D1 free-tier limits — UNKNOWN, not checked (§7 of ARCHITECTURE-DIRECTION.md).

## ADR-004: No authentication in v1

**Decision:** No authentication in v1. If added later (Stage 6), use OAuth via a maintained library (GitHub/Google). Never hand-rolled password hashing.

**Context:** The friend proposed Auth.js with email + password. Others: none in v1, then GitHub OAuth, Better Auth or Auth.js. Never store passwords yourself.

**Rejected options:** Email + password with hand-rolled hashing (security risk); Auth.js in v1 (premature, no per-user data worth protecting yet).

**Consequences:** No per-user data in v1. Simpler stack. When auth is added, it is OAuth-only via a maintained library.

**Trigger to revisit:** When per-user data exists worth protecting (saved seasons, shared drafts, leaderboards).

## ADR-005: Hosting = Cloudflare Pages; CI = GitHub Actions on public repo

**Decision:** Host on Cloudflare Pages. CI via GitHub Actions on a public repo. pnpm without workspaces. Vite through the framework. No WASM, WebSockets, queues, Durable Objects, Turborepo or Nx until a measurement demands them.

**Context:** The council converged on Cloudflare (free, one-command deploy) over AWS. The friend's "may not work well" concern about Next.js on Cloudflare is partly right: OpenNext adapter on Workers, not Pages, with limits (Node middleware unsupported, 3 MiB compressed Worker size on free plan — VERIFIED, opennext.js.org/cloudflare).

**Rejected options:** AWS (S3 + CloudFront, Lambda, DynamoDB/RDS, Cognito) — more complex, no benefit at this scale; Vercel (costs money beyond free tier); WASM/WebSockets/queues (premature).

**Consequences:** Free hosting and CI. Public repo means free GitHub Actions. Vite is the build tool through whichever framework is chosen. No advanced infrastructure until measured need.

**Trigger to revisit:** If Cloudflare free tier is revoked (rule 4: assume any free tier can be revoked); if bundle exceeds 3 MiB compressed; if a feature needs WebSockets or queues.

**Free-tier source:** OpenNext Cloudflare adapter notes, https://opennext.js.org/cloudflare (read 27 Oct 2026, VERIFIED). Cloudflare Pages free tier limits — not independently verified beyond the adapter docs.

## ADR-006: Testing = Vitest + Playwright + fast-check

**Decision:** Unit tests via Vitest, end-to-end via Playwright, property tests via fast-check (e.g., "no player drafted twice"). Golden fixtures from seeded runs. Keep the legacy HTML as the archived reference and prove seeded parity before changing the model.

**Context:** The project currently has 1 test file (169 lines), no CI, no types. The lab has mathlab tests (check-design.mjs, realcheck.js, flexparse, etc.) that run on the extracted engine. The spec §7 defines E1-E10 acceptance tests.

**Rejected options:** Jest (slower, heavier); Cypress (Playwright is preferred by the council); no property tests (misses invariant violations like "no player drafted twice").

**Consequences:** Fast unit tests in Node (no browser). E2E tests verify the UI. Property tests catch edge cases. Golden fixtures from seeded runs enable regression detection.

**Trigger to revisit:** If Vitest proves insufficient for the test volume; if a different E2E tool is needed for mobile testing.

## ADR-007: Four free-tier rules (Z.ai)

**Decision:** Four rules govern all free-tier usage:
1. **No card** — never require a credit card for any service on the demo path.
2. **Nothing on the demo path sleeps** — no service that pauses on idle (Supabase fails this).
3. **Quotas fail closed** — when a quota is exceeded, the feature degrades gracefully, not catastrophically.
4. **Assume any free tier can be revoked** — design so revocation of any single free service does not break the core product.

**Context:** Proposed by Z.ai (§13). These rules prevent vendor lock-in to free tiers and ensure the demo always works.

**Rejected options:** Relying on a single free tier without fallback (violates rule 4); paid tiers in v1 (violates rule 1).

**Consequences:** Every external dependency must have a fallback or be non-critical. The core product (simulate a season) must work offline with no external services.

**Trigger to revisit:** If the Owner decides to pay for hosting/infra; if a free tier is revoked and no fallback exists.
