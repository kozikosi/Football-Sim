# DEEP 1 — D2 · `kind:'save'` shares vs "no hidden full save"

1. **How I would decide:** I would **remove `kind:'save'` from v1 share creation** and ship `kind:'run'` only — the result line, which is already implemented and tested. I would leave `GET /api/share/:token` generic so a future, explicitly ruled kind can be added without a route change. I would *not* try to salvage save shares by stripping seed/pool fields until the Owner asks for that feature, because partial redaction is easy to get wrong and still contradicts the purpose.
2. **Why:** V `api.ts:371-377` stores `snapshot = row.envelope` — the whole envelope with seed, draft pool and pick history — behind a 128-bit capability link. The Owner's 1 Nov words (canonical §3.1) are unusually specific: *"The challenge is not replay their exact season and matchup, just to play the general game and try to go undefeated. the challenge shouldn't carry a save. it's not a seed challenge. it' a brag share"*, *"no to the hidden full save"*, *"The user shouldn't be exporting anything. That's too much. No downloads."* A full save behind a link is an export by another name. P-209's locked brag is text + bare URL; the run share already satisfies it. This has been open since 21 Nov because I originated the finding and explicitly declined to rule on it — that was right; the Owner must.
3. **What would change my mind:** an explicit Owner ruling that a read-only save snapshot is wanted (e.g. "let a friend see my completed board"), **plus** a test asserting the snapshot carries no seed, no pool and no resumable state. A saying-so without the byte-level carve-out would not change my mind; the prohibition and the seed are both explicit.
4. **Who owns:** **Owner** — externally visible and reverses a stated anti-goal. Architect implements. Not a seat call, not a queue row.
5. **Blocked meanwhile:** `POST /api/shares` has two kinds and its tests/contract wording describe both. Until ruled, any build could ship a feature the Owner prohibited. The S15 shell close-out is **not** blocked by this — brag text has no save and no seed today.

# DEEP 2 — A · Account deletion (A1–A6 as one cluster)

1. **How I would decide:**
   - **A1 → A**: build `DELETE /api/account` before launch. Accounts are a mandatory release capability, so a person must be able to erase the data we hold about them; a hand-run Owner erasure puts the Owner in the data path permanently.
   - **A2 → A** for v1: hard delete behind a typed confirmation. B (grace window) is a genuine consumer-grade improvement but needs new state, a scheduled job and a restore path — real scope on the critical path. C (anonymous marker) leaves data behind and defeats the request.
   - **A3 → C if the library can avoid storing tokens; otherwise A if a deletion hook exists; otherwise B with explicit copy.** V: `encryptOAuthTokens: true` means tokens *are* stored, though encrypted, and the comment itself says they are not needed after sign-in. The cleanest privacy posture is to store nothing; I would not assert a Better Auth API I have not read — Architect verifies.
   - **A4 → A**: delete all share rows and runs; accept 410 links and changed public aggregates; document both plainly. Orphan share rows leak; carving deleted runs out of the fold invents a stats rule nobody asked for.
   - **A5 → A**: accept session-id-only identity, idempotent 204, no tombstone, one batch. A retried erase must not 404 or fail half-way.
   - **A6 (if deferred) → A**: a documented manual erasure runbook with a published contact. C is not defensible once accounts hold real saves.
2. **Why:** V `AUTH_ALLOW` has no `delete-user`; the four data tables key on `user_id` with no cascade, so our rows survive Better Auth's user deletion — the gap is ours, not a library omission. The primitives (`db.batch`, soft-delete, share revoke) already exist, so this is a small, bounded build. Portfolio framing matters too: "professional delivery" includes handling erasure. The reason for typed confirmation and idempotency is that the action is irreversible and retried over flaky mobile connections.
3. **What would change my mind:** for A1, a ruling that launch is a single-tester private rehearsal (then B suffices) or an explicit "manual erasure contact is acceptable" with the contact named. For A2, evidence of accidental-deletion risk in testing, or a free scheduled-purge primitive already in the Worker (then B becomes cheap). For A3, reading Better Auth 1.7.27 and finding neither a no-store option nor a hook (then B is the only honest path). For A4, an Owner view that public aggregates must survive an erasure — that flips me to C, but it needs a new stat rule and a privacy explanation to users.
4. **Who owns:** A1/A2/A4/A6 = **Owner** (person-facing, irreversible, externally visible). A3/A5 = **Architect** (library capability and mechanism), with the Owner accepting any residual GitHub grant under B.
5. **Blocked meanwhile:** whether Claude spends the next sitting on the route or moves to the client sync module; the launch privacy posture; whether the Owner is personally in the erasure path. Nothing blocks the S15 shell close-out.
