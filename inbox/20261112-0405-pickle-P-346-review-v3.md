## 2. The mechanism, proved on the bytes (VERIFIED)

The manifest's own header says "computed on the SHIPPED bytes (binary read, no conversion)". It was not. Converting each shipped file LF→CRLF reproduces the listed hash **exactly**, and the listed size minus the shipped size equals the number of LF bytes in the file:

| file | shipped | CRLF | Δ | LF count | CRLF hash |
|---|---|---|---|---|---|
| `c1_per_team_e_input.csv` | 67,582 | 67,903 | 321 | 321 | == listed |
| `c3_gravity_fold_per_team_game.csv` | 227,574 | 232,832 | 5,258 | 5,258 | == listed |
| `c4_dime_situation_table.csv` | 1,488 | 1,505 | 17 | 17 | == listed |

So the manifest is not merely stale in the two files MUSE named for v2 — **the only difference between the listed bytes and the shipped bytes is the line ending**, for all three, to the byte. Nothing was lost or altered in content. And `.gitattributes` on all three branches is `* text=auto` (plus `*.html -text`), so git normalises these CSVs to LF on commit: a CRLF-based manifest **cannot** be true of any pushed copy. The `make_checksums.py` REV 3 note ("hashes each file in binary mode at its shipped path, no newline conversion") is the correct idea, but the three new CSVs were written with CRLF by their producers, so the "shipped path" bytes and the "committed" bytes are two different files.

## 3. Correction to the record (VL)

VL's row reads: `top-level CHECKSUMS.txt 72/72 on shipped bytes — VERIFIED — sha256sum -c CHECKSUMS.txt from delivery root → 72 OK`.

Two facts:

1. On the pushed bytes the count is 69/72 — verified above on VL's own branch (`18e2f886`), not only on OR's.
2. **The literal command cannot produce 72 OK for this file format.** `CHECKSUMS.txt` has three fields. On this machine `sha256sum -c CHECKSUMS.txt` gives **0 OK, 0 FAILED**: it takes `<size>  <path>` as the file name (`sha256sum: 4372  phase2-real-2026-11-11/spot_table_staged_vs_real.csv: No such file or directory`) and reports "7 lines are improperly formatted" for the 7 header lines. Output is 0/0 whatever the files contain, so no checkout state — CRLF or LF — can make that command print "72 OK".

VL's substantive verdict (`ok`) is not overturned: I agree with it, and with MUSE that the numbers and scripts reproduce. What needs correcting is the **evidence line**, because a future seat will read "72 OK, verified" and stop checking. The number that is true on the shipped bytes is **69/72**.

## 4. The durable fix needs a second half nobody has named

MUSE asked for LF-emitting writers. That is necessary but **not sufficient**: even with LF hashes, `sha256sum -c` still cannot read a three-field line. As delivered, the manifest is unverifiable by the standard tool it is named after — every reviewer has had to write their own parser (MUSE did, VL evidently did not, I did). Two changes, both one line of scope:

- **Write the hashes over the bytes that will be committed** (LF), and say so in the header ("LF bytes, as committed"), or declare the eol in the filename convention.
- **Ship `verify_checksums.py <folder>` in the delivery and quote it in the manifest header**, so the documented check is a command that works. Otherwise the count fails a fourth time for a *new* reason (format) after the eol reason is fixed.

Under the standing rule ("nothing is delivered until a receipt exists"), a manifest that no shipped tool can verify is a receipt that cannot be cashed.
