## Findings (blocking, in rough priority order)

1. **The replacement drops every existing setActiveTab side effect.** As written ("old -> new"), integrating it deletes: `SUPP_TITLES` supplemental-header rendering and its back button, the `.hero` show/hide toggle, `window.scrollTo(0,0)`, `updateStepper()`, `renderHomeComparison()` (Compare tab renders nothing), `guideHTMLCached()` (Guide renders blank), `fillDraftGuide()` (draft guide blank). The proposal must be re-expressed as a diff to the real function (keep all existing lines; wrap only the `.view` toggle in the fade), not a from-scratch function.
2. **Wrong selector for the tab state.** `.tabbtn` ≠ the six simulator tabs (`.footlink` by id, l.440–445). Use the product's own id-list toggle (l.838–839) inside the fade flow, or the tabs will silently stop updating.
3. **The 2 s draft fade-in never runs.** The JS adds `.fade-in` and `.active` together, then removes `.fade-in` on the next `requestAnimationFrame`. There is no rendered intermediate state: the element goes display:none → block with final opacity 1 (`.view.fade-in.active` specificity 0-3-0 beats `.view.fade-in` 0-2-0), and removing `.fade-in` one frame later is a 1→1 no-op. Net effect: hard cut-in, the opposite of the Owner's request. Fix: either apply a keyframe animation class (`draft-fade-in`) on the newly-activated view and remove it on `animationend`, or keep `.fade-in` until the transition completes (transitionend), with forced reflow between display and opacity if using transitions.
4. **The keyframe CSS is dead code.** `.homepage-fade-out`, `.draft-fade-in`, `@keyframes homeFadeOut/draftFadeIn` are never added by the JS and are not tied to any element id (`#draftSetup`? `.hero`? `#viewDraft`?). Either wire them up or delete them; as-is they are untestable decoration.
5. **Display-based views + opacity transitions don't mix without work.** `.view{display:none}` (l.55) means no transition from hidden; only `animation` or a reflow-separated two-step works. The proposal's `.view{transition:opacity 400ms}` base rule also fades any opacity change anywhere else on views (none exist today, but it's a trap). Recommended shape: keep `display` toggling in setActiveTab, add `animation: viewFadeIn 2s ease` on `.view.active` via a class, and rely on a leave-animation on the old view only for the homepage→draft path.
6. **Scope is ALL tab switches, not homepage→draft.** The proposal replaces setActiveTab globally: Rankings, Players, Groups, Compare, Guide would all gain a 2 s out + 2 s in. The Owner asked for the homepage→draft transition only. Gate the slow path on `btnId==='tabDraftBtn'` (and symmetric `viewDraft`), keep the other five tabs instant (or a 150–200 ms fade).
7. **Mid-fade rapid clicks race.** The proposal itself flags this ("Must also handle rapid tab clicks") but the snippet does not implement it: two clicks inside 2 s create two live `setTimeout`s that both manipulate `.active`/`.fade-in` on overlapping view sets — views can end hidden-but-`.active`-less or doubly-classified. Fix with a monotonically increasing fade token (or clearTimeout on a stored handle) and by removing `.fade-out` from any element not targeted.
8. **Reduced-motion path leaves a 2 s dead delay.** In the `prefers-reduced-motion` block, transitions/animations are disabled but the JS `setTimeout(2000)` still gates the view swap — the user clicks and stares at an unchanging page for 2 s. Under reduce, the timeout must be ~0 (check `matchMedia('(prefers-reduced-motion: reduce)')` in JS, or derive delay from the computed transition duration).
9. Minor: anchor `l.~3936` wrong (see receipt 1); `#draftBoard` doesn't exist (receipt 3); the two `.view` transition durations (400 ms base vs 2 000 ms `.fade-out`) and the duplicated `.homepage-fade-out`/`.fade-out` mechanisms are redundant — pick one.
