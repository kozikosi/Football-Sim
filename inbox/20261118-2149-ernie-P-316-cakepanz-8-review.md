## 2. Findings — Block B (P-337)

### F1 — DEFECT (a11y / dead control): the simple row's main button does nothing, but announces `aria-expanded`

`src/lib/components/BoardRow.svelte` (both trees, lines 15–27): in the `simple` branch the row is

```svelte
<button class="cp-main cp-mainsimple" onclick={() => (open = !open)} aria-expanded={open}>
```

but the detail panel that `open` reveals (`<div class="cp-fits">` with the flex chips) lives **only in the `{:else}` branch**. So in the simple form a click flips `open` and nothing renders. A sighted user clicks the row and sees no response; a screen-reader user is told "expanded" with no panel. Law L2 checks that the chips and advice panel are absent — it does not check that the row is inert, so the battery is green on a control that lies.

**Fix (one line, either):** render the main element as a non-interactive `<div>` in the simple form (drop `aria-expanded` and the handler), **or** — better, and it also answers F4 — let the simple row's click open the *same* `cp-fits` panel, so "every number is one click away" is true at the row level and not only via the whole-board door.

### F2 — DEFECT (UX / honesty): the "one number" is not necessarily the ranking key

The simple row shows `r.wins` as `.cp-rec` (the recommendation), and the honest line says "the board simplified". But the row **order** still comes from `vm.sort`, and `SortControls` offers `wins | priority | ovr`. `BoardFooter` hides the sort controls behind a toggle in simple mode but **does not reset the sort**, so a user who was sorting by `ovr` or `priority` at pick 10 sees, from pick 11, a board ordered by one key while the single visible number is `wins`. The "one recommendation number" then does not rank the rows the user is reading.

**Fix (cheapest honest one):** label the number with its basis — `2.4 WINS` rather than a bare `2.4` — and, when `sort !== 'wins'`, add the basis to the honest line ("ordered by priority"). Forcing `sort = 'wins'` at the flip is the other option, but it changes row order, which would move the board VM and break L4's frozen-state sha comparison; the label does not.

### F3 — DEFECT (theme): the new Block B surfaces bypass the token system

`BoardRow.svelte:80–82` (`.cp-rec`, `.cp-pickbtn`) and `DraftBoard.svelte:62` (`.cp-fullbtn`) are new CSS in this round and they hard-code `#e8c87e`, `#8a5f18`, `rgba(217,169,76,…)`. The theme defines `--goldm: #ad7f2e`, `--gold2: #e6c67d`, `--gold3: #9a6b1f`, `--on-gold`, `--hairline`, `--sub` (`src/lib/assets/tokens-w89.css:42–57`) and re-defines them per mode (`:105–111`). The new recommendation number and both new buttons therefore **will not follow the light/dark token sets** — and `#e8c87e` is not even the value of `--gold2` (`#e6c67d`), so the recommendation number is a fourth gold.

This is consistent with the file's pre-existing `cp-chip`/`cp-btn`, so it is not a regression — but it is a *new* surface added after the theme work, and it lands squarely on the Owner's two open contrast decisions (light gold2 1.65:1, dark `--text`). **Flag, do not fix:** the Owner's contrast ruling should be taken with these three selectors in hand, or the next theme pass will have to re-touch them.

### F4 — RISK (UX): the FULL BOARD door is one-way for the rest of the draft

`App.svelte`: `onfullboard={() => { simpleOff = true; }}` and `lateMode` requires `!simpleOff`; `simpleOff` resets only on a **new** draft. That is what the order asked for ("stays full"), and L3 asserts it. But a user who taps FULL BOARD once — to look at one thing — is locked out of the simple form for the remaining ~22 rounds, with no way back and no message saying so. Cheap mitigation: while `lateMode` is available and `simpleOff` is true, show a `SIMPLE` button in the footer that clears `simpleOff`. Presentation-only, moves no number, L1/L3 unaffected (L3 would need to assert the return too).
