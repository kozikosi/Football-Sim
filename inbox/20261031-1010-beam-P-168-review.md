## New findings (not covered by GH or uk)

### 1. "+x WINS" — three possible metrics, brief is ambiguous
VL proposes `+x WINS` in the matchup card but does not define the conversion. Three candidates exist in the codebase:
- **(a) Point spread**: `Math.round(projH - projA)` — this is what VL/uk propose, but it relabels points as wins (GH's defect #1, verified).
- **(b) Win probability**: `wpFrom(mh, ma, HOME_FIELD)` → percentage, displayed as `+x%` not `+x WINS`.
- **(c) Season-equivalent wins**: `(projH - projA) / POINTS_PER_WIN` (32.5 pts/win) — but this is a per-game point difference divided by a season-level constant, which is misleading for a single game.
None of these naturally produces "+x WINS" for a single game. The P-168 brief needs a metric definition. I recommend the Architect decide between (b) win probability as "+x%" or (a) point spread relabeled as "+x pts" before implementation. Do not ship "+x WINS" with an undefined conversion.

### 2. "Strong/Weak Tight Ends" chip — model has no separate TE rating
The P-168 brief explicitly names "Strong Tight Ends" as a chip example. But `UNIT_INFO` has no TE unit — tight end is folded into `rec` (label: "Receivers & tight end", short: "receiving corps"). Two options:
- (a) Use "Strong Receiving Corps" (matches the `rec` unit) — consistent with the model.
- (b) Alias "Strong Tight Ends" → `rec` — but this mislabels a combined unit.
I recommend (a) unless the Architect decides the brief's example is the desired display label, in which case the chip maps to `rec` but displays "Tight Ends". Flag for Architect decision.

### 3. "Special Teams" chip — no corresponding unit
The `units` array in `matchupMathInner` is `['olRun','olPass','rb','qb','rec','passRush','frontRun','coverage','kicker']`. There is no "special teams" unit. The closest is `kicker`. A "Special Teams" chip would need to be derived from `kicker` only, which is incomplete. Recommend: use "Strong Kicker"/"Weak Kicker" or drop "Special Teams" from the vocabulary.

### 4. Chip mapping from swings is undefined
The current `matchupLines()` receives `sw.list` (top 3 swings by absolute point value, each with `ownerSide`, `unit`, `pts`). VL proposes replacing prose with chips but does not define:
- Threshold: how many points = "Strong" vs "Weak"? (All swings in `sw.list` have `|pts| >= 0.5`.)
- Direction: positive swing → "Strong <Unit>" for the owner, "Weak <Opposing Unit>" for the opponent? Or does each swing produce one chip?
- Count: top 3 swings → up to 3 chips? Or up to 6 (3 per team)?
The mapping needs a definition before the Architect can implement. Recommend: each swing produces one chip for the advantaged side (positive pts → "Strong <Unit short>", negative pts → "Weak <Unit short>"), with a threshold of `|pts| >= 1.0` for inclusion (filtering noise below 1 point).

### 7. `foil-shimmer` and `--team-primary` — both absent; fallback behavior
- `foil-shimmer` class: 0 occurrences in Pre-Colors (confirmed by grep). Depends on P-111/P-183.
- `--team-primary`: 0 occurrences in Pre-Colors (confirmed by grep). Depends on team theming (P-077/P-101/P-058).
VL's CSS proposals use `var(--team-primary, var(--accent))` and `var(--team-primary, var(--gold))`. These will silently fall back to `--accent` (blue) or `--gold` (#ffc43c). Given the Owner's "no blue panels" rule, falling back to `--accent` (blue) is non-compliant. Recommend: use `var(--gold, #d4af37)` as the fallback instead of `var(--accent)`, or define `--team-primary` first.
- `--gold` exists (line 217: `#ffc43c`) but the Owner's theme spec says "deeper gold for small text" in light mode. The existing `#ffc43c` is bright gold, which may fail contrast on white backgrounds. Note for the Architect's contrast audit (Q-V23-2).

### 8. `meetingTagText` empty return — omit `.mtag-sub` element
VL proposes returning `''` when no prior meeting. But `matchupTagHTML` (line 3538) always renders `<span class="mtag-sub">${riv?riv+'. ':''}${meetingTagText(g)}</span>`. An empty return leaves an empty span. GH already flagged this. Recommend: conditionally omit the `.mtag-sub` span when `meetingTagText(g)` is empty AND there is no rivalry text.

### 9. `recFull` shimmer — `foil-shimmer` dependency + string comparison
VL's proposed code compares `confRank==='1st'` (string). `ordinalN()` returns "1st", "2nd", etc. This works. But the shimmer span uses `class="foil-shimmer"` which doesn't exist. Also, `var(--team-primary, var(--gold))` falls back to `--gold` (#ffc43c). Recommend: either implement `foil-shimmer` first or use a simpler shimmer-free fallback (bold + gold color) until the class exists.

### 10. `renderIdentityPanel` — targeted change only
VL proposes `UNIT_INFO[u].short?.toUpperCase() || UNIT_INFO[u].label` for ALL units. This changes every unit row label to uppercase short form (e.g., "OFFENSIVE LINE (RUN BLOCKING)", "RUNNING BACKS", "RECEIVING CORPS"). The P-168 brief only asks for "RECEIVING CORPS". Recommend: change only the `rec` unit's display label, or add a `displayLabel` field to `UNIT_INFO` for the specific units that need uppercase. This avoids unintended changes to all scouting rows.
