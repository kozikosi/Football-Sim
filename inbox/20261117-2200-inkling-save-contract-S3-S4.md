## S3 — the context snapshot type: the contract and its checks

**S3-1. Determinism (the point of canonical JSON).** Same in-memory snapshot → identical bytes on any two devices and any two runs (keys sorted, no whitespace, no `undefined`, non-finite rejected, only plain-JSON values) — hash identical. **Check:** construct from a fixed fixture twice in the same process and on a second machine (or CI); `canonicalHash` equal; a one-bit change in any field flips the hash. (`core/hash.ts` `canonicalHash` already exists — VERIFIED in the tip; the snapshot consumes it, it does not re-invent it.)

**S3-2. Completeness (every field the consumers need, nothing else).** The snapshot carries **at minimum**: `season`, `week`, `form` (per player), `focus` (per team), `flags`, `packHash`, `engineVersion` — per the plan doc (REPORTED). **Check:** a typed-construction test asserting every listed field is present and non-optional for the GAME snapshot; the NEUTRAL snapshot (Wins) has form=0/no-focus by construction ("form 0, no focus, league-average opponent mix" — REPORTED from the plan doc); a missing field fails the test, not the build.

**S3-3. Hash is part of identity, not decoration.** A snapshot whose hash does not match its contents is **refused at consumption** (thrown/returned, named), never silently used. **Check:** flip one byte of the serialized snapshot → the consume path refuses with a named reason; the direct object path (in-memory) may trust the type system but the serial boundary never does.

**S3-4. Version coupling.** `engineVersion` and `packHash` are in the snapshot; a snapshot from another engine/pack version is refused at consumption (never mixed "best effort"). **Check:** `{...snap, packHash: 'x'}` → refused; `{...snap, engineVersion: 'old'}` → refused. (F5 ruling context — logged picks hold within a build; across builds, logged picks hold and unmade picks may differ — the stamp governs that knowingly, not silently.)

**S3-5. No ambient reads.** Construction and consumption never call `Math.random`, `Date.now()`, or module-level mutable state — the snapshot is the ONLY source. **Check:** the purity test class the repo already owns (core purity tests / `purity.test.ts` pattern) pointed at the snapshot module: build two snapshots around a seeded reseed and assert byte-equality. (INFERRED from the plan's §3.3 determinism requirement; named so the Architect knows the check's shape.)

**S3-6. The three-evaluation discipline holds.** Wins (neutral snapshot) never moves with focus/form; Priority (focus snapshot) moves only with focus; the game (week snapshot) moves weekly — the three differ only by those documented inputs, and the whole point (number agreement across screens) is verifiable: the same snapshot object through every selector produces agreeing values. **Check (report-only is acceptable at first):** for one team in week 3 of a fixture season, wins(row), wins(recap), wins(header) are equal integers. (REPORTED from the plan doc; the check is mine.)

## S4 — the additive async store: the contract and its checks

**S4-1. Additivity is literal.** The existing sync API's behavior is byte-identical after S4 lands: same writes, same bytes, same parse results, same `SAVE_KEY`/`sportKey` naming, same `saveTo`/`loadFrom` semantics — the async API wraps/extends; it does not re-derive or re-order what the sync API produced. **Check:** the pre-change test suite for the sync path passes INCLUDING byte-level fixtures (a saved blob before S4 restores identically after).

**S4-2. Refusal, never a crash.** Every failure mode reaches the app as a `ParseResult`-shaped value (`ok: false`, reason `corrupt` | `newer-version`, message naming the specific violation) or a thrown-named-error caught at the store boundary and mapped to `LOAD_FAILED{kind}` / `START`-rejection — never an uncaught exception, never a half-settled draft state. **Checks:** (i) truncated blob, (ii) wrong-type payload, (iii) `schemaVersion: SCHEMA_VERSION + 8` (newer), (iv) `schemaVersion: 0` (bad), (v) slot outside {A,B,C}, (vi) `saveRevision: 0`, (vii) `createdAt` unparseable — each yields a NAMED refusal, state untouched, UI receives the kind. (parseEnvelope covers most today — VERIFIED: lines 40–66; the contract is that S4's wrapper preserves and reports it exactly.)

**S4-3. Newer-version is a refusal, never an overwrite.** A save written by a newer build is never overwritten by this build — the store refuses to WRITE over it either (read-before-write or an equivalent guard). **Check:** seed the slot with a newer-schema blob → the store's write attempt is refused (or no-ops with a named reason), the newer bytes survive verbatim. (The envelope rule today is load-side only — "never overwrite it" is the envelope header's own words, VERIFIED; the write-side guard is the INFERRED extension this contract makes the S4 seam own.)

**S4-4. Atomic write / no torn saves.** A crash or throw at any point during a write leaves the PREVIOUS save intact, never a torn blob: validate-before-overwrite or write-temp-then-swap; storage-layer failures (setItem throws, quota, private mode) are contained. **Check:** fault-injecting `KeyValue` whose `setItem` throws on call N — assert the previously persisted bytes are unchanged and the error surfaces as a named failure, not a corrupt save.

**S4-5. Slot integrity end to end.** Every enveloped write carries `envelope.slot === slotOfKey(key)` (the F8 merge law; asserted at the storage module) — S4 keeps it. **Check:** a direct call to the S4 API with a mismatched (slot, key) pair is refused pre-write; N20-style assertion lives in the shell battery, the engine-side twin lives here.

**S4-6. Sequential consistency per slot.** Two S4 writes in rapid succession land last-writer-wins in call order; no interleaving, no lost update; the resolution order is defined in the API's contract comment. **Check:** dispatch write A then write B for slot C without awaiting either → final bytes parse as B; A's bytes are superseded wholly (not partially).

**S4-7. Idempotent round-trip.** serialize → parseEnvelope → (payload check) → serialize yields identical bytes (the savedAt stamp is the one legitimate difference — it may only advance, never fork the envelope). **Check:** byte-equality after re-serialization with the same `now`; `saveRevision` advances monotonically (≥ previous) across any number of round-trips including undo.

## The ways this contract gets claimed without being true (the failure modes, named)

- **The mock-store green** — the async API tested only against a Map-backed fake while the real localStorage module throws differently (quota, private mode). S4-2/S4-4 fix this by requiring fault-injection at the `KeyValue` boundary, not a happy-path fake.
- **The parse-bypass** — a restore path that JSON.parses without calling `parseEnvelope`/`parseRecord` (the envelope exists precisely so nobody does this; the newest save kind is only safe if the newest parse is mandatory). S3-3/S4-2 forbid it in code review; a grep for raw `JSON.parse` on the load path is part of the landing receipt.
- **The drift check that cannot fail** — a "snapshot hash matches" test that never computes the hash from the bytes. S3-1 demands both halves (byte-equality AND hash-of-bytes) on every run.
