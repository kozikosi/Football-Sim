## D1 — the mid-season resume is one reload deep (defect, shown)

**Evidence:** `probes/probe-gen-envelopes.mjs` builds the real pair (a done 1024-pick draft + a season two
weeks in) with the delivery's own `hydrateApp`; `probes/probe-two-reload.mjs` injects it into localStorage and
reloads three times:

```
boot1  hub=1 phase=running   keys=[autosave:draft]            hash #/hub
boot2  hub=0 complete=1 h1="Your draft is complete"           hash #/complete
boot3  hub=0 complete=1
```

**Root cause (code, not inference):** `loadDraft()` ends with `void clearAutosaveWeek()` unconditionally
("a slot load replaces the session"), and `hydrateBoot()` calls `loadDraft(...)` *before* it applies
`r.week`. Nothing on the resume path calls `autosaveSeasonNow()` — it runs on `beginSeason`, `playWeek`,
`restoreSeason` and `saveSeasonWeek` only (`App.svelte:122/147/178/217/234/250/264`). So the boot reads the
week, resumes it in memory, and destroys its save in the same tick. A user who closes the tab after a refresh
(before playing a week) comes back to Week 0's Complete screen and would restart the season with
`beginSeason`, overwriting the week autosave with `nextWeek=1`.

**Why every law is green:** N28 and S29 reload ONCE (and N28's assertion is partly source-text). The
transition matrix (§22.3, row 2) names "refresh mid-season → hub" — true for the first refresh only. This is
the absence-law lesson one level up: the law asserts the landing, not that the world survived it.

**Improved text (exact patch; applied + proven in a scratch copy, never to the delivered trees):**

WHERE `src/App.svelte` (both trees), three anchors:

1. `  function loadDraft(record: unknown, lineage?: { saveId?: string; createdAt?: string }) {`
   → `  function loadDraft(record: unknown, lineage?: { saveId?: string; createdAt?: string }, opts: { keepWeek?: boolean } = {}) {`

2. `    void clearAutosaveWeek();   // a slot load replaces the session; a stale season autosave dies with it`
   → `    if (!opts.keepWeek) void clearAutosaveWeek();   // a slot load replaces the session; a stale season autosave dies with it — but the BOOT path keeps the week it is about to resume`

3. `    if (r.draft) loadDraft(r.draft.record, r.draft.lineage);                   // the board + header + next pick return`
   → `    if (r.draft) loadDraft(r.draft.record, r.draft.lineage, { keepWeek: !!r.week });   // … the week this boot resumes must NOT be cleared`

HOW TO CHECK: rebuild (`npm run distfile`), serve, run `probes/probe-two-reload.mjs`; expected
`leg1_hub true · week_key_after_boot1 true · leg2_still_hub true · leg3_still_hub true · pageErrors []`
(I measured exactly that in the patched copy, R9).

**The law that would have caught it (add to `batteries/shell.battery.mjs`, S29 block, after the resumedHub
assertion):**

```
await page.reload(); await page.waitForTimeout(2000);
const weekKey = await page.evaluate(() => !!localStorage.getItem('sim:nfl:autosave:week'));
const stillHub = (await page.locator('.cp-hub[data-phase="running"], .cp-hub[data-phase="finished"]').count()) === 1;
ok('S29b a SECOND reload keeps the resumed season (the boot must not delete the week autosave)', stillHub && weekKey, `hub=${stillHub} weekKey=${weekKey}`);
```

A node-side twin is cheap too (`readAutosave` → run the boot composition → `readAutosave` again must still
return the week), but the browser law is the one that describes the user's promise.

## D2 — the method tooltip blocks the detail chips at phone width (defect, shown)

**Evidence:** `probes/probe-ds-hit.mjs` (390×844, touch) opens the first row and hit-tests the chip centre:

```
chip {x:89,y:457,w:97,h:25, centre (138,469)}   tip {x:99,y:451,w:262,h:101}
elementFromPoint(138,469) → SPAN.cp-gonetip  "GONE% — how often the CPU took him befor…"
```

The simple form at 390 is the same (`probes/probe-ds-hit-simple.mjs`): `"Draft at TE1"` centre (276,746) →
`SPAN.cp-gonetip`. At 1180 the identical probe returns `BUTTON.cp-chip.cp-primary`. Playwright's `tap` retries
to timeout and names the tooltip as the intercepting element.

**Mechanism:** the tooltip is shown by `.cp-gone-wrap:hover .cp-gonetip, .cp-main:focus .cp-gonetip`.
On a phone, tapping the row *focuses the row button* and *opens the detail* in one gesture — so the tooltip
appears exactly when the user wants the chips, is 262 px wide (67% of a 390 px viewport), right-anchored, and
sits over them. The late flip (10th pick) makes it worse: in simple mode the detail IS the only way to reach
a chip, and the simple row's chips start at the left edge, under the tooltip.

**Improved text (exact patch, `src/lib/components/BoardRow.svelte`, both trees):**

1. CSS: `.cp-gone-wrap:hover .cp-gonetip, .cp-main:focus .cp-gonetip { display: block; }`
   → `.cp-gone-wrap:hover .cp-gonetip { display: block; }`   (hover only; a tap must never raise it)
2. The tooltip span gains `aria-hidden="true"` (it is a mouse affordance; see D3) in both branches:
   `      <span class="cp-gonetip" role="tooltip">{method(oddsMeta)}</span>`
   → `      <span class="cp-gonetip" role="tooltip" aria-hidden="true">{method(oddsMeta)}</span>`
3. The method becomes an in-flow line of the detail (the way a phone reads it — no overlay): inside both
   `{#if open}` blocks, after the primary chip:
   `      <p class="cp-gonehow">{method(oddsMeta)}</p>`
4. CSS: `.cp-gonehow { flex-basis: 100%; margin: 2px 0 0; font-size: 0.72rem; line-height: 1.4; color: #c8a48f; }`

HOW TO CHECK: at 390, open a row; `document.elementFromPoint` at the primary chip's centre must return the
chip button, and the detail must contain `.cp-gonehow` with the method text. (Expected: chips=1, hit=BUTTON,
`cp-gonehow` present; I verified the mechanism of the failure, not this patch's output — the patch is a
proposal, 25 lines, no engine contact.)

**The law that would have caught it (late battery, L7 extension):**

```
const hit = await page.evaluate(() => {
  const c = document.querySelector('[data-testid="cp-simple-detail"] .cp-chip.cp-primary');
  const b = c.getBoundingClientRect(); const el = document.elementFromPoint(b.x + b.width / 2, b.y + b.height / 2);
  return { chip: c.textContent.trim(), hit: el?.className || el?.tagName };
});
ok('L7b at 390 the detail chip is the element under the finger (no overlay swallows the tap)', hit.hit.includes('cp-chip'), JSON.stringify(hit));
```

(Assert "the hit element is the chip or a descendant", not a class string, in the real law — the class name is
minified in the dist. `L7b` needs one viewport resize to 390 inside L7's block.)

## D3 — the tooltip is inside the row button (defect, a11y; cheap)

`<button class="cp-main" …><span class="cp-name">…</span> … <span class="cp-gonetip" role="tooltip">GONE% —
how often …</span></button>`. A button's accessible name is the concatenation of its descendants, so a screen
reader announces the two-sentence method **on every row**. R11. Fix: `aria-hidden="true"` on the span (D2
patch step 2) and, if the method must be announced, `aria-describedby` on the gone cell pointing at a hidden
copy — not on the row button.

Also: the simple row's sort caption is `title` + `aria-label` on a plain `<span>`; `aria-label` on a generic
role is not reliably exposed. Use a visually-hidden text node (`.cp-sr`) inside the number's span instead.

1. **The full board's numbers are unlabelled.** OVR, wins and priority render as three right-aligned numbers

   76 Pancakes (AGENTS.md §2); the track label belongs in the dev overlay.
4. **The flip at the 10th of 32 picks.** The doc flags the overall-320 reading; for a 32-team league the two

   still has 22 picks to make, and it removes the advice panel with one line of prose. See the ideas filing

## The weakest point of the work

The battery is excellent at proving what it *looks at* and blind to what the user does next: both defects live
one gesture past the last assertion (a second reload; a tap on a chip at phone width). The round already learned
this lesson once (L9's false green) and stopped there. The missing discipline is a *budget*: every new
user-facing control gets one law that operates it at 390 px, and every resume path gets a law that reloads
twice. Both are three lines each; both are the difference between "the detail is there" and "the detail works".
