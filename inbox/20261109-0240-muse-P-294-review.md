### 3. Theta discrepancy reconciliation — VL and Super are both partly right; verdict: BLOCKED

VL's review says theta pricing is BLOCKED (no ovrEq on the architect branch — flexeval.mjs counts placements, it does not price theta). Super's review says theta pricing is DONE (he computed a grid using his own flex-pricer tool on council/super, defining ovrEq = winsLost / slotWinsPerOvr(dest), after fixing a lookup bug `slope[dest]` → `slope[flexSlot]`). I verified both claims independently.

**(a) Super's tool and the line-117 fix — VERIFIED.** Read `tools/mathlab/flex-pricer.mjs` on council/super @ c9566494. The ovrEq definition is `winsLost = max(0, slotWins(natural, ovr) − slotWins(flexSlot, ovr))` and `ovrEq = winsLost / slope[flexSlot]` where `slope = slotWinsPerOvr()`. The line-117 fix is VERIFIED present (the parent commit has `slope[dest]`, c9566494 changed exactly that line to `slope[flexSlot]`). The fix is correct: I confirmed in the Pre-Colors engine that `slotWinsPerOvr()` is keyed by concrete slot ids (WR1, DE1, …), while `dest` can be a family key (WR, EDGE, …) — so `slope[dest]` returns undefined (ovrEq null) for every family-dest rule, and `slope[flexSlot]` (via the FAMILY_SLOT mapping to a concrete slot) is the right lookup.

**(b) Super's grid reproduces exactly — VERIFIED.** Command, run from a scratch tree of council/super @ c9566494 (product hash pinned 40233d6be00e987c before/after, exit 0): `node tools/mathlab/flex-pricer.mjs`. My re-run vs Super's committed `results/flex-pricer-2026-11-08T23-43.json`: same 84-rule set, same summary (10 underpriced / 69 overpriced / 5 aligned), 0 cell diffs at @85/@90 across all rules. Representative cells all match (CB→WR ovrEq@85 1.37, @90 2.40; WR→TE 1.98 / 4.14; EDGE→MIKE 2.54 / 5.10; CB→MIKE 3.31 / 6.54; CB→RB 5.28 / 9.24; →SAM ovrEq@85 49.53–91.31, @90 100.18–180.57).

Two corrections to Super's prose (the underlying numbers are right):
- "theta all clamped at 30" for →SAM is not accurate at θ=0.5, OVR 85. Four of the seven SAM rules give 24.77–29.25 at θ=0.5 @85 (TE→SAM 24.77, FS→SAM 26.15, SS→SAM 27.15, DT→SAM 29.25 — below the clamp); only REDG/LEDG/CB→SAM clamp at θ=0.5 @85. All SAM rules do clamp at θ=0.75/1.0 @85 and at all θ @90.
- "most OL/DL/DB→slot rules ovrEq@85 0–0.98" holds for OL+DT (8/9 within) and SS/FS (13/14 within), but the EDGE/CB cross-unit rules exceed it (up to 5.28 @85 / 9.24 @90). Loose, not wrong in the majority sense (21/39 within at @85).
- One apparent 0.01 diff (WR→TE @90, θ=0.75: Super 3.10 vs 3.11 from the rounded 4.14) resolves in Super's favour: the raw ovrEq is 4.13828, so 0.75×4.13828 = 3.10.

**(c) Is Super's ovrEq definition sound? — YES, as a first-order conversion.** The penalty P is subtracted from OVR at the destination (`effOvr`), so the cost must be expressed in destination-slot OVR points. Dividing wins lost by the destination slot's wins-per-OVR slope does exactly that: `X · slope[dest] = winsLost` ⇒ `X = winsLost / slope[dest]`. The slope is the 70–90 secant (`(slotWins(90)−slotWins(70))/20`), a linear approximation — acceptable for the theta formula's purpose. Caveats, all noted rather than fatal: (i) it ignores the displaced player (single-player, all-else-80 measurement; the full T6 paired-seed re-optimization is blocked on the injectable RNG, as Super himself flags); (ii) low-slope destinations produce extreme ovrEq — SAM's slope is tiny, so any wins lost converts to 49–181 OVR points and the theta clamp at 30 does the work there; (iii) `max(0, …)` prices win-gaining flexes at 0, consistent with P clamped [0, 30]. The definition is also consistent with the formula's own description ("wins lost, converted to OVR-equivalent").

**(d) Coverage gap — VERIFIED: the four proposed rules are NOT in the grid.** `RB→WR`, `TE→EDGE`, `TE→OT`, `DT→EDGE` are all absent from Super's 84-rule grid (checked by lookup). They are not in REV 4's product FLEX, so the pricer — which iterates REV 4 rules — never prices them. These are precisely the rules the −12 decision turns on.

**Verdict on theta pricing: BLOCKED, not DONE.** Super's grid is verified evidence and his ovrEq definition is sound — but the pricing as a council deliverable is not DONE, for three reasons:
1. **The definition is unconfirmed.** It was invented by a council seat, not by the formula's author (Z.ai/Owner) or the Architect. Claude's write-up §1 says he "will not invent it" and will price theta once the formula is sent; the formula as sent never defines ovrEq. A council seat inventing the definition does not make it the Architect's pricing.
2. **The grid doesn't cover the rules that matter.** The four proposed rules (RB→WR, TE→EDGE, TE→OT, DT→EDGE) are absent, so no θ pick can be made from this grid for the actual flex decision.
3. **It's measured against the wrong engine.** The pricer runs against Pre-Colors (the old single-file product), not the Colors engine on the architect branch. The Colors engine has `slotWins` and `slotWins20` (`slotWins20/20` = the same slope), but no `slotWinsPerOvr()` function — the Architect would need to add it or use `slotWins20/20`.

So VL's "BLOCKED" is correct as a status, and Super's grid is the verified method that unblocks the path.
