REVIEW-OF: 20261031-1036-uk-P-201-player-pool-plan.md
VERDICT: rejected

The plan correctly identifies the need to check TE supply before a larger draft, but it mixes the pinned Pre-Colors build, the proposed 32-slot V23 table, and other build constants. It also treats the incoming 50-OVR data as already known; the Owner's file has not been supplied.

- **[VERIFIED] Current pool differs from the stated baseline:** parsing the pinned `PLAYERS` array gives 1,200 players, OVR 70–99, 151 WR and 53 TE. The proposal says the current range is 50–99 and uses ~142 WR/~51 TE. The latter counts appear in the older math spec, but do not match the pinned file. Counts for the future Owner-supplied pool are **UNKNOWN** until that file arrives.
- **[VERIFIED] Draft length/slot list is inconsistent:** Pre-Colors has 26 `ROSTER_SLOTS` and 26 rounds. The math spec's planned count is 26 + FB/P/DIME = 29, then DL5 = 30, then TE3/WR4 = 32. The proposal's “now 29 with DL5” is off by one; its proposed LB4, CB4, SS2 and FS2 are not in the 32-slot spec, while it omits FB and DIME.
- **[VERIFIED] Supply table is therefore not a valid 32-slot check:** for the stated planned table, the per-team slot needs are QB 1, RB 2, FB 1, WR 4, TE 3, OL 5, DL 5, LB 3, DB 6 (including the DIME slot), K 1 and P 1: 32 × 32 = 1,024 slots. DIME is not a player position, and DL5 can be filled by DT/EDGE; check eligible candidates using the actual flex rules rather than counting DIME or DL5 as standalone tags. The future pool still needs a CSV-aware, per-tag eligibility check.
- **[VERIFIED] CPU floor terminology is wrong:** the pinned `cpuPick` uses a round `ovrFloor` of 90 in round 1, 85 in rounds 2–3, then no floor. Separately, its replacement baseline is `Math.max(repl[g] ?? 70, 76)`. The proposal conflates these and cites an `ovrFloor` value of 3 from another build.
- **[VERIFIED] Several listed constants are not pinned-build values:** Pre-Colors has `RUSH_BASE=105`, `PASS_BASE=220`, `PT_TO=3.0`, `PT_SACK=0.8`, `LAM_TO=1.2`, and `LAM_SACK=2.2`; the proposal's values differ. `MC` is the protected coefficient object, not “4000 Monte Carlo trials.” `DEFAULT_WEIGHTS` has 34 keys in this file while `ROSTER_SLOTS` has 26, so calling it a 32-slot table is not an accurate description of the pinned build.
- **[VERIFIED] The proposed re-measurement sequence does not follow the tools:** `slotWinsPerOvr()` is a deterministic 70→90 finite difference from `slotWins`, not Monte Carlo sampling over `PLAYERS`. `fitlm.js` fits the configured engine targets; `run-all.sh` checks a stored fit and does not run `fitlm`, `after.js`, `defaggr.js`, or `postures.js`. `realcheck.js` does use `PLAYERS` to assemble team rosters, so it is pool-sensitive. The plan needs to distinguish supply/draft/replacement-level checks from engine refitting and avoid refitting protected constants merely because the data file changes.
- **[VERIFIED] The cited “ENGINE-MATH-SPEC C8.2 quote” is not a section in the current spec.** The only `C8.2` occurrence is a parenthetical reference in §12.6; there is no C8.2 checklist or quoted passage. That section does say to rerun `run-all.sh` and `realcheck` after lower-rated players arrive, but it does not support the proposal's full list of constants or ordering.
- **[RISK] The proposed remedies “allow WR→TE flex more aggressively” and “reduce TE slots” are not data-intake decisions.** Flex is protected and changing it requires the Owner's specific approval; changing the roster is a product decision. Keep both as unresolved Owner choices, not automatic mitigations.
