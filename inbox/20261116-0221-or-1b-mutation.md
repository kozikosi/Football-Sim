## A.6 — The two de-gated tests

The commit de-gated two tests that were previously failing (red) and rewrote them as structural assertions:

### (a) `lineup.test.ts` — "base: totals are not comparable" (line 240)

**Old (pre-1b):** asserted the 4-3 vs 3-4 gap as a hard-coded `2400` (pinned 9 Nov), then REPORTED it as 2700 on every run.
**New (1b):** asserts the *accounting identity*:
```
gap = 70 * (sum of 4-3 spot values - sum of 3-4 spot values) + sum over flexed spots of (spot value * flex price)
```
and that `flexCost > 0` (so dropping flex cost changes the answer).

**VERIFIED live assertion, not a tautology.** To break it:
- Set a flex penalty to 0 in the 3-4 lineup (e.g. make `TE3` natural for FB, or make `DT2` natural for the ILB) → `flexCost` becomes 0 → `flexCost > 0` fails. The solver currently charges 6 at three spots (`MIKE`/`DT2`, `TE3`, and one cheap slot); zeroing any one makes the identity collapse.
- Make the solver leave an empty 3-4 spot (`l34.placements` has a `p.player === undefined`) → `l34.placements.every((p) => p.player)` fails.
- Reorder the spot values so `sum(u43) - sum(u34)` is negative while the gap is positive → the identity `gap - (70*(diff) + flexCost)` diverges.

The test is a *structural* gate: it pins the accounting, not a weight. It fails if the solver mis-accounts (empty spot, price not charged, stand-in counted twice). The `REPORT` line still prints the gap (2773.0387) so the number is visible without being pinned. **This is the correct fix for the Owner's "no weight pinning" ruling** — the gap can move (provider, flex table, third stand-in all change it) without breaking the gate.

### (b) `versions.test.ts` — "E5 stamps" (line 16)

**Old (pre-1b):** compared `engineVersion()` to a hard-coded `PIN_ENGINE = 'nfl1.108bcc20a9f253'`; the comment said "DE-GATED 13 Nov (no weight pinning; the stamp is provenance, not law)"; the stamp was only REPORTED, never gated.
**New (1b):** asserts the stamp *properties*:
- shape `/^nfl1\.[0-9a-f]{14}$/`;
- deterministic (`engineVersion()` called twice gives the same value);
- `eng === 'nfl1.' + hash53(text)` — the stamp is exactly the label plus the hash of the rules text;
- `hash53(text + ' ')` ≠ `hash53(text)` and `hash53(text.replace('"QB"', '"QX"'))` ≠ `hash53(text)` — one character or one renamed position changes the stamp;
- `drift({ ...cur, engineVersion: 'nfl1.00000000000000' }, cur)` → `{ engine: true, data: false, any: true }` — a save from a different engine is flagged.

**VERIFIED live assertion, not a tautology.** To break it:
- Change `engineVersion()` to return a constant → `eng === 'nfl1.' + hash53(text)` fails (the stamp is not the hash).
- Change the rules text (add a character) → `hash53(text + ' ')` ≠ `hash53(text)` still holds, but `eng` no longer equals `hash53(text)` because the rules moved → the "stamp is exactly the hash" assertion fails. This is the correct behaviour: a rules change *should* move the stamp, and the test catches a stamp that doesn't track the text.
- The data stamp (`PIN_DATA`) stays a pinned value on purpose: a ratings file that changes silently would change every save's dataVersion. That one is a deliberate-change signal, not a rules table.

**This is the correct fix for the "no weight pinning" ruling**: the engine stamp's *value* is no longer pinned (it moves with the rules), but its *properties* (shape, determinism, change-sensitivity, drift detection) are gated. A stamp that stops tracking the text fails; a stamp that moves because the rules moved is fine.
