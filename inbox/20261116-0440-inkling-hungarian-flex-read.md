## H1. The Hungarian — what it is, exactly
- `hungarian()` (colors/src/core/hungarian.ts, 37 lines) is the textbook e-maxx / cp-algorithms assignment algorithm — row potentials `u`, column potentials `v`, alternating-path maintenance via `minv`/`way`, `p[j]` = matched row of column j (1-based). Not a greedy approximation; it finds a provably min-cost assignment of its MODEL (additive, per-slot costs, one cell per (row, spot) pair, Hungarian is exact for that). VERIFIED by reading + the suite (below).
- **O(n³)**: outer loop n iterations; the inner `do…while (p[j0] !== 0)` loop runs at most n+1 times per i (one augmentation per iteration, each strictly expanding the explored set); the j-scan is n each ⇒ O(n³) time, O(n) extra space beyond the matrix. Arithmetic holds. (No test asserts the complexity, only n≤7 correctness.) INFERRED (code reading), not benchmarked.
- **Square-only**: `for (const row of cost) if (row.length !== n) throw new Error('hungarian: matrix must be square')` — non-square rejected loudly; `hungarian([[1, 2]])` throws (test at lineup.test.ts:113 asserts this). VERIFIED (read + the test ran green in my suite run).
- **Deterministic ties, by index order**: strict `<` in `if (cur < minv[j])` and `if (minv[j] < delta)` ⇒ among equal minima the lowest column index wins; `way[j]` only updates on strict improvement ⇒ the first j0 producing it wins the tie. Same matrix ⇒ same assignment, on any IEEE 754 device for the same inputs (basic +, −, × are exactly rounded/deterministic). INFERRED cross-device (not run on a second machine); same-machine determinism is by construction.
- **Brute-force check**: lineup.test.ts:103 — "hungarian: equals brute force on 300 random matrices of size 1..7 (with ties and negatives)": 300 matrices (sizes 1..7, entries in [-20, 20]), each checked for (a) the returned array is a permutation and (b) its cost equals the exhaustive-permutation minimum (`brute(c)` enumerates all n! assignments). Plus "exact against brute force on a tiny custom spot list" (L187, lineup-level, players↔spots). The suite passes 363/363 in my run, so both are green. VERIFIED (read + suite run).

## H2. How to make it wrong that the 300-matrix test does NOT catch
1. **NaN / ±Infinity in a cost cell — silent, plausible, wrong answer.** VERIFIED: `hungarian([[NaN, 1], [2, 3]])` returns `[1, 0]` with no throw and no signal. The `NaN < INF` comparisons are all false, so `delta`/`minv` evolve as if the cell were +INF; a NaN cell becomes invisible to the search instead of a loud error. The engine's ILLEGAL price is finite (1e12 today; the derived ladder would be ~8.5e11), so no current path emits non-finite cells — but a future overflow or a hand-edited cost grid poisons the assignment for free. The fix belongs at the API boundary (`if (!Number.isFinite(c)) throw`), not inside Hungarian. The existing test (integer costs in [-20, 20]) can never see this class.
2. **A sign error at the CALLER.** The algorithm is exactly what its matrix says it is; "max value" lives entirely in lineup.ts (`row[j] = -(PLAYS + v*effOvr) + …`). Flip the sign and hungarian returns the exact min-cost assignment OF THE WRONG PROBLEM, still a permutation, still internally "exact" — the 300-matrix test stays green, the lineup becomes garbage. The test guards the algorithm; it does not guard the encoding. (The lineup-level anchor — the natural full roster must place every player at zero flex — catches this class indirectly; it is that anchor's job, not the matrix test's.)
3. **Everything above n = 7.** The brute force is exponential; it only ever stress-tests small matrices. The real grid is 64×64 (32 players + 32 fillers; 32 spots + 32 bench). Correctness at 64×64 rests on the algorithm's proof plus 1–7 stress — never on comparison against an independent solver at scale. A defect that only manifests at larger n (e.g., potentials `u`/`v` drifting into float territory where `INF = POSITIVE_INFINITY` arithmetic behaves differently near 2^53 — minv[j] -= delta is fine while minv = INF; more delicate: u/v grow to ~1e12, no precision hazard below 2^53) is INFERRED-safe, but never tested, at any size the engine actually runs.
4. **A different-but-equally-valid tie path.** If Hungarian returned a DIFFERENT optimum among those of equal cost, the test stays green by design (it asserts a permutation + min cost, not WHICH permutation). Determinism is by construction (strict `<`) but is NOT a test property — no test runs the same matrix twice and deep-equals the result, and no cross-device equality is possible to guarantee beyond IEEE basic ops. So "the tie order changed after a cosmetic code reshuffle" would be silent: lawful assignments, moving lineup cells, no gate tripped. (The 3-4 third stand-in already moved across table versions for exactly this reason; noted, not re-litigated.)
5. **Ragged input of equal length but wrong content — i.e., wrong row/col roles.** Squareness is enforced; semantics are not: a caller transposing the matrix gets an assignment of the transposed problem (a bijection — the total cost optimum is the same SET for square problems; the returned matrix is transposed as a consequence only if the caller misuses the output's meaning). For square problems Hungarian is invariant under transposition in OPTIMUM VALUE, so this is silent correctness the caller can't feel; but any future rectangular use breaks the contract — currently rejected loudly, which is the right behavior. (Moving off square for efficiency would silently break everything; keep it square.)
6. **Informative only, not a defect:** the algorithm knows nothing of interactions — two players across spots cannot "cost extra together". The table is priced per cell; the solver is exact about a model that is not. Any wrong table, exact solver.
