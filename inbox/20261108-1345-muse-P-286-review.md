## 2. The snapshot bug — NOT VERIFIED (the claim does not hold up; the most significant finding)

**The corrupted line does NOT exist in the pinned commit.** `grep -rn "DESTain"` across the extracted pinned `colors/src/` returns **no matches** (exit 1). The full 66-line `draftBoard.ts` at `4ca9a071` was read. The actual line 49 is:
`natural: fit(p.role, DEST[main.slot]).penalty === 0,`
— the CORRECT line. Lines 41 and 45 use the correct `DEST[c.slot]` form. There is no mangled `DEST[c.slot]` anywhere in the file.

**The snapshot's copy is equally clean.** The snapshot `src/engine/sports/nfl/view/draftBoard.ts` is byte-identical to the pinned file (item 1's clean diff), so it is also uncorrupted.

**The snapshot DOES compile.** The vite build succeeded, and the engine tests that import the snapshot's `draftBoard.ts` pass (item 3). The string `DESTain.slot]` contains an unmatched `]` — a syntax error — so if it were present, neither the build nor the tests could run. The README's claim "No build can compile it" is **false**.

**The stand-in exists and is clearly headed** (`src/lib/view/boardVM.ts`, header: "WHY A COPY … stands in until a re-pin"). **But it is NOT "the SAME view model, line-for-line, with the line repaired."** The diff against the pinned file shows real differences beyond the header and import paths:
- The function is renamed `boardVMFallback` (not `boardVM`).
- The odds parameter is nullable (`GoneOdds | null`) with null handling (`g = odds ? goneChance(odds, p.id) : 0`); the pinned file takes non-null `GoneOdds` and calls `goneChance(odds, p.id)` directly. This is a behavioral difference (gone = 0 when odds is null, which changes the priority calculation).
- `BoardSort` is imported from `appstate.ts` (and re-exported) instead of defined locally.
- Two comments are dropped (the "Owner 30 Oct" flex comment and the "primary spot" comment).

**Everything the slice renders DOES flow through the stand-in — VERIFIED.** `App.svelte` line 15 imports `boardVMFallback` from `./lib/view/boardVM.ts` and line 64 calls it. The components import types from `../view/boardVM.ts`. The app never imports `selectors.ts` (which would use the snapshot's `boardVM`). The snapshot's `draftBoard.ts` is **not in the built bundle** (grep for `DEST[main.slot]` / `DEST[c.slot]` in `dist/assets/*.js` returns 0). So the rendering flows through the stand-in, and the snapshot's `draftBoard.ts` is dead code in the built app (exercised only by the engine tests, which pass).

**Conclusion:** the stand-in is a well-built, clearly labelled file, and the slice works through it — but its justification (a corrupted snapshot line) is false. The re-pin Z.ai requests is **not needed for this reason**. The Architect needs to confirm whether a corrupted line exists anywhere else, or whether this was a misread/mistranscription. The slice should either drop the stand-in and use the snapshot's `draftBoard.ts` directly, or the stand-in should be justified on a real basis.
