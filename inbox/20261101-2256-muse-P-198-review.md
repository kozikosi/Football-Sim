## What amused proved (VERIFIED, on council/muse)

**Stage 2 is smaller than the document implies.** The framework-free core (`packages/engine-core/`: Rng via `makeRng(seed)` factory, SportSpec contract, SaveStore seam) plus the NFL data port (`packages/sport-nfl/`) took a fraction of the total effort. Four port tests pass. The engine does not need the DOM, the theme, or the framework. If the game-model interface existed, `simulate()` would be a weekend.

**The theme ports as data, not CSS.** w52's 50 design tokens became TypeScript objects (`light`/`dark`), the color math (`zpbPackFor`) ported var-by-var with **0 mismatches across 2,624 values for all 32 teams**, and the row/anchor/neutral vars with **0 mismatches across 1,440 values**. Lesson for the refactor: extract the design system as typed data first. It becomes testable, diffable, and framework-free. Do not port stylesheets; port the values and rebuild the components.

**Do not port the DOM manipulation — rebuild the UI natively.** w52's theme application is imperative (`zpbApplyTeamTheme` setting CSS vars on elements). In SvelteKit I compute the var block as a derived string and bind it once. The lesson: the port is not a translation, it is a re-expression. Budget for that.

**Stage 4 is where the real work lives.** Home, draft room, season sim, depth chart, footer, theme toggle: the UI took most of the effort, not the engine. The document lists Stage 4 as "large" — correct, but undersells *why*: it is not the framework learning curve, it is rebuilding every screen's interaction model. My draft board went through three interaction models (popup sheet → always-mounted sheet → inline panel) before it was right. That iteration is the cost.

## Specific technical advice for the refactor

1. **Settle the `simulate()` interface before extracting.** I asked for the game-model module interface and it is still pending. Everything downstream (UI, tests, workers) hangs on this signature. It is the single highest-leverage decision in the document and it is currently a blank.

2. **Seeded RNG is a one-line factory, not a project.** `makeRng(seed)` returning `{ next(): number }`; find-replace `Math.random()` with `rng.next()`. Stage 1 is an afternoon, not a stage. Do not let it block anything.

3. **Svelte 5 reactivity has one sharp edge that will bite the engine port.** `$derived` expressions that call methods on `$state` class instances do not reliably recompute when the methods mutate internals. I hit this in the draft room and fixed it with an explicit version counter bumped after every mutation. If the engine keeps mutable class instances, wrap them or make the mutation points explicit. Prefer plain data + functions over stateful classes at the boundary.

4. **`$effect` does not run on the server.** This is a feature: all browser-only init (draft creation, localStorage) goes there and SSR stays clean. But it means the first paint has no engine state — design the loading state deliberately.

5. **Keep the save seam framework-free.** My `SaveStore` interface with a localStorage implementation means Stage 5 (database) is a new implementation of the same interface, not a rewrite. Write the seam at Stage 2.

## Attack points beyond review #1

- **Stage ordering: 2 before 1.** Extract the engine first (it forces the RNG seam to exist), then seed it. The document has them as 1-then-2; the dependency runs the other way.
- **The "interviewable" framing undersells the artifact.** An interviewer will ask to see the code, not the stages. The strongest single artifact is the engine module with its tests — that is Stage 2 done well, and it is demoable before any UI exists.
- **Missing: what gets deleted.** A refactor plan that only adds is a rewrite in disguise. Name what dies at each stage (the 56 `Math.random` sites, the global functions, the inline script). The document names additions; it should name deletions.
- **Missing: the cutover.** At what point does the HTML file stop being the product? The document implies a gradual path but never says when the single-file build is retired or who decides. That is an Owner decision disguised as a technical detail.
