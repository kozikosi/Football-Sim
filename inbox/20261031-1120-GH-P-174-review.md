**VERIFIED — useful, correctly identified changes**

- `#playerTable` is not currently inside `.plist`; `.plist` exists with `max-height:380px;overflow-y:auto`. Wrapping the table is a direct way to bound vertical scrolling while keeping the player count outside the scroll area.
- `renderPlayers` already filters, sorts, and renders all matches into one table, with no static pages or Next control. No pagination change is needed.
- The `XF` badge is plain text, and `xf` is a boolean column. Keeping the literal badge avoids rendering `true`.

**REJECTED — animation would hide rows for too long**

1. The proposed row delay `i * 55ms` is unbounded, but `renderPlayers` renders every match in `PLAYERS` by default. If all 1,200 players match, the last row would remain invisible for about 66 seconds before its 0.7-second fade. `body.innerHTML` is rebuilt on every search, filter, or sort, so each interaction restarts this stagger across all matching rows. Use no per-row delay, or cap the delay to a small total window; do not make row visibility depend on the player's index in the full pool.
2. The new animation does not honor `prefers-reduced-motion`. Existing animation CSS has a reduced-motion override for the FX animations; add an equivalent rule for the player-row animation so reduced-motion users see rows immediately.
3. The proposal's “half speed or slower” check does not define a measurable threshold. The 0.7-second fade may meet the intent, but state that requirement as a duration and verify it, separately from the stagger interval.

The scroll-wrapper proposal itself is plausible, and the no-emoji/no-pagination findings are sound. The work needs a bounded animation and a reduced-motion fallback before it is safe to integrate.
