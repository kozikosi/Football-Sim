## 0. The one implication that changes the cutover conversation
The T2 claims protocol (`claims.json` + `scripts/check-claims.mjs`) is the first time this project has a *machine-checkable* definition of "verified" — a 2026-11-23 verifier RED that was really a stdout-format mismatch can no longer be resolved by a prose paragraph. That is more transferable than any of the code fixes: **lift the claim set into Claude's Colors v1 cutover gate**, so "verified" means a command's exit code, not a reviewer's mood. My review this sitting shows the limit too: the prose state block overclaimed (N1/N2) while the full claim set was RED. So the rule is two-part: (a) machine-check every claim, (b) generate the human-readable state block *from the claim set*, so green prose and RED gates cannot coexist.

## Ranked ideas for cakepanz / the shell (all shell-side, engine stays frozen at 408410477)

1. **Fingerprint every generated artifact's inputs (close the hole I found).** `SHELL-STATUS.md` hashes the dist bytes but not the `ACCEPTANCE-RECEIPTS.txt` it reads; when the receipts were rewritten mid-sitting, the status kept saying COMPLETE. Generalise: a single `freshness.json` mapping `generated-file → sha256(each input it reads)`, checked at packaging. Concretely: add `acceptanceSha` to SHELL-STATUS and a claim that it equals sha256(ACCEPTANCE-RECEIPTS.txt). This is the mature form of my earlier "generated-artifact freshness gate" (0305-B) — this sitting supplied the missing counterexample that proves why it matters.

2. **Seal the meta layer with an attestation, not by listing it.** The receipt of record is excluded from the seal for a good reason (a final-state receipt cannot survive a regen roundtrip), which leaves the biggest claim tamper-evidence-free. Have the acceptance script emit `receipt-attestation.json`: `{log_sha256, per_step_exit_codes, tree_sha_start, tree_sha_end, command}`. Seal that tiny file; keep the growing log unsealed. The gate verifies the log's sha against the attestation. Cost near zero; closes N3.

3. **Generate prose from claims.** The README "STATE OF RECORD" block and `ZAI.md` are hand-written while `claims.json` is machine-checked — that is why "receipt refreshed" could be printed over a still-23/23 log. Make the state block a template rendered from the claim results (one line per claim: OK/RED + its command). Then a reviewer can read prose *as* the gate output, and the two cannot drift. This also makes a fresh Verifier's job a single command.

4. **A `statusVM` single source for the shell.** `src/App.svelte` holds ~14 independent `$state` flags (`screen`, `error`, `busy`, `shareNotice`, `savedSuggest`, `feed`, `dataVersion`, `seedPinned`, season stats, …) and the top bar / hub / Complete screen each derive their own status. Introduce one derived `statusVM = {phase, label, tone, action, why}` and have every surface read it, with DOM hooks derived from its `phase` name. This is simultaneously a UX fix (one status everywhere, no contradictory "done"/"in progress") and the antidote to the six-site selector drift I have filed twice.

5. **Turn side-by-side into the Owner's parity release gate.** The fixed capture contract now yields 41 non-vacuous scene captures with 0 fallbacks — that is a semantic visual-regression harness, not just screenshots. Add a one-page static HTML board: per scene, LEFT (w89 reference) / RIGHT (cakepanz) / a token-diff column (palette, spacing, type, the exact `--glow`/gold token), with a machine verdict. The Owner's standing ruling — "directionally similar is a FAIL" — becomes a checkable comparison. Make "no fallback captures" and "no new token holes" hard gates on every future shell edit.

6. **Kill the last display-number parse with a law.** `port/suggestWhy.ts` still parses display strings (`Number(String(x[sort]).replace(/[^0-9.\-]/g,''))`) for the INTERIM tie extension, explicitly awaiting an engine `rawSort`. Already filed as a §5 proposal to Claude; my addition: once `rawSort` lands, add a grep-law to the node battery that fails if any shell file parses a numeric value out of a display string, and present the genuine tie as a distinct "all tied" state (keeping the display-rounded caveat). The falsifier discipline applied to UI code.

7. **Spatial badge field as a view of `placements`, not new data.** The Owner's pfd-01 north star (field of badges, no faces) can be built shell-only: `optimalLineup` already returns `placements` with `row`/`slot`/`effOvr`, and `teamColors` + the gold higher-OVR marker already exist. Add the contrast + reduced-motion gate at the same time (the shell already has reduced-motion shots). Post-v1.1, P3, no scouting/GM/faces.

The engine already owns plan vocabulary and `plans.ts`; the shell only presents it. Version the "why" reason shape (`{kind, text, value, source}`) so a new engine law does not break old cards — my earlier "versioned why-reason shape" idea, now with a concrete consumer.

9. **Seed-free brag as a hard law.** Regardless of the account/API ruling, the Share screen's copy-paste brag must carry no `?seed=`, no `b36:` code, no full save envelope.
