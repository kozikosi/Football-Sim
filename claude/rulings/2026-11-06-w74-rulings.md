## F1 — which AppState is law: `appstate.ts`. RULED.
VERIFIED finding: the two pairs differ in more than names. `store.ts` is the implemented, tested draft reducer (`record`, a live `DraftState`, `status`, `error`; actions START/PICK/UNDO/LOAD). `appstate.ts` is the types-only app contract (boot, identity, dataset, slot, phase, `draft: DraftPayload`, season, plan, ui). Nothing imported `appstate.ts`; `selectors.ts` imported the store's shape. So "delete the duplicate" would have deleted working code.
Ruling: `appstate.ts` is the only module that exports `AppState`/`Action`. `store.ts`'s pair is renamed `DraftStoreState`/`DraftStoreAction` (Z.ai's draft; type-only, no behaviour change). Layer rule: the draft store is the draft engine's runtime; its `draft: DraftState` is a memo of `restoreDraft(record)` and is NOT part of the contract (the contract's `draft` is the payload). The root reducer (next slice) delegates draft actions to the draft store and keeps `AppState.draft` = the store's `record`.

## Envelope — the Owner's three questions (answers; the Owner can overrule)
1. saveId/createdAt now, not v1.1. Nothing has shipped, so adding them costs nothing; adding a required field after saves exist costs a migration of every save (or makes old saves "corrupt"). Z.ai's own w71 §E wants a lineage uuid minted per new season: that IS `saveId` (minted at draft start and again by RUN_IT_BACK). The only non-trivial cost is `saveRevision` discipline (+1 per committed transition, undo included), which Z.ai already wants now. `createdAt` is set once with `saveId`, and `savedAt` cannot stand in for it. `profileId` stays out (no second writer yet); VERIFIED absent from `envelope.ts`.
2. No `datasetId`. A dataset is identified by its content: `dataVersion` = `'sha256:' + hex` of the canonical text. A second name for the same thing can disagree with the bytes. Z.ai's `datasetId` (uuid minted at new season, for multi-device identity and shareables) is the same job as `saveId`; adding both would duplicate it. `dataset.source` ('bundled'|'user') is app state and is derived at load.
3. SHA-256 vs "a canonicalization spec is enough". Z.ai is right that the canonical form is the load-bearing part, and that is what makes row order, CRLF and Unicode composition irrelevant (already in `hash.ts`). The algorithm is the cheaper half to get right once: SHA-256 is a named standard anyone can reproduce with `sha256sum` or Web Crypto and check against `dump-storage.mjs` output, where cyrb53 is our own 53-bit function with no external test vectors. The price is that it is async (hash at dataset load, never in a reducer; already the rule) and that every dataset or rules-table edit is a deliberate re-pin. The `sha256:` prefix makes the algorithm self-describing, so a later change is detectable, not silent. No strength argument is claimed: 53 bits would be enough to notice an edit.
