# 1b vertical slice: one neutral drive, pack to box score (Architect, 15 Nov 2026)

Code: `colors/src/sports/nfl/sim/` (`toypack.ts`, `drive.ts`, `box.ts`), tests `colors/test/nfl/sim-slice.test.ts`. Labels: VERIFIED (run by me this session), INFERRED, UNKNOWN.

## What exists now
One drive, neutral teams, all the way through: a model pack (rules and node tables as data, validated at load) -> keyed draws (`core/keyedrng.ts`, one cell per (game, event, tag)) -> an append-only event log (`drive_start`, `play`, `extra_point`, `drive_end`) -> a fold -> a box-score view model (team lines, drive table, scoring summary). Numbers that must replay bit for bit go through `core/pmath.ts` (the field-goal curve, the lambda tilt). The lambda seam is live and inert at zero: `P_k` proportional to `p_k * exp(lambda * theta_k * gap)`, one node (pass result) wired.

**The pack is TOY (hand-set, not fitted).** It proves plumbing, not football. No test pins a toy number as a target and none of its outputs may be quoted. Kickoff time, penalties, two-point tries, overtime, personnel and players are not in the slice; they are nodes, built one at a time.

## What I would change in the plan (from building it)
1. **Lab-product bit identity.** The toy proved one uniform per (event, tag) is enough to replay, branch and couple. The Lab (Python) still uses numpy and `random` streams, so a Lab result cannot be replayed play by play in the product. A Python twin of `keyedrng` (Philox, about 60 lines, same pattern as `pmath.py`) would let the Lab and the product draw identical numbers from the same pack JSON. Then "the TS port reproduces the Lab" becomes an exact comparison per play, not a distribution comparison with a tolerance. This is the conformance-vector step done properly. INFERRED value; UNKNOWN cost until tried.
2. **Paired lambda estimates come free.** Coupling means the Lab's derivative with respect to a duty gap can use the same key on both sides of a gap. The toy kernel measured 3 to 4x lower variance for pairing; the slice makes the mechanism a function call (`runDrive` twice, one key, two gaps).
3. **Gate identities, report magnitudes.** The two red tests died because they pinned a derived total. The pattern generalises: for every ledger-like quantity, gate the accounting identity and print the number. I would apply it when the pool ledger test is written.
4. **Order of the next nodes (1c):** pack builder first (port the Phase 1 pools to a baked pack so the slice runs on real data and the 10% totals bar can be re-run in TypeScript), then nodes in order of how much variance they explain (play call, completion and yards, clock, 4th-down policy, kickoff), each with its held-out report.
5. **A framework-free dev harness** (`colors/harness.html`, separate from the product's `index.html`) that renders the slice's box score would let CI's build step go green and let me check 390 px and desktop without touching the framework pick. Needs Owner nod only if it implies a UI choice; I would keep it a plain table.
