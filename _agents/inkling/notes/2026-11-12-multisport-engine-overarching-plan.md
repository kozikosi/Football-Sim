## 0. The one-paragraph answer

The "new multisport engine build" is not one build. It is a stack of six gates, and the single most valuable thing I can contribute is the **order and the boundary**, because everything else — framework, CSS, database, auth, CI shape, the lab — is downstream of those two. The football engine that ships as Colors v1 is Gate 1's product and Gate 2's payload. The multisport claim is proven at Gate 5 by a headless basketball pack against a frozen contract, never by adding sport abstractions into the football build. The online platform is Gate 6 and inherits two guarantees now — a pure reducer for an engine and an append-only, typed event log — and nothing else. Every document the project produced this week is real work; the failure mode is that none of it is sequenced, so it competes instead of composing. This note puts it back in order.

## 1. Diagnosis: what the conversation actually contains

- **(A) The football game.** Colors v1: Z.ai's shell + the Architect's engine. Real, scheduled, half-built. Its failure mode is shipping late with an unverifiable model.

Its failure mode is being *designed* forever and *built* never, and in particular being validated on intuition instead of measurement.
- **(C) The platform.** Online leagues, accounts, payments, 10,000 users. It is referenced in the Owner's six questions, in GPT's §1–10, and in the framework-test scoring — as if it were load-bearing today. It has no evidence base: zero users, one unshipped game, no server anything. Its failure mode is eating the budget of (A) and delivering infrastructure nobody can test.

## 3. The architecture in one page

```
                 ┌──────────────────────────────────────────────┐
   fold/reduce   │  EVENT LOG  (ordered, typed, seeded, serial.) │
   (pure)  ◄──────┤  the only interchange between engine and     │
        reducer   │  everything else                             │
                  └───────▲─────────────────────▲────────────────┘
          propose(state, │                     │ emits
          spec, seed)    │                     │
                  ┌──────┴─────────┐   ┌───────┴────────┐
                  │     ENGINE     │   │  SPORT PACKS   │
                  │ pure functions │───│ football/ …    │
                  │ kernel math    │   │ basketball/…   │
                  └────────────────┘   └────────────────┘
                                              (data + spec; no logic shared
   below the line: effects only        except through the kernel)
   storage · network · renderers
   ────────────────────────────────── ENGINE BOUNDARY (enforced, §3.4) ──
```

**3.1 SportSpec — a sport's DNA, data not code.**
`SportSpec = { version, sport, eventGranularity, slots[], units[], dutyTable, flex: { rules, priceFn }, targetTable, scoringGrammar, solver: 'assignment' | 'rotation-enumeration', statReducers[] }`.
Three points my work supports: (a) the λ/cuts/tiers are fitted constants **of the football spec**, not kernel constants — the kernel takes them as inputs (VERIFIED from my FL-1 and P-322 review: the SCOPE table is sports-specific data, deletable with zero effect on the live 99 rules but silently mispricing DL5 — that class of bug happens precisely when spec data is allowed to live behind kernel logic); (b) the flex price *function* (finite-difference in wins) ports; the flex *rules table* does not (VERIFIED above); (c) the solver is part of the spec because it is genuinely different in kind (Hungarian vs constrained enumeration) — GPT's §10C "sport-independent shell, not sport-independent engine" survives precisely this way: the shell (scheduling, saves, awards plumbing, franchise nav) is shared; the sport engines are packs.

**3.2 EventLog — the product, internally.** Every interesting surface is a pure fold:

| Fold | Consumes | Replaces / enables |
|---|---|---|
| Box scores, play-by-play, recaps | log | the recap path (already derives from result; becomes derivable *and auditable*) |
| Standings, awards, leaderboards | log | `computeRegularSeasonAwards` integration |
| The Lab (§6) | logs from seeded runs | ad-hoc score-diffing archaeology |
| Clutch feed / big penalties (P-354) | log events flagged clutch | a second narration code path that re-derives state |
| Halftime focus change, 4Q automatics (focus feature) | log + spec | scattered conditional logic in UI state |
| Gravity / double-team viz (P-350) | log's target/doubling events | "the UI asks the engine" coupling |
| Share card (Q8, 20-0 moment) | log + margins | replay artifacts |
| Server authority (Gate 6) | log replay from client commands | server trusts client (never do this) |
| Determinism regression (Gate 1) | log equality | flaky "same seed feels different" bugs |

**3.3 Versioned rules and data are save-format citizens, not housekeeping.** `ruleVersion = hash(engine + footballSpec)` written into every save and every completed-season record; `poolVersion` into the ratings header. This is what makes "historical franchises preserved" mean anything when slot values drift: a 2016 season replayed under R7 must produce its R7 story forever. Re-pin via MERGE-MANIFEST in the same commit as any protected-constant change, same discipline the Owner approved for §3. It also gives the portfolio story its one-sentence spine: *"our saves know which football they were played under."*

**3.4 The boundary, enforced — three cheap checks, no new infrastructure:**
1. **Lint boundary:** within the engine tree, `window|document|localStorage|sessionStorage|indexedDB|fetch|XMLHttpRequest|Date.now|new Date|Math.random|performance.now` are errors (Biome `noRestrictedImports`/`noRestrictedGlobals` or one grep-test — pick one, don't build both).
2. **Replay test:** stated Pack + fixed seed ⇒ byte-identical log hash, run in CI on every PR.
3. **Import-direction check:** the engine tree imports nothing outside the engine tree (one test scanning imports; a `depcruise` config only if a seat wants it and it stays local).
GPT asked for exactly this ("make the boundary an enforceable architectural rule"); three greps and one hash check do it. No package split until Gate 5 proves a second pack — AGENTS.md's single-file history shows that *premature* structure is this project's disease, not over-abstraction.

**3.5 What this buys, explicitly:** GPT's six "whether" questions answered for Gates 1–5: engine independently testable (yes — CI), runs without the browser (yes — Node), multiplayer authoritative later (yes — log replay; build never until Gate 6), DB preserves franchises (yes — `ruleVersion`), 10k concurrent leagues (designed for; not built; no infra now), basketball without duplication (yes — Gate 5 falsifier, or the absence is honestly UNKNOWN and reported).

## 4. Colors vs Cakepanz — my recommendation (the Owner decides; I do not)

I have not re-run the tracks this session (they live on `architect/engine-and-seats` and `gh-pages`); what I cite is MUSE's stack audit of 2026-11-12 (VERIFIED by her against the repo, REPORTED to me): **Colors** = TS engine + view-models + platform adapter, Philox2x32, no `.svelte` files, React 19 declared but unused, no styling, no CI; **Cakepanz** = 10 `.svelte` files, the whole visual product (72 Wins), no type-check/test scripts, no lint, Vite 7, `gh-pages` root has a local-only commit (`7c9694e9 "Publish w89 as live index"` — VERIFIED this session by `tools/preserve.mjs check`). **Pre-Colors** = frozen reference, correct oracle for football rules, wrong foundation for anything new.

**My recommendation: Colors is the product home.** Cakepanz is demoted from "track" to "the design specification of the target UI" — every visual decision Z.ai and the Owner converged on gets encoded as requirements (72 wins as acceptance criteria), the shell is re-implemented on the chosen framework at Gate 4 (if it differs from what Cakepanz already is, the framework test decided it), and its CSS tokens and assets are harvested, not its runtime.

Why not the reverse: making Cakepanz the home means porting the Architect's engine (typed, tested, deterministic, storage-isolated — the parts of this project I would actually defend in an interview) *into* an untested, unlinted, untyped UI tree by the only person allowed to edit the product's internals (the Architect) — i.e., days of archaeology before the first new screen, and a permanent two-copies-of-the-truth risk during the port. The UI is cheaper to re-implement on a known-good engine than the engine is to extract from an unknown-good shell.

Why not "keep both" — the failure this whole document is about. Permanent dual tracks = the λ-objective problem at architecture scale, forever.

Confidence: **moderate (INFERRED from MUSE's audit, not from my own byte-level inspection of both trees).** The exact reasons the Owner should choose differently: (a) if the Cakepanz shell's actual code is materially cleaner than reported — measure, don't re-litigate; (b) if Z.ai can re-host the Colors engine inside the Cakepanz structure in under a week with the existing storage adapter — then Cakepanz-home is real, at the price of accepting no types/CI until the port lands (say so); (c) if the Owner values *shipping the 72 wins next month* above *one coherent codebase* — then Cakepanz-home with the engine strangler-merged in is a legitimate, explicitly-temporary Option B, time-boxed with a kill date. Option C (full third build from scratch) is rejected outright — it is the one option guaranteed to re-litigate every decision this project has already paid for.

## 5. The framework test — my scoring corrections (adopt GPT's split, with teeth)

GPT's two-category split (framework-specific decides the winner; framework-independent = shared acceptance tests, pass/fail, zero weight) is **correct and is the single best methodological idea in his assessment.** Adopt it verbatim. What I add or change — each labelled:

1. **Contract suite first, prototype second (order, not math).** Write and freeze the engine-contract suite (seeded replay, halftime rule, 4Q auto, Priority-not-Wins, focus change visible everywhere) *before* any prototype starts. Otherwise the suite drifts toward whatever the prototypes actually built — the engine equivalent of the audit-written-after-the-build.
2. **Disqualify by correctness; rank by modification cost.** Correctness 20% becomes a gate (GPT's own call — keep). The winner is then decided by second-round-change (20%) + maintainability (10%) + agent quality **intervention-adjusted** (15% → subtract each required human intervention from the agent score; an agent that needed 12 prompt-nudges did not "build it") + engine integration (10%) + UI (10%, unchanged) + server-ready (10%, and score it as "no engine imports outside the engine tree", mechanically greppable) + tooling (5% → fold into the pinned-Node build check). **Change amplification is the operationalization of "second-round":** files touched, unrelated files touched, by `git diff --stat` on the fifth-then-sixth focus diff, not by the author's summary.
3. **Sixth-focus isolation rule (my addition):** the agent adding the sixth focus must not see the prompts used to build the original focuses — otherwise it *reads the answer* (the existing four setups are right there in the repo). Run it from a clean clone of the prototype with the feature list only.
4. **A different model family runs the modification.** GPT said "another agent inspects and modifies"; sharpen it: if Z.ai built all four prototypes, the inspection/modification agent must be a different family (the council has enough — GPT, Claude, GLM, Pickle…). This is the only honest test of "another agent can understand this codebase", which is the actual question for a 100%-AI-written project.
5. **Scoped verdict or no verdict.** The write-up must say *"X is the best choice for interactive, stateful, sim-adjacent UI features built and maintained by AI agents under this prompt and budget"* — never *"X is the best framework"*. The 2026-11-12 "Svelte is locked" failure happened because an unscoped claim traveled further than its evidence; the test's *purpose* is to end that class of error, and a broad verdict would recreate it.
6. **Acknowledged confound:** all four prototypes share one author (Z.ai). No design removes this; record it in the verdict header, and note that a rerun with a different builder — even on a single contender — is the only way to de-confound later. UNKNOWN whether that rerun happens; do not block the framework decision on it, but do not let the verdict hide it either.
7. Next.js staying out (React represented) is right. SolidStart in the test is right (the Owner called it). Do not add a fifth.

## 6. The Simulation Laboratory — the honest answer, then the smallest useful version

**Is the Lab the right next major investment? No before Gate 2; yes immediately after.** It is the steering wheel of every engine decision this project will make next — dynamic engine, form/synergies, the fluctuating dial, the Ledger rebuild — and driving without it is how the λ objective produced days of debate with receipts but no confidence. But before Gate 2, every lab output is produced on a product that does not exist as a build; the Lab only becomes load-bearing when there is one artifact whose hash it certifies. So: **Gate 3, first thing after Colors v1 ships, before the framework-dependent UI rebuild.**

**Smallest useful first version (L0 + L1), concretely:**

- **L0 — invariants as tests (this is most of it, and it is cheap).** `lab/invariants.ts`: a roster never violates slot legality; no player on two teams; every game ends with a valid final score; box-score player stats reconcile to team totals; draft picks follow order; a season awards each award once; player ages advance monotonically across saves. Each invariant is one assertion over the event log — which is why Gate 1's log exists. These catch the "silently wrong game" class, which tests of convenience never do.
- **L0 — one flat report.** Seeded full-season batch (1,000 runs); emit means/variances/percentiles for points, yards, drives, plays/drive, turnovers, one-score %, margin SD, home-win %, and per-position production; compared against real nflverse 2016–2025 (the staged 484k rows — VERIFIED staged by P-344's delivery being re-downloaded and re-run byte-identically by me; **integration into the engine CI does not exist yet**, which is exactly L0's job). Hold out 2024–25 from all fitting.
- **L1 — the A/B harness.** Same seeds, build N vs N+1: distribution deltas with bootstrap CIs; a golden-franchise fixture (fixed seed: 32 picks + 3 sim weeks + one awards run; stored in-repo; any engine change must reproduce it or a human re-pins it with a written reason — never silently). This is the mechanism that turns "the engine feels better now" into a litigable claim, and it is ~a day of work on the existing lab.
- **Explicit non-goals:** no parameter sweeps before L0 baselines exist; no dashboard until someone files "the report has been read twice and acted on once"; no held-out tuning; never let league averages substitute for distributions (means pass trivially on a broken model; the 48.5% one-score rate and the 16.1% blowout rate and the 54.8% home-win (REPORTED, MUSE's margin gate) are the hard cells).
- **Human factors:** volume ≈ 1,000 seasons (≈35 min single-threaded at the Pre-Colors 7.8 ms/game rate — VERIFIED by the Architect, 3,000 games; INFERRED for Colors TS) is fine for nightly and local A/B; CI gates stay L0 invariants + replay only. **Review-chain change (one line, mine to propose):** any engine-touching P-item requires a lab A/B delta table attached, same as it requires a receipt today. Without that one sentence, the Lab is a museum exhibit; with it, it is the steering mechanism.

**What the Lab must answer first** (in order): (1) Do the Gate-1 invariants hold over 1,000 seeded seasons? (2) Does Colors v1 sit inside ±10% of 2016–2025 on the gate's named cells? (3) Which single change (e.g., λ 0.20→0.40 display rules, DIME 0.15→0.126 re-anchor from P-346's real-data finding, WR1 doubles tau) moves distributions most, and is it toward or away from football? (4) Does the play-level Ledger view actually beat the drive engine on the metrics P-341 measures (DIME share, plays/drive 5.63 target, R1–R5 receipt classes)? Answer (4) only when the Ledger's Phase-2 evidence lands; do not preempt it.
