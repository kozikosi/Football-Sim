## What the slice is

The Owner's N2 ruling: **static brag shareables over replay URLs** — a card/image a user saves or posts after a season (or a great game), carrying **the result and the proof (the seed, the team, the record)**, generated from the engine's own saved season/game — nothing invented, nothing faked — and the **seed card** as its companion: the seed is the proof, the card is the display.

**The shape of the brag (the thinking, not just the list):** a fan posts a brag because it reads like a headline, not a database row. So the card leads with the result in one line (`CHI 39 · IND 36`, user-first, each side in its own ink), the outcome word under it (`VICTORY — FINAL` / `CHAMPIONS — the Super Bowl is yours`), then the specifics that make the brag *believable* (drives, lead changes, my drives / the record, the points, the playoff path), then the **proof block in monospace** — seed, gameSeed, engine pin, dataset stamp, save identity — quiet and exact, like a lab note. A brag without proof is noise; the proof block is what separates this card from a made-up image.

**The artifact form — why a PNG:** the prompt allows "an image or a self-contained card" and invites a better idea. A PNG was chosen deliberately:

- *postable anywhere* — it drops into any chat or feed; a DOM-only card needs a screenshot (desktop, croppy), and a share URL is exactly what N2 ruled out;
- *provably static* — the bytes carry the result and the proof; the battery verifies the PNG magic bytes and that the card contains no link back into the app;
- *one data source, two surfaces* — the canvas painter (`bragCard.ts`) draws from the **same plain-JSON view-model** the DOM card renders (`shareVM.ts`), so what you see is what downloads and the numbers cannot drift between them.

**The data path (engine-true at every step, nothing generated):**

- the **game brag** — the feed's own path: `feedVM()` / `playUserWeek()` (the engine's `buildSchedule` → `gameSeed` → `matchupModel`/`teamIdentity`/`simulateGame` → the snapshot's `gameFeed`), so the card's scoreline IS the played game — the battery matches it EXACTLY against a node recompute;
- the **season brag** — from a real `SeasonEnvelope`: the payload's own table row (record, PF/PA), the payload's own champion and userOutcome, the user's own results (the playoff path); the envelope's own `saveId`/`engineVersion`/`dataVersion` ride the proof. No season producer exists in the UI yet (the season screens are a later slice), so the battery builds the envelope the way the app's season slice will store it: `batteries/seasonfixture.mjs` → fixture league → `startSeason` → `playWeek` to a finished season → the real `SeasonPayload` → `serialize`. The envelope lands in a slot like any save and is read back through the ONE parser (`restore`) — corrupt-never-repair, as ever;
- the **seed card** — the seed the run forks from + the honest replay recipe. Honest is the point: for a season save the recipe says the engine replays the whole season from (seed, year, run); for a draft save it says the board and the week-1 game replay while "your own picks are the one free variable". And the recipe is not decoration: **the battery replays the season node-side from the same (seed, year, run) and lands the same champion and the same record row** — the seed card's promise is a verified claim, not a caption.

**Where it lives in the UI:** the feed gains SHARE THE RESULT (the brag moment: the game just played) → the share screen renders the brag card + the seed card, each with its own SAVE PNG. The Saves panel gains a **Brag card** button per loaded slot — a season save renders the season brag; a draft/week save renders the seed card alone with an honest note ("no result stored in this save yet").

**On the Architect's flex-table build (`97d7e9d`, per the prompt's note):** it touches flex pricing; Slice 5 renders saves' own numbers and no flex value appears on either card — nothing in this slice is affected. Still building on `4ca9a071`, the frozen snapshot for this track; the re-pin is the Architect's call.

## The goals check (the Owner's question this round — one paragraph per goal)

**Svelte 5 + Vite — confirmed.** Slice 5 is built the same way Slices 1–4 were: Svelte 5 (`svelte ^5.57.3`, runes state — `$state`/`$derived` in `Share.svelte`, plain props + callbacks per the established component contract) with Vite 7 (`@sveltejs/vite-plugin-svelte ^6`), `vite build` → `dist/` clean (316 kB JS / 107 kB gzip, +15 kB over the slice-4 build), no warnings. The two new TS modules are framework-free view-model/painter code; the engine is consumed as source exactly as before (esbuild strips types in the build, `node --experimental-strip-types` in the tests). No new dependency (the painter is the platform's own canvas), no non-Vite step, nothing that a Svelte 5 + Vite build would not survive. Nothing has drifted.

**Cloudflare deployment (eventually) — confirmed, and it is a small change or less.** The app is a static build: `vite build` → `dist/` (an index.html + hashed assets), no SSR, no API routes, no Node runtime at request time, storage is `localStorage`, the dataset is bundled at build time (`?raw` imports), and there is no client-side routing — the screens are Svelte state, so no SPA fallback rule is even needed. `vite preview` in the battery is dev tooling, not runtime. A Cloudflare Pages deploy is literally: build command `npm run build`, output directory `dist` — zero code changes. The one forward note: when real accounts arrive, their endpoints are the first non-static surface, which is the account slice's business (Cloudflare Pages + Functions is the natural home; nothing in the current tree needs to move for it).

**The account system (designed, eventually) — confirmed, with two frictions named.** The envelope remains the portable unit exactly as designed: self-contained plain JSON text (saveId · saveRevision · createdAt · engineVersion · dataVersion) written through the `StorageModule` seam — the only browser-storage toucher — so a server store is a swap behind that interface, not a rewrite. Slots A/B/C are local profiles in `localStorage` keys; nothing in the UI assumes a save can only live on one machine (the lineage — saveId/createdAt — already survives loads by design, and the brag card renders from whatever envelope it is given, wherever it came from). Two frictions, named because the Owner asked for the thinking: **(1) saveRevision has no device dimension** — two devices revising the same saveId concurrently would collide; the fix is a `deviceId` in the envelope meta at the next schema touch (filed as an IDEA — a schema-level change that belongs to the account slice, not smuggled into a brag-card delivery). **(2) `savedAt` is client clock** — harmless for replay determinism (engineVersion pins that, per F5) but a sync layer will want a server-authoritative timestamp; again the account slice's call. Neither blocks; the design path holds.
