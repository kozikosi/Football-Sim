## Q1 — Slices: are (a)–(d) the right four?

(a) player cards, (b) stats table, (c) draft-board row are right — they cover read-heavy, data-dense, and interactive-row shapes, which matches the varied-shape requirement (one read-heavy, one write-heavy, one state-heavy). (d) the settings form is the weakest slice: it is small, low framework differentiation, and mostly tests persistence (localStorage) rather than the framework. **Swap (d) for a live-updating feed.** The feed is a real w89 surface (one of the four screens), it is write-heavy + state-heavy, and it exercises reactivity under changing data — the core framework difference. A feed that updates live (new play-by-play lines arriving, scores changing) separates the frameworks on the thing they actually differ on. Keep the settings form as a backup if the feed proves too big for one sitting. Do NOT add a 1,000-row board — the board is paginated/filtered in the real product, so 1,000 rows at once is not a user flow; it would measure a scenario that never happens.

## Q2 — Settle rule: which candidate should be PRIMARY?

**Primary: a synthesis of Ernie (2) + Inkling (3), stated as ONE rule: "≥15% less time-to-green on ≥2/3 pairs AND the summed normalized paired difference exceeds the within-slice spread."** That is Inkling's threshold + Ernie's variance gate, combined. The Z.ai prompt Rev 2 already applies exactly this (Inkling primary + Ernie condition (b) as a secondary gate) — so the council's job is to bless that combination as the primary, not to pick a different one. Reasoning: Ernie's statistical critique is the crux (N=3 cannot resolve a bare 15% threshold when per-slice variance is problem difficulty), and Inkling's time-to-green is the Owner's actual axis (authoring efficiency). Neither alone is sufficient; together they are. Glyph's composite (1) is out as primary — unmeasurable at N=3 (two noisy units under one name). Beam (4) and OR (5) are repair-cycle rules — repair cycles are the compounding cost, which is the right primary for MAINTENANCE, but this experiment is about AUTHORING (first build), so repair cycles are a witness here, not the decider. **Forced workarounds: a WITNESS, not a primary and not a tiebreak.** It explains WHY an arm lost and flags a maintenance problem, but it is not the decider for authoring. Beam's "≥1 forced workaround per slice outside the store → Svelte loses on maintenance" is too strong for authoring — it is a maintenance signal, and the experiment's settle is about authoring. Record it, use it to explain the result, do not let it override the time-to-green verdict. **VL's retired rule: the retraction is final as a primary.** The double-AND (≥15% on BOTH wall-clock AND repair cycles) manufactures washes at N=3 — that is why Inkling retired it. But its SPIRIT survives: both time AND cycles must agree, which is exactly what Inkling's flag (≥2× repair cycles → untrusted + rerun) and Ernie's condition (b) (signal must exceed spread) do. VL's contributions to adopt: pre-registration, replication, and the tiebreak. The double-gate itself is not saved.

## Q3 — E0 (static audit + Cardboard Ringers): can it settle without timed builds?

**Yes — the static audit runs first and CAN settle the question without any timed builds.** It is deterministic (no timing noise), blind-reviewable, and cheap. If one arm has materially fewer framework-owned lines AND the named-mechanism audit shows the shared layer is equal, that is a settle. **Cardboard Ringers: yes, run as an admission test before the main slices.** If it takes more than one sitting in either arm, the platform hypothesis is strained before any surface ships. **If E0 is decisive, E1–E4 do NOT all still run.** E1 runs on ONE slice as a spot-check (confirm the static result holds under timing, not re-litigate it). E4 still runs (self-report preference is a separate dimension from the settle rule — the Owner asked which framework agents prefer, and that signal is valuable even after a settle). E2 and E3 are deferred — they are about maintenance and tooling, which matter for the WINNER's onboarding, not for the settle. Running all of E1–E4 after a decisive E0 is wasteful; the point of E0 is to save that work.

## Q4 — Benchmark battery (E4): are the eight benchmarks right?

The eight are good. **Add one: "how much you had to fight the framework"** — distinct from "how much you had to look up." Looking up is about not knowing (training-data thinness); fighting is about the framework resisting you (compiler-forced idioms, getter wrappers, re-exports). The forced-workarounds count measures fighting objectively; the self-report should measure it subjectively too. **Reword "confidence their code is correct" → "confidence the code does what you intended."** Correctness is about the type system catching errors; intent is broader (the code does what you meant, not just what compiles). **Weight "speed of iteration" most.** The Owner's question is "easier/faster/more complete," and the experiment's primary metric (time-to-green) IS iteration speed — so the self-report should weight the same dimension as the objective metric. Consistency between the objective metric and the subjective battery matters more than any single benchmark.

## Q5 — w89 beauty: how to carry it into the new repos?

**A shared token file + a reference screenshot.** A `tokens.css` (or `theme.css`) with the gold palette, the `--tc` team-color variable, the Cinzel + Cinzel Decorative font stacks, and the dark background — copied into both repos (copied, not imported; the repos are standalone). Plus a reference screenshot of w89 (the live site) as the visual target. **"Resembles w89" checkable in three ways:** (1) **Palette check** — the slice uses the token file's colors (no hardcoded colors outside the tokens; grep for hex codes outside `tokens.css`). (2) **Font check** — Cinzel + Cinzel Decorative are loaded and used for headings (grep the font-family declarations). (3) **Side-by-side screenshot verdict** — the slice next to the equivalent w89 screen, judged by a reviewer blind (labels swapped). The per-slice fidelity check should include a screenshot comparison, not just DOM node counts — DOM counts prove the structure matches, screenshots prove the LOOK matches.

## Q6 — Methodology: is within-agent + randomised order + pinned fidelity right?

**Yes — it is the right design.** Cross-agent measures the agent, not the framework (Ernie's design attack), so within-agent is the only design that holds skill constant. Randomised order cancels the learning effect (the second build benefits from the first's learning). Pinned fidelity (DOM node count, rows, states, fixture SHA) is what makes the comparison a comparison. **Biggest remaining confound: training-data mix.** The agent may simply know Vue better because there is more Vue in its training data. **How to control for it:** (a) the E3 tool-access audit — if the agent leans on MCP/docs for one framework far more than the other, that is a signal the training data is thinner there; (b) the E4 "how much you had to look up" benchmark as a proxy for training-data thinness. **But the confound is partly the answer, not just noise to control.** A framework with thinner training data IS harder for agents to use — and the Owner's question is precisely "is it easier for agents to code in Vue or Svelte?" If Svelte 5 has thinner training data and agents therefore look things up more and make more mistakes, that is a real finding about authoring efficiency, not a bias to remove. Report the lookup rate alongside the time-to-green, and let the Owner weigh them.

## Q7 — Platform: confirm the synthesis, or side with VL (DIALS first)?

**Confirm the synthesis (Sim Lab v0 + receipt diff core + DIALS content as read-only presets, DIALS last).** VL's argument is backwards: he says the diff viewer is a consumer of differences that do not exist yet, but the diff viewer does not need differences — it needs RUNS, and runs exist (the engine runs). The receipt diff proves the engine is a function (same inputs → byte-identical records), which is the foundation the Sim Lab needs. DIALS first would build a knob UI for a λ that has no validated estimator — knobs without a validated dial are decoration. **The one constraint that keeps it honest: Inkling's two-editable-fields (kappa, seed) + λ and flex displayed as read-only provenance until A3 validates the estimator.** That is the tightest constraint on the table — tighter than Beam's read-only mode (which is a mode, not a field count) and Glyph's falsifiers (which are checks, not constraints). **Should the experiments' slices emit diff-able receipts? Yes.** Every slice should emit a receipt (the same `verified-as-of.json` + a run receipt) that the diff view can compare. That makes the experiments feed the platform directly — the framework test produces the first comparable receipts the diff view consumes.

## Q8 — Process: adopt `verified-as-of.json` in every future prompt and in CI?

**Yes — in prompts first, CI second.** A machine-readable claim→ref/sha/command is exactly what the council needs to verify premises without re-reading filings. It is the fix for the stale-premise problem that has bitten this project repeatedly (w85, 10,946 B, the R3.1 flag omission). **Falsifier: if after two prompts the prompt churn (corrections to stale premises) does not drop, retire it** — because then it is overhead without benefit. A second falsifier: if a `verified-as-of.json` file itself goes stale (claims that no longer match the branch), that is a failure of the tool — it must be maintained or it is worse than no tool (a stale machine-readable claim is more dangerous than a stale sentence, because it looks verified). Adopt it in prompts now; prove the value there before automating it in CI (CI is a bigger lift and the project has no CI anywhere yet — do not bundle a new process tool with a new infrastructure build).
