### The four experiments (Rev 2)

**E0 — Static audit + admission test (new in Rev 2, runs FIRST).** Before any timed build: (a) count **framework-owned lines** in each repo for the same pinned Slice 5 fixture, with the **named-mechanism audit** (name the framework-owned mechanism per line-group; shared-layer code does not count) and the **forced-workarounds count** (places where the framework's own rules forced code you would not write in plain TS — getter wrappers, re-exports, compiler-forced narrowing fixes). If one arm has materially fewer framework-owned lines AND the named-mechanism audit shows the shared layer is equal, that is a settle on static, deterministic, blind-reviewable evidence — no timing noise at all. If it is a tie, fall back to the timed rule (E1). (b) Run **Cardboard Ringers** in both repos in one sitting (2 teams × 3 roster slots, one match, one table). If it takes more than one sitting in either arm, flag it — the platform hypothesis is strained.

**E1 — Within-agent authoring sitting (the core one).** Same agent builds the same slice in BOTH repos, order randomised per slice. Slices: (a) player cards, (b) a stats table, (c) a draft-board row, (d) a settings form. Fidelity pinned numerically: same DOM node count, same rows, same states, same chrome bytes. Measure: time-to-green (start to all repo checks passing), repair cycles (edits after first build), defect count (type errors, test failures, console errors), framework-owned lines, forced workarounds. Record the exact command and its exit code for every "done" — receipts, not narration. Do not write "verified" without the exit code. Lessons applied: cross-agent measures the agent, not the framework (Ernie's design attack) — so within-agent; bundle is dead as a decider (~11 KB); line count is flat (R=0.9778) so it is a secondary metric, not the decider — EXCEPT the static audit in E0, where lines are the primary (Ernie's cheaper measurement).

**E2 — Maintenance edit, not greenfield.** Give the agent a working slice in each repo, then ask for the same change in both: add a feature, fix a planted bug, refactor a piece of state. Measure: time to first *correct* edit, how many wrong edits came first, whether existing tests broke, whether the agent reached for the framework's tooling to diagnose, and forced workarounds introduced by the edit. Greenfield flatters a framework; maintenance is where the mistakes live.

**E3 — Tool-access audit.** For each repo, enumerate what the agent can actually use and whether it works: MCP servers (Svelte MCP, Vue MCP, Context7), devtools (vite-plugin-vue-devtools is in the Vue repo; Svelte's devtools story), type checking, Vitest, Playwright, state-inspection hooks (`window.__pinia` vs `window.__SIM_STATE__`). Measure: which tools exist, which the agent actually invokes, which ones measurably help (fewer errors, faster green) versus which are unavailable or broken. Count real gaps, don't work around them: the Vue repo already rules out `vite-plugin-vue-mcp` on Vite 8 (peer support only through Vite 6) — that is a tooling gap to record, not a problem to silence.

**E4 — Self-report on a benchmark battery.** After building in both, each agent rates both frameworks on the same battery — state management, debugging, confidence their code is correct, readability of their own code, speed of iteration, tool helpfulness, how much they had to look up, how much they enjoyed it — Likert scale plus one line of why, then an overall preference and a confidence. Same questions, both frameworks, every agent. Aggregate across agents so the preference signal is comparable instead of anecdotal.

E0, E1, E2, and E4 run together (same agents, same slices, survey right after while it is fresh); E3 runs alongside as the audit. Z.ai is the principal executor for the building (largest context window), but the within-agent design means any agent can run a slice — more agents shrinks the skill-variance problem.

### Settle rule (Rev 2 — the live candidates; the council picks or synthesizes)

The Rev 1 prompt used Glyph's rule (≥15% lower correction effort on ≥2/3 slices). The round-2 filings contest it. Here are the FIVE live candidates, stated accurately:

1. **Glyph:** ≥15% lower **correction effort** (composite of time + cycles) on ≥2/3 slices, wash → Vue on tooling. *Challenged by Inkling (composite unmeasurable at N=3) and Ernie (15% unresolvable at N=3).*
2. **Ernie (round-2 fourth rule):** paired, variance-relative, first-build-primary. Pre-declare ≥3 slices of varied shape; first build primary + one maintenance edit (doubles paired points to six); count framework-owned repair cycles only; per-slice paired difference normalized by that slice's total cycles; arm wins iff (a) sign consistent ≥2/3 AND (b) summed normalized difference exceeds within-slice spread. If (a) but not (b) → tie → tooling → Vue. Wall-clock secondary; lines third. *Plus: run the static audit (E0) FIRST — if decisive, the timed rule is moot. Do not adopt any rule whose primary gate is a 15% wall-clock threshold.*
3. **Inkling (live, round-2):** ≥15% less **time-to-green** on ≥2/3 pairs (sign-consistent, magnitude-gated) with pinned fidelity and no critical regression → that arm wins authoring. All pairs within ±5%, or split → wash → tooling → Vue. **Amendment:** if the winning arm also repairs ≥2× more often, flagged untrusted and the measurement repeats once on the next sitting — a flag with a rerun, not a veto. *Retired his own round-1 double-AND ("double gate → false negatives"). Drops the lines gate (sign-flips across scale).*
4. **Beam:** ≥15% fewer **framework-owned repair cycles** on ≥2/3 slices, wall-clock sign-consistent (Svelte not slower) on ≥2/3 slices. Within ±5% on repair cycles = tie → tooling → Vue. *Plus the "forced workarounds per slice" innovation: if Svelte needs ≥1 forced workaround per slice outside the store seam, Svelte loses on maintenance; if they cluster in the store (written once), wash.*
5. **OR:** ≥15% on **repair cycles** (compounding cost) AND **not slower than Vue by >5% on wall-clock** (one-time cost), on ≥2/3 slices. If neither clears → Vue on tooling. *Separates one-time cost (wall-clock) from compounding cost (repair cycles) and quantifies both.*
6. **VL (note — adopts a retired rule):** ≥15% on BOTH wall-clock AND repair cycles, first build of Slice 5 primary, pre-register, ±5% tie → Vue. *This is Inkling's RETIRED round-1 double-AND rule. VL adds pre-registration, replication, and a tiebreak, but the core double-gate is the one Inkling retired for manufacturing washes. Do not adopt it without addressing the retraction.*

The Z.ai prompt (Rev 2) records ALL the raw data (time-to-green, repair cycles, forced workarounds, framework-owned lines, wall-clock, tool calls) so ANY of these rules can be applied to the same data after the fact, and it applies Inkling's live rule (candidate 3) mechanically as the primary, with Ernie's variance-relative check (candidate 2, condition b) as a secondary gate. Your job in Q2 is to say whether that is the right primary, or whether a different candidate (or a synthesis) should be primary.
