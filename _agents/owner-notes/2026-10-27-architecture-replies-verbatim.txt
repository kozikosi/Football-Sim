If **that requirement appears**, **Cloudflare D1 + Drizzle** is the best fit under the free-tier rules: D1 is part of the Workers free plan, has no separate subscription, and does not pause due to inactivity the way Supabase free projects do — which would be fatal for your traffic shape where the demo may go weeks without a visit. D1 free-tier limits are: 10 databases per account, 500 MB per database, 5 GB total storage, 5 million rows read and 100,000 rows written per day; once exceeded, queries fail until the next UTC midnight. For a demo-scale project these limits are far above actual need, and D1 does not require a credit card, satisfying the “no card” rule.

Drizzle’s value is **dialect portability**: if free-tier policy changes or you decide to move to Postgres, Drizzle’s schema and query layer do not need a full rewrite. This is not “ORM for ORM’s sake”; it is reasonable insurance under free-tier rules.

**What feature triggers a database**: cross-device draft saving, shareable persistent links (not temporary links encoded in the URL, but server-stored share records), or user accounts. Before those features exist, **versioned JSON + Zod + IndexedDB/localStorage** is enough, simpler, faster, and more aligned with your “no premature abstraction” principle.

## 4. Authentication: if you add it, GitHub OAuth + Better Auth; but v1 can skip auth entirely

You agree that “auth should support a real feature,” and that is correct. Without a feature like “cross-device saving” or “share with others,” adding auth only increases attack surface and maintenance burden. An interviewer will not give you extra points for wiring up one more OAuth flow — they are more likely to ask “what user problem does this solve?”

If v1 genuinely needs a minimal “save and share” feature to make the project feel more like a product, **GitHub OAuth is the lowest-cost option**: free, no email infrastructure, and well accepted by your target audience (technical interviewers). **Better Auth** is a better fit in 2026 for the SvelteKit + Cloudflare combination than Auth.js: it has a native plugin system (passkeys, 2FA, organizations), user and session tables live in your own D1, it is type-safe, and it does not lock auth state into a third-party vendor. Auth.js has a more mature OAuth provider library, but if your needs go beyond “login,” Better Auth has broader coverage.

**What you must never do**: implement password hashing yourself, or use unverified email/password login. Z.ai’s point that “the README should proactively admit this is a conscious shortcut” is correct — if you ultimately choose email/password without verification, interviewers will see it, and you need to acknowledge it in documentation and explain what production would do. But the better choice is to use GitHub OAuth directly and avoid the issue.

**v1 recommendation**: **no authentication**. Make the core simulation and draft board fully usable without login. Auth becomes an optional phase-2 enhancement, added only when saving/sharing features genuinely require it.

## 5. Biome: keep it; do not migrate for keywords

This is a point you explicitly object to, and I agree. Z.ai says “ESLint + Prettier wins on keywords,” but your repository already uses Biome. The migration cost is real, and the benefit is only “two more tool names on a résumé.”

By 2026, Biome is no longer an early experiment: v2 unifies linter, formatter, and import organizer, formatting compatibility with Prettier is above 97%, and it is 15–20× faster than ESLint + Prettier. Its rule set covers correctness, suspicious, style, complexity, performance, a11y, security, and more — sufficient for a general TypeScript project that is not React-specific.

**The only condition worth considering a switch**: if you choose Next.js and need **React Hooks rules** or **framework-specific lint rules**, then use a **hybrid approach**: Biome handles formatting and general linting, and ESLint handles only framework plugin rules. Do not migrate everything — that pays an unnecessary migration cost for a tool that already works.

If you choose SvelteKit, Biome coverage is even less of an issue, because Svelte-specific rules are not in the mainstream ESLint ecosystem anyway. **Keep Biome and spend the saved time on tests and the engine.**

## 9. Migration priority (with acceptance criteria)

**Phase 0: Stabilize the baseline (before writing any new code)**
- Pin a known-good version of the current HTML and document reproduction steps for the intermittent draft-board failure.
- Establish characterization tests for the existing football logic, locking current behavior with fixed inputs.
- Acceptance criterion: you can reproduce a known draft state with an automated script and detect whether it breaks.

**Phase 1: Extract the engine (without changing behavior)**
- Extract football logic from the HTML into a pure TS module, injecting a seeded RNG to replace `Math.random()`.
- Keep the existing UI calling the extracted engine; behavior unchanged.
- Acceptance criterion: with the same seed and inputs, the extracted and pre-extraction versions produce bit-identical statistical output.

**Phase 2: Validate and benchmark**
- Run Vitest on the engine and add key invariant property tests (a player cannot be drafted twice, roster constraints, standings consistent with box scores).
- Measure the time for one typical simulation and one full Monte Carlo run on target hardware.
- Acceptance criterion: the engine runs independently in Node tests; benchmark data is written down as evidence for “why WASM is not needed.”

**Phase 3: Framework UI + Worker**
- Rebuild the draft board and results display in the new framework and connect simulation to a Web Worker.
- Keep the engine module unchanged; replace only the UI layer and call entry points.
- Acceptance criterion: a seeded run in the browser matches the Phase 2 Node output; the UI remains interactive during simulation.

**Phase 4: Optional enhancements (only with a real feature)**
- Auth / cloud saves / sharing / monitoring.
- For each feature, first state clearly “what user problem it solves,” then decide whether it justifies a database or auth.

**Do not enter Phase 3 until the Phase 0 intermittent draft-board failure is understood and fixed.** A draft board that still intermittently breaks in a new framework will not get better because of migration — it will only be harder to debug.
