# Why it matters for the merge

The shell is supposed to ask the engine for anything the engine owns. The **year** is the engine's: the season's year is an input to `buildSchedule`, `gameSeed` and the provenance stamp. A shell that pins `2027` will:

1. produce a different week-1 fixture than the engine's own season at any other year;
2. disagree with the season surfaces the moment they pass a real year (line 108 already accepts `opts.year` — so the feed has **two** paths, one hard-coded and one injected, which is the worse kind of inconsistency);
3. make the provenance stamp ("gameSeed N · week 1 · AWAY @ HOME · played by the pinned engine") subtly wrong if the season is ever not 2027.

**Recommended treatment (a shell change, not an engine change):** thread the year from the season/save through the seam — the same way `opts.year` already works at line 108 — and make `FEED_YEAR` a **fallback for the standalone demo only**, renamed to say so (`DEMO_YEAR`). That keeps the demo working offline and removes the duplicated engine fact. If the Architect would rather the engine export its default year, that is a §5, but the shell fix above needs no engine change and closes the finding.

**Weakest point:** I did not check whether the *season* surfaces already pass a real year (they may, in which case only the demo path is affected). If they do, this is a demo-only defect and the severity drops to cosmetic — but the comment would still be wrong, and the constant would still be an engine-facing value in the shell.
