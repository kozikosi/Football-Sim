# STACK ADVISORY — the free-tier constraint + the interview lens
**From:** Z.ai, High Councillor (seat ZAI) · **Date:** 2026-10-28 · **Type:** advisory — no product build this chat
**Intake:** Owner directive: (a) re-review the friend's stack reply under a hard **zero-cost** constraint the friend was not told about; (b) the primary success metric is **portfolio value** — "showing an interviewer that I know how to use the right tools"; (c) GPT's 12-section analysis is on the table. Question asked: *"Does that change your answer to my friend?"*

---

## 1 · Executive answer

The friend's stack survives the free constraint almost intact. SvelteKit, Cloudflare, Vite, pnpm, GitHub Actions, ESLint+Prettier, Drizzle — all still correct under "everything free," and most were the right call on their own merits. The constraint changes exactly **three lines** of his advice:

**1. "Simulation can just run server-side in Svelte" → the simulation runs in the browser.**
Cloudflare's free Workers give **10 ms of CPU per invocation** — hard-enforced, requests start erroring past it — and ~100k requests/day. A Monte Carlo measured in *minutes* cannot live there. Every paid escape hatch (Queues, beefier CPU, long-running containers) violates the free rule by definition. The browser is not the consolation prize: the user's machine is effectively **infinite free CPU**, a Web Worker keeps the UI responsive, there are no server round-trips to pay for, and a long run can checkpoint partial results to IndexedDB and resume after a refresh. GPT reached the same conclusion; the friend's instinct simply predates the free rule. This one change also deletes the "35-minute Monte Carlo vs edge CPU limits" worry from question 18: **the workload never touches edge CPU at all.**

**2. WebSockets become moot.**
With client-side compute there is no long-running server conversation to keep alive. The friend's fallback ("or just use HTTP polling") was already the right shape; the honest v1 answer is that nothing needs either. If a future feature genuinely requires server authority (shared league seasons), that is a new decision with its own budget conversation — and polling comes first there too.

**3. Auth gets one nuance.**
"Email + password, no verification" is mechanically fine and free, but under the interview lens an unverified-password path is exactly the thing an interviewer probes. Either volunteer it in the README as a conscious shortcut with the production answer ready ("verification needs an email sender; deferred deliberately"), or add **GitHub OAuth** — OAuth apps are free, it is ~30 lines, it needs no email infrastructure, and for this project's audience it is a more relevant keyword than email verification would be.

Plus one thing the friend **could not have known — the traffic shape.** This app's usage is bursty-idle: weeks of silence, then an interviewer clicks the link once. Any free tier that sleeps or pauses on idle can serve a **dead demo at the exact moment it matters** (Supabase pauses free projects after inactivity; Render's free web services spin down; Fly.io has had no meaningful free tier since 2024). So a new rule, equal in rank to "no credit card":

> **Nothing on the demo path may sleep.**

## 2 · The four free-tier rules (the audit the friend didn't have)

1. **No card, ever.** A free tier that requires a payment method is a paid tier with a grace period.
2. **Nothing on the demo path sleeps.** Idle-pause equals a dead portfolio link — the one failure mode that can cost an interview.
3. **Assume quotas fail closed.** The free Workers' 10 ms CPU limit is enforced with hard errors, not slowdowns. Heavy compute therefore never goes on the server — it goes in the user's browser.
4. **Assume any free tier can be revoked.** PlanetScale killed its free tier in 2024; Fly.io retired its free allowances the same year. Keep every choice swappable: Drizzle for dialect portability, a framework-independent engine, a static-first shell.

## 3 · Verdicts on the 19 questions

1. **TypeScript + Zod — yes to both.** The sim's types (players, roster slots, sim settings, results) are the documentation; JSDoc types across a 1.2 MB logic surface are a tax with weaker enforcement. Zod (over Valibot: bigger ecosystem, `z.infer` is the pattern interviewers recognize) **at load boundaries only**: player pools, config files, save imports, API responses. Never inside simulation loops — re-validating per tick is a classic performance self-own; parse once at the edge, hand narrowed types to the engine. For the 42 configurations: one discriminated-union `SimConfig` schema, variants become data, all validated in one CI sweep.
2. **Rust→WASM: no — and write down the trigger.** The Monte Carlo parallelizes trivially across Web Workers by seed; measure a worker-pool implementation first. Revisit Rust→WASM only if a *measured* product requirement survives the pool (e.g., "100 seasons × 32 teams in <5 s on a mid-range laptop, and JS is within 2× of budget"), and even then as a hot-path leaf module, never the whole engine. AssemblyScript sits between and avoids Rust's toolchain weight, but it is a third language to defend for a gain nobody has measured. "I profiled and wrote the trigger condition" is the senior answer.
3. **Node (current LTS) for tooling and CI.** Every CI action, Playwright install, adapter doc, and interview question assumes Node. Bun is a fine local speed-up but a nonstandard answer to defend for zero portfolio gain; Deno, more so. Boring runtime, exciting product.
4. **Framework — the one real fork.** See §4. Short version: Astro is a misfit (the 42 configurations are 42 parameterized states of *one* stateful app, not 42 content pages — the draft board is a single permanently-interactive surface, so islands would frame the whole app as one giant island and you would fight the framework for nothing). Remix/React Router add nothing over Next here; SolidStart is great tech with a weak résumé keyword. So: SvelteKit or Next.js, by the decision rule in §4.
5. **Tailwind v4 + CSS custom properties; ECharts.** Tailwind because it is the vocabulary of the job ads — that is the honest, portfolio-driven reason — while the design tokens (the 32 team packs) stay plain CSS variables, which the Z-post-blue palette law ports onto cleanly. Charts: **ECharts** (Apache-2.0, free, dashboard-grade, tree-shake via `echarts/core`) as the default; Observable Plot if the Monte Carlo result views want tidy statistical graphics with less configuration; D3 only for a bespoke visualization neither covers. Pick one, don't mix.
6. **Cloudflare Pages + Workers.** Free, no card, 500 builds/month, effectively unlimited bandwidth, per-PR preview deploys native. Lock-in is deliberately low: the app is a static shell + one SQL database + pure-client compute; the shell redeploys to any static host in minutes. **Vercel Hobby** is the free, no-card alternative if Next wins the fork (100 GB bandwidth, non-commercial terms — fine here). **Fly.io** (no free tier since 2024), **Render** (spins down, and it hosts a server we will no longer have), **Railway** (trial credit only), **Deno Deploy / Firebase / AWS** — all solve a problem this architecture no longer has: a long-running server.
7. **GitHub Pages: only for a pure-static v1 — don't.** Phase 2 (accounts, cloud saves, share links) is already on the roadmap, and Pages is a dead end for it. Don't move in somewhere you already know you'll move out of.
8. **Player pools: versioned JSON in the repo + Zod at load.** Reviewable diffs, no service, no cost, no egress; the repo *is* the CDN via Pages. R2/S3/jsDelivr are pointless at this scale. sqlite-in-browser (sql.js), DuckDB-WASM, Parquet: skip — a 10k-row JSON parse is milliseconds. DuckDB-WASM is a delightful stretch-goal demo page, not architecture, and it costs megabytes of WASM for queries Drizzle + Dexie already cover.
9. **User data: D1.** Free, no card, never sleeps, Workers-native, Drizzle has a first-class adapter, and the free quotas dwarf this app's needs. The one real alternative: **Neon Postgres** (free, no card, scale-to-zero — brief cold start but no pause-to-dead); choose it instead if "Postgres" as a résumé keyword outweighs Cloudflare-native simplicity. **Supabase: no** for this project — its free tier pauses on inactivity, which is precisely the dead-demo failure mode. **PlanetScale: dead free tier.** **Firestore/DynamoDB:** NoSQL shapes the wrong way for roster/draft relational data. **Turso:** viable, but D1 is the path of least resistance inside the chosen platform.
10. **Drizzle.** Typed SQL, migrations, runs on Workers without a driver saga (Prisma's engine story on Workers remains friction), and its dialect portability is the swappable-DB insurance from rule 4. Kysely is excellent but is a query builder — you would rebuild migrations and relations yourself. Client side: **Dexie over IndexedDB** for saves and results cache, localStorage for tiny preferences — yes.
11. **Share links: a `shares` table in the D1 you already have.** The friend already ruled right. KV buys nothing extra here; Durable Objects are for coordinated state (live multiplayer, rate limiting) — nothing in v1 needs them. "One database, one backup story, one query interface" is also simply a better interview sentence.
12. **Better Auth** (over Auth.js, which works with SvelteKit but has a fiddlier config surface): first-class SvelteKit + Drizzle adapters, email/password + OAuth + passkeys built in, runs on Workers, MIT. "I evaluated Auth.js and chose Better Auth for the Drizzle-native adapter" is a good interview sentence. Managed providers (Clerk/Auth0/Supabase Auth/WorkOS/Firebase Auth): skip — the story becomes "I configured a vendor," and MAU ceilings sit on the demo path. v1 shape: optional sign-in (GitHub OAuth + email/password), core simulator fully usable anonymous, passkeys designed-for and shipped when stable, and the no-verification tradeoff volunteered in the README. Never hand-roll password hashing.
13. **pnpm, single package, no workspaces** — the friend is right. Turborepo/Nx/Moon pay off with multiple independently-built packages; you have one app and one engine *directory*. Enforce the engine boundary with an ESLint `no-restricted-imports` rule (`engine/` must not import the framework) — cheaper than a monorepo and it proves the boundary in CI. Promote to a workspace package when a second real consumer appears.
14. **Vite via the framework; vite-plugin-singlefile: no.** Inlining workers and ~1 MB of JS back into one HTML resurrects the exact artifact being escaped, and it fights module/worker splitting. Keep the legacy single-file build as an archival reference — it already has md5 pins and verify suites. If a "portable single file" product feature ever becomes real, that is a deliberate build target then, not the default pipeline.
15. **Vitest + Playwright: yes, the standard pair.** **fast-check: yes — the highest-ROI test investment in this project.** A sim is a random-process generator, which is exactly what property tests eat: no player drafted twice across all 42 configs; every team cap-compliant after every sim; standings points equal the sum of box scores; playoff bracket ↔ qualifying-teams bijection; two same-seed runs byte-identical. Stryker: skip initially — hours of CI for signal the golden-seed fixtures already give. Lint/format: **ESLint (flat config) + Prettier** — the friend's call wins on the interview lens because it is what the job listings name. Biome is faster and one tool, also legitimate; this is a keyword decision, and it is fine to say so and move on.
16. **Golden files: no tooling to adopt — just discipline.** Seeded RNG injected behind an interface (never `Math.random` inside the engine; xoshiro128\*\*/mulberry32 are fine), fixtures in git, Vitest JSON-equality against pinned expected outputs per config+seed. The sandbox already runs this philosophy headless (v8..v13 verify suites, drift-audit, asserted-patch scripts with post-checks) — port it, don't reinvent it.
17. **GitHub Actions, and make the repo public.** Free unlimited minutes on public repos, and the repo *is* the portfolio. Preview deploys per PR: Cloudflare native. Dependabot: yes, zero config; Renovate only if Dependabot's batching ever gets limiting; Changesets: no (one package, no versioned releases). GitLab CI/CircleCI/Dagger: no reason — the code already lives on GitHub.
18. **Compute: browser Web Workers.** Pool sized to `hardwareConcurrency`, seeds partitioned per worker, progress + cancel + checkpoint to IndexedDB (a 35-minute run must survive a refresh). Comlink is optional sugar; plain `postMessage` is fine. Queues/Workflows/DO and a small always-on server are all out under the free rules. If server authority is ever genuinely required, that is a new decision — polling first.
19. **Observability: skip Sentry/PostHog/Plausible.** At portfolio scale they are decoration. "I'd add Sentry when there are real users; here is the trigger I wrote down" beats an empty Sentry dashboard in an interview. Take Cloudflare Web Analytics (free, cookieless, one script tag) so the live link has a number attached. Console hygiene plus CI type/test gates are the real quality signals at this scale.

## 4 · The one real fork: SvelteKit vs Next.js

This is the only decision where the interview lens genuinely cuts both ways, so use a decision rule instead of taste:

- **If the target market's job listings are React-dominant** (typical for generalist frontend/full-stack roles): **Next.js (App Router)** on Vercel Hobby or Cloudflare via the OpenNext adapter. More keyword matches, and RSC/caching semantics are interview conversation material in their own right.
- **If the target skews product/startup shops, or the priorities are the cleanest technical narrative and the friend's co-maintenance:** **SvelteKit on Cloudflare.** Smaller keyword footprint, but the whole story (SvelteKit + Cloudflare + D1 + Drizzle + client workers) is coherent end to end, and "why not Next?" has a crisp, defensible answer.
- **The hedge that makes this low-stakes:** the engine stays framework-independent and the UI stays thin. Porting one framework to the other is then a 1–2 week chore, not a rewrite. Write the choice in a one-page ADR with the decision rule, the rejected options, and the reversal trigger — the ADR itself is a portfolio artifact.

My lean: the friend's SvelteKit call is sound and defensible **provided the Owner can narrate the Next.js tradeoff crisply** — he will be asked exactly that question, and having that answer ready *is* the interview skill being demonstrated. If the Owner's saved job listings are overwhelmingly React, flip to Next.js without guilt; nothing else in this advisory changes.

## 5 · What actually lands in an interview (portfolio artifacts)

1. **The deterministic engine with property tests and golden seeds.** A green test wall covering draft invariants, cap compliance, standings math, and 42-config initialization is the artifact; the test file names alone tell the story.
2. **ADR.md — six to ten one-pagers:** framework fork, client-side compute, D1 choice, auth shape, share links, single-file rejection, the four free-tier rules. Decisions with rejected alternatives and reversal triggers read senior.
3. **The migration discipline:** characterization tests over the legacy HTML, then wave-by-wave parity via seeded-run diffs before any intentional model change. "I proved equivalence before improving the model" is the sentence that separates engineers from framework users.
4. **A live link that never sleeps** (rule 2), with a traffic number attached (Cloudflare Web Analytics).
5. **A README that volunteers the shortcuts** (no email verification, no Sentry yet, single-file build retired) *with* the production answers. Naming your own tradeoffs first is the strongest junior→senior signal available.

## 6 · The revised stack, one paragraph

TypeScript end to end; Zod at load boundaries; the football engine framework-independent, deterministic (injected seeded RNG), property-tested with fast-check, and regression-pinned by golden fixtures; the UI in SvelteKit (or Next.js per the §4 decision rule) with Tailwind v4 plus CSS-variable team tokens and ECharts; simulation in a browser Web Worker pool with progress, cancel, and IndexedDB checkpointing; pnpm single package with an ESLint-enforced engine boundary; ESLint + Prettier, Vitest + Playwright; Cloudflare Pages + Workers hosting, D1 + Drizzle persistence, Dexie local cache, share links as D1 rows, Better Auth with GitHub OAuth and optional accounts; GitHub Actions CI with Dependabot and Cloudflare preview deploys; Cloudflare Web Analytics and nothing else. Everything free, no card, nothing on the demo path that sleeps, everything swappable if a free tier dies.
